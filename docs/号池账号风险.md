# 号池里的账号风险：会被封的是谁、因为什么、怎么止损

> 写这篇的原因：`方案A-多号池分钟级轮询.md` 第 9 节只有一张六行的风险表，太粗。
> 真正要决策的是"**我能不能拿一个真实微信号去干这件事**"，这需要把风险拆到
> "哪一层受损、能不能恢复、会不会牵连别的号"这个粒度上。
>
> 本文所有"微信侧机制"的说法都标了来源；没有来源的是我们的推断，会明写"推断"。

---

## 0. 一句话结论

**号池放大的不是频率风险，是环境风险。**

单号低频（2 小时查一次）本来很安全；可一旦把 N 份会话收到同一台机器、同一个出口、
同一个 UA、同一个节奏上去打，这 N 个本来互不相干的会话就长出了**同一个指纹**——
而这恰好是关联检测最容易抓的特征。

> 号池的技术价值（配额叠加）和风控成本（行为同质化）是同一件事的两面。
> 你能叠加多少配额，就同质化到什么程度。

---

## 1. 先把"封号"这个词拆开：三层主体

日常说法里"号被封了"混了三种完全不同的损失，恢复代价差三个数量级：

| 层 | 具体是什么 | 丢了要多久补 | 会不会牵连 |
|---|---|---|---|
| **会话** | 一份 `wap_sid2` + `uin/key/pass_ticket` | 重抓一次，**几分钟** | 不会 |
| **账号** | 一个微信号（实名主体的一个身份） | 补号 / 申诉，**几天~永久** | **会** |
| **主体** | 一张身份证下的所有微信号 | **不可恢复** | 全部 |

我们这条链路日常遇到的 `200013`、`-3`、验证墙，**全部只损第一层**。
把 `200013` 当成"号废了"是这类项目最常见的误判——它会让你不断丢弃还能用的凭据，
并且掩盖真正的原因（出口/频率）。

---

## 2. 六级梯度：从"被当爬虫"到"被当坏人"

| 级 | 表现 | 触发系统 | 受损层 | 恢复 | 我们的概率 |
|---|---|---|---|---|---|
| **L1 限流** | `ret=200013` | 接口反爬（频率/配额） | 会话 | 退避，分钟~小时 | 高，正常 |
| **L2 会话失效** | `ret=-3` | 会话过期或参数不配套 | 会话 | 重抓 | 高，正常 |
| **L3 验证墙** | 返回 HTML / 滑块 / captcha 页 | 出口+行为指纹 | **出口**为主 | 换出口，小时~天 | 中 |
| **L4 账号异常** | 微信弹"账号异常，需验证" | **账号安全模型** | 账号 | 短信/好友辅助，可能失败 | **低但最危险** |
| **L5 限制登录** | 封号（可申诉） | 违规处置 | 账号 | 申诉，数天~不给解 | 低 |
| **L6 永久封禁** | 不予解封 | 严重违规 | 账号 + **关联账号** | 无 | 极低（除非买号/涉黑产） |

**L1–L3 是"你被当成爬虫"，L4–L6 是"你被当成坏人"。这是两套系统，触发条件不同。**

- 前者看：请求频率、UA/客户端特征、Cookie 完整性、有无人类操作序列、IP 信誉。
  外部从业者的实测描述与此一致：*"微信的风控不是只盯单 IP 频率，还会看请求特征……
  客户端类型、User-Agent、Cookie 的完整性、甚至打开公众号主页到触发历史消息之间的
  '人类操作间隔'。这些特征一旦异常，风控系统不会直接封号，而是让接口返回异常数据，
  比如缺字段的 HTML 片段或直接跳转到验证码页面。"*
- 后者看：**行为性质**——是否批量注册、是否涉黑产、是否对抗平台策略。
  微信安全中心的公开公告里，被"永久限制登录"的都是涉诈"工具人"那一类
  （[2026-08 公告](https://news.qq.com/rain/a/20260821A03TSD00)），不是"读文章的人"。

所以：**只读公开文章、低频、单号，落在 L1–L3，是设计上可控的。**
但有三种做法会把它推向 L4+：

1. 用**买来的号**（号本身可能在灰名单里，来源不可知）
2. 用**主号/常用号**（一旦被牵连，损失不可承受）
3. 规模做到**"像一个号池"**（几十个号同 IP 同节奏，跟黑产工具链长得一样）

## 3. 最大风险源不是频率，是"环境跳变"

这是本文最想讲的一点。

一份 `wap_sid2` 不是"一行字符串"，它是一段**会话**。它在服务端伴随一组环境特征落地：
哪台设备、哪个微信版本、哪个网络出口、以及它是怎么被"走到"的（打开文章 → 进公众号 → 点历史消息）。
（推断，依据是 L3 的实际表现；微信未公开这些维度。）

而我们的用法是：**在手机微信里生成这个会话，然后拿回 PC/服务器上用 `requests` 打。**

具体有三处不一致：

| 维度 | 会话来源 | 我们请求时 |
|---|---|---|
| 网络 | 手机移动网络 | 家里宽带 / 云服务器 IP |
| 客户端 | 微信 WebView（真机型 UA） | `requests` + 抄来的 UA，无 TLS/JA3 特征，无 JS |
| 行为 | 打开文章 → 进号 → 点历史消息 | 直接 `GET profile_ext?action=getmsg` |

三处同时不一致 = 一份"突然出现在另一个环境里的会话"。
这解释了为什么有时候**第一次请求**就撞墙，而不是打了几百次才限流。

> 推论：**风险主要和"你换了环境去用这个会话"相关，而不是"你打了多少次"。**
> 一个只在微信 App 里自己用的会话，一天看十次历史消息不会有任何问题；
> 一个被搬到另一个 IP 上打 API 的会话，可能第一次就被拦。

对策只有两条，二选一，不要都想要：

- **A. 贴近**：让请求环境尽量像会话来源（同设备、同网络、同 UA）。
  这也是为什么 PC 微信 `--mode local` 抓的凭据比安卓副号抓的更"耐打"——
  它本来就在同一台机器、同一个出口上。
- **B. 低调**：做不到贴近，就把频率压到"不像程序"。L0 档（2 小时一轮）走的就是这条。

**号池是 A 的反面**：它把 N 份会话从各自的真实环境里抽出来，集中到一个新环境里打。
所以号越大，越依赖 B；而 B 的效率上限很低（一天几次）。

## 4. 连坐：四条通道，一条躲不掉

微信官方公告有明文（[2022-06 公告](https://news.qq.com/rain/a/20220614A04QD400)）：

> "对于多次违规及情节严重的违规者将加重处罚，视违规情况采取包括但不限于
> **封禁与该主体所有相关账号**、对确认违规支付账户进行冻结处理……"
>
> "平台将同步**追溯关联账号**，对团伙头目、代理以及发展下级的招募账号一并从严打击。"
> （[2026-08 公告](https://news.qq.com/rain/a/20260821A03TSD00)）

公开的法律咨询口径给的关联维度是：**相同身份信息、相同手机号、相同银行卡、
同设备登录、同 IP**（[法律快车](https://www.lawtime.cn/wenda/q_60431775.html)）。

按强度排序：

| 通道 | 强度 | 我们踩到的概率 | 说明 |
|---|---|---|---|
| 实名主体（身份证） | **最强**，官方明文 | 高（池号若都是自己的实名） | 一张证下的号视为一个主体 |
| 手机号 / 银行卡绑定 | 强 | 中 | 换绑也留痕 |
| 设备（同机登录过） | 强 | **高**（在同一台手机上切号抓凭据） | 设备指纹 |
| IP / 出口 | 弱 | **必然**（只有一条宽带） | 单条最弱，但会累积信誉 |

**对号池的含义**：第 4 条无法避免——我们只有一条出口。
所以必须守住一条硬规则：

> **池号和主号绝不能共享出口和设备。**
> 一旦池号所在的 IP 被标记，主号在同一 IP 上登录就是"自投罗网"。

这也是为什么"用自己的常用微信号跑号池"是这一整套方案里**唯一不可接受的做法**——
它不是"风险高一点"，它是"把不可恢复的资产放到可恢复性最差的路径上"。

## 5. 买号：唯一"技术上可行、风险不可控"的选项

如果不想用自己的实名，就会想到买号。这条路的风险结构和上面完全不同：

| 风险 | 说明 |
|---|---|
| **不可申诉** | 实名不是你的 → 封了就是沉没成本，人脸验证也过不了 |
| **来源不可知** | 批量注册的号权重低，可能在灰名单里；有的号历史发过违规内容 |
| **可被找回** | 原手机号/原好友保留找回能力。你付钱买的东西可能被拿回去，且对方能看到你用它干了什么 |
| **追责跟随号** | 号之前的行为记录跟着号走，不跟着卖家走 |

**结论：不建议。** 它不是"贵一点"，是"出了事你没有任何救济手段"。
而且它的使用痕迹仍然留在**你的** IP 和设备上——连坐通道一条没少。

## 6. 量化：风险拐点在哪

拿我们实际的强度对比"一个真人"：

| 档 | 规模 | 请求/天 | 折算到单个 biz | 像不像人 |
|---|---|---|---|---|
| **L0**（推荐） | 1 号 / 40 目标 / 2 小时一轮 | 480 | **12 次/天** | 像一个每天翻几次历史消息的人 |
| L1 | 3~5 号 / 10~20 分钟一轮 | 3k~6k | 75~150 次/天 | 像一个重度使用者，勉强 |
| L2（对标级） | 70 号 / 145 目标 / 62 秒一轮 | **4 万+** | 276 次/天 | **像一个集群** |

拐点很清晰：

- **≤ 5 个号**：5 份会话在一两个 IP 上还不构成"集群"特征；补号速率也人肉可承受
  （5 号 × 3 小时寿命 ≈ 每 36 分钟补一个）。
- **> 5 个号**：进入"号池特征"区间——多会话、同出口、同节奏、同目标集。
  这个组合本身就是机器批量的定义，无论你多慢。

所以**建议上限就是 5 个号**，而且这 5 个号只值"把 12 次/天提到 75 次/天"，也就是
把延迟从 2 小时压到 20 分钟。**如果不需要 20 分钟的时效，一个号都嫌多。**

## 7. 止损：代码里已经有的闸门

风险管不住的部分靠"别做"，管得住的部分已经写进 `tools/wxmp_pool.py`：

| 信号 | 单号处理 | 整池处理 |
|---|---|---|
| `0` 成功 | 清冷却、连败归零 | — |
| `200013` 限流 | `900 × 2^(n-1)` 秒，封顶 2 小时 | **不熔断**（这是频率问题，退避就够） |
| `-3` 无会话 | `3600 × n` 秒，连 3 次判死 | 不熔断 |
| **验证墙** `RET_WALL` | **4 小时**（账号级信号，不是"这个号不行"） | 记一次 trip |
| 网络/非 JSON 超时 | 300 秒 | **绝不熔断**（避免网络抖动把池停掉） |

**整池熔断**：30 分钟内累计 **3 次**撞墙 → 全池静默 1 小时，
`acquire()` 直接拒绝，`list_history` 遇到撞墙**不换号、直接抛**。

为什么撞墙不换号——这是整篇的设计要点：

> 撞墙说明**出口或行为模式被认出来了**。此时换一个号打同一个出口，
> 等于把还没被牵连的号一个个送进同一个已被标记的通道。停，比换更省号。

```bash
python tools/wxmp_spider.py pool --status     # 每号的配额/冷却/连败 + 熔断器状态
python tools/wxmp_spider.py pool --resume     # 换过出口、降过频率之后再开闸
```

登录类操作、写操作（关注/点赞/在看/转发/支付）一律不做——它们才是 L4+ 的入口。
我们只需要 `getmsg` 一个只读接口。

## 8. 早期信号清单（贴在显示器上那种）

出现任意一条，**立刻全停**，不要在同一个环境里试探：

1. **微信 App 里弹出"账号异常/需要验证"** → 已经到 L4，停手
2. **手机微信被要求重新登录** → L5 门口，立刻停，别再抓
3. **池号被限制加好友/发消息** → 号已受损，直接出池
4. **接口开始返回 HTML 而不是 JSON** → L3，换出口 + 降频（不要先换号）
5. **同一出口下"原本好的号"也开始 `-3`** → **出口被标记**，不是号的问题
6. `pool --status` 里出现连续 `fail` 且 `last_ret` 一直是同一个值 → 停下来读原因

第 5 条最容易被误判：看到好号也 `-3`，本能反应是"号过期了，重抓"，
结果重抓十次都没用——真正的问题是出口。

## 9. 红线

| # | 红线 | 理由 |
|---|---|---|
| 1 | **主号永不入池** | 不可恢复的资产不能放在可恢复性最差的路径上 |
| 2 | **池号不与主号共用设备/出口** | 连坐四通道里唯一躲不掉的是 IP |
| 3 | **不做任何写操作** | 关注/点赞/转发/支付才是 L4+ 的入口 |
| 4 | **不自动注册、不买卖号** | 出了事没有任何救济手段 |
| 5 | **同一台设备不登录多个池号** | 设备指纹是强关联通道 |
| 6 | **出现 L4 信号立即全停** | 继续试探只会升级处罚 |
| 7 | **号池不超过 5 个** | 超过就进入"集群特征"区间 |

合规面另外两条（不属于账号风险，但同源）：
只对采集方展示**标题 + 摘要 + 原文链接**，不二次分发全文；
不采集需要登录态/付费的内容。

## 10. 这些是不是在做之前就该想清楚

诚实地说：**如果你的目标是"看到新文章"，这套号池根本没必要。**

我们已经有的两条零凭据路径（`sogou` + `appmsgalbum`）加低频 `getmsg` 补漏，
在"不漏"上是够的（见 `方案A` 第 4 节：10 条缓冲 ≈ 5 天）。

号池唯一买到的东西是**时效**——把"2 小时内知道"变成"20 分钟内知道"。
为此要承担的成本是：

- 一个真实微信号（且不能是主号）
- 一条干净出口（不能和主号共用）
- 每 36 分钟补一次凭据
- 以及上面全部 7 条红线

**这笔交易在什么情况下划算？** 只有当你真的需要"事件当天就聚合"——
比如活动报名有截止时间、讲座名额有限。如果只是资讯浏览，2 小时延迟没有任何损失。

## 11. 还没验证的（别当成已知）

1. **撞墙的真实判定维度**——是 IP、UA、请求序列，还是组合？决定"换出口"有多大用。
2. **同 IP 多号是否连坐**——如果连坐，号池超过 1 个号就没有意义，必须一出口一号。
3. **`wap_sid2` 会不会因"环境跳变"提前失效**（而不是自然过期）。
   如果是，凭据寿命就不是 3 小时，而是"用一次就废"，整套号池的算术要重算。
4. **L4 的真实触发门槛**——目前只能靠"我们还没遇到"推断它很远，这不是证据。
5. **微信 UA 与 TLS 指纹的权重**——`requests` 的 JA3 和微信 WebView 差异极大，
   这可能是"第一次就撞墙"的主因，也可能无关。换 `curl_cffi` 之类的指纹伪装能不能改善，
   没测过（也不打算测——那属于对抗平台策略，是红线之外）。

前三条决定号池到底该不该存在，值得优先用**一个号、一周、低频**去观察。
观察期不要加号：先确认"单号在目标环境下能活多久"，再谈叠加。
