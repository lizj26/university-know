# 「更新一次网页」要多久（三校版）

> 本文回答一个问题：当前站点（**清华知道为外链** + **浙大 / 上交 / 西交三校**）跑一轮定时更新
> 要花多少时间，瓶颈在哪，以及为此保留了哪些优化。
>
> 数字分两类，文中严格区分：
> * **本机实测** —— 在本机跑出来的、可复现的数字；
> * **联网实测** —— 2026-10-11 一次真实联网测量（`tools/bench_update.py`，本地并行 6 复现云端
>   `matrix` 的并行方式），逐校耗时来自 `_work/bench-{cold,warm}.json`（现归档在
>   `_work/_archive/bak-20261011_1014.tar.gz`）。

---

## 1. 一轮更新由两段构成

| 阶段 | 干什么 | 并行度 | 谁在跑 |
|---|---|---|---|
| **fetch** | 每个校区抓自己的来源，产出 `data/<校区>.json` | **每校区一个 runner，完全并行** | GitHub Actions `matrix`（**3 条腿**：zju / sjtu / xjtu） |
| **build** | 把 `data/*.json` 全量内联进 `index.html` | 单进程，**不可并行** | `refresh.py --build-only` |

要点：**fetch 段的墙钟 ≈ 最慢的那个校区**，与校区数量无关；build 段与规模关系也很小。
当前 3 校里，**浙大一个人就决定了整轮时长的下限**（站群 WAF 限流，见 §4）。

---

## 2. 实测：build 可以忽略

本机 `python refresh.py --build-only`（当前 3 校 / 149 条）：

| 规模 | 合计条目 | 构建耗时 | index.html |
|---|---|---|---|
| 当前数据 | 149 | **1.22 s**（含 Python 启动） | **0.36 MB** |

历史上做过更大样本的离线基准（在临时目录里合成数据、真跑 `--build-only`）：

| 规模 | 合计条目 | 构建耗时 | index.html |
|---|---|---|---|
| 每校 40 条 | 2 992 | 0.81 s | 3.72 MB |
| 每校 80 条 | 4 232 | 0.86 s | 5.56 MB |
| 每校 160 条 | 6 712 | 0.94 s | 9.67 MB |

* 条目从 3 000 涨到 6 700，构建只多花 0.13 s —— **build 不是瓶颈**。
* 真正的代价是**页面体积**：条目翻倍，`index.html` 随之变大。当前才 149 条 / 0.36 MB，
  完全不用担心；只有当条目数回到数千级别时才需要重新盯这个指标。

## 3. 联网实测：逐校 fetch 耗时

环境：本机直连各校官网，参数 `--timeout 12 --retries 1`。浙大单独用低速档
（`--workers 2 --delay 2.0 --domain-delay 1.0 --rotate`）。

| 校区 | 冷启动（首次 / 数据丢失后重建） | 增量（平时的定时更新） |
|---|---|---|
| sjtu 上交 | 31.2 s / 95 请求 / 77 条 | **18.7 s / 29 请求 / 15 条** |
| xjtu 西交 | 152.6 s / 80 请求 / 63 条 | **14.6 s / 29 请求 / 17 条** |
| zju 浙大 | 508.7 s / 190 请求 | **190.4 s / 91 请求** |

（清华知道为外链，本站不抓取，故不计入；历史上它走上游接口 pkuknow.cn，慢在对端。）

---

## 4. 云端矩阵墙钟 ≈ 最慢那一腿

三条腿在 `matrix` 里**同时跑**，所以墙钟由最慢的校区决定：

* **稳态（增量）一轮 ≈ 3~4 分钟**：瓶颈是**浙大**（约 190 s），sjtu / xjtu 都不到 20 s；
  再加 build 约 1 s。
* **冷启动 ≈ 8.5 分钟**：浙大单腿约 509 s。
* 浙大之所以慢，是站群 WAF 按来源 IP 对整个 `zju.edu.cn` 域名累计限流；来源已从早期的
  44 个精简到 6 个，但它仍是唯一需要单独低速档的校区。

结论：**只要浙大能接受 3 分钟左右，整轮更新就是 3~4 分钟**；其余两校贡献可以忽略。

## 5. 离线微基准：增量抓取与超时的效果

`python tools/bench_fetch.py` 用本地模拟站点（HTTPS + 自签证书，页面结构与高校站一致）
跑**真实的 `crawl_campus`**，用来隔离「增量抓取」和「超时参数」各自的收益：

| 场景 | 用时 | 请求数 |
|---|---|---|
| cold 冷启动（`data/` 里没有这批 URL） | **19.3 s** | 54 |
| warm 增量（**URL 已在库 → 跳过正文**） | **1.19 s** | **6** |

再让 6 个来源里 3 个完全卡死（模拟被墙）：

| 参数 | 用时 |
|---|---|
| 旧参数 `--timeout 25 --retries 2`（卡死 = 25 s × 3） | **90.2 s** |
| 新参数 `--timeout 12 --retries 1`（卡死 = 12 s × 2） | **21.7 s**（省 76%） |

卡住一个来源的最坏耗时 = `timeout × (retries + 1)` —— 个别站卡死才是拖时长的元凶，
所以「缩短超时」比「加大并发」更有效。

## 6. 保留的优化清单

1. **增量抓取**：URL 已在 `data/` 即跳过正文请求，每轮省掉 90% 以上请求。
2. **增量轮也导入一次**：没有新稿时也刷新「上次检查时间 / 是否有新增」到页面。
3. **可配置超时** `--timeout`（默认 25 s）+ `--retries`，来源级可单独覆盖 `"timeout": 12`。
4. **来源级 `details: false`**：列表页自带日期的来源连新稿也不进详情页。
5. **`--workers` 4~6**：同校不同主机并行，同主机仍按 `--delay` 限速（礼貌抓取不变）。
6. **分校区独立 runner**（`matrix`，3 条腿）：墙钟 ≈ 最慢校区；只有 build 与提交是单点，
   避免并发写冲突。
7. **来源发现自动化**（`tools/discover_sources.py`）：按「官网 + 职能部门」口径自动探测
   并推导 `link_re`，新增校区时不必手工试。

## 7. 云端定时任务参数（当前）

```yaml
# 普通校区（sjtu / xjtu）
- campus: <key>
  command: python fetch_campus.py --campus <key> --workers 6 --delay 1.2 \
           --timeout 12 --retries 1 --no-build
# 浙大（站群 WAF 按 IP 对整域限流，只能压低速率换成功率）
- campus: zju
  command: python fetch_campus.py --campus zju --workers 2 --delay 2.0 \
           --domain-delay 1.0 --rotate --timeout 15 --retries 1 --no-build
```

`timeout-minutes` 保持 240：稳态一轮只要几分钟，但**冷启动**那一轮仍可能跑到 8 分钟以上，
留足余量比反复调参省事。三档定时（北京时间 09:00 / 12:00 / 22:00）在 3 校规模下绰绰有余。

## 8. 怎么自己跑一次真实测量

需要联网授权（沙箱会询问），建议在网络畅通时跑：

```bash
# 1) 只测构建（不需要联网，几秒钟）
python refresh.py --build-only

# 2) 离线演练抓取（本地模拟站点，不需要联网）
python tools/bench_fetch.py --sources 6 --items 8
python tools/bench_fetch.py --sources 6 --items 8 --hang 3 --hang-sec 45 --retries 2

# 3) 真实测量：三校，本地并行 3 路（≈云端矩阵的并行方式）
python tools/bench_update.py --campus zju,sjtu,xjtu --parallel 3 --extra "--timeout 12 --retries 1"
```

`tools/bench_update.py` 会逐个校区计时并汇总：每个校区的抓取用时、请求次数、条目数、
抓取阶段墙钟、串行等效耗时、最慢校区（= 云端矩阵的墙钟下限），最后再量一次 build 耗时。
