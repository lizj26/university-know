# 「群发级列表」：正常用微信能怎么拿到，以及 pkuknow 的通道可能是什么

> **结论先行**
>
> 1. **正常使用微信**能拿到「群发级列表」的途径只有 4 条：历史消息页、会话里的多图文折叠、
>    转发/收藏链接、PC 微信本地消息库。前三者是人工操作，第四条是唯一可自动化的低成本入口。
> 2. **官方从未开放**"任意公众号文章列表"的 API。第三方平台授权、公众平台后台都只能拿自己的号。
> 3. **pkuknow 最可能是"多号池 + `mp/profile_ext` 分钟级轮询"**（假设 A），
>    号池消息推送（假设 B）可能作为加速，商业供应商 API（假设 C）不能排除但证据偏弱。
> 4. 它的成本不在代码，在**号池的存活率**——这正好解释了作者那句"消耗挺多资金"。

---

## 0. 先把「群发级列表」这个词钉死

微信群发的原子结构：

```
一次群发 = 一个 mid（消息批次 id）
        └── 1..8 篇（idx = 1..8），每篇独立 sn（防篡改签名）
        └── chksm：列表接口为这批内容下发的校验串
        └── 整批共享一个发送时刻 sent_time
```

**实测（清华站 291 条微信样本 / 176 个批次）：**

| 指标 | 数值 |
|---|---|
| 多图文批次占比 | **38%**（67/176） |
| 若只取 `idx=1` 会丢的文章 | **115 篇 / 291 条 = 40%** |
| `url` 参数组合 | `__biz + chksm + idx + mid + sn`，291/291 一致 |
| 同批次内 `published_at` | **完全相同，连秒都一样**（12 组抽样，0 例不同） |

所以「群发级」不是形容词，是可测的形状：**按 `mid` 聚合、`idx` 连续、时间同源、带 `chksm`**。

这就引出了最重要的一条：**只拿推送里的首篇 URL，会漏掉 40% 的文章。**
这就是为什么"能拿到批次"比"能拿到文章"值钱得多。

### 字段指纹：怎么判断一份数据是从哪条路来的

| 指纹 | 群发级列表（getmsg 家族） | 文章级列表（搜索/RSS/时间线） |
|---|---|---|
| `idx` 覆盖 | 1–8 连续 | 多为 0 或 1，不连续 |
| `chksm` | 几乎 100% 有 | 常有缺失 |
| 同 `mid` 内时间 | 完全相同（含秒） | 逐篇各自时间 |
| 链接形态 | `?__biz=&mid=&idx=&sn=&chksm=` | 常是 `/s/<短码>` 短链 |
| 可翻页深度 | 很深（可回填数月） | 浅（搜一搜/搜狗约 10 条） |

下面所有的判断都建立在这张表上。

## 1. 正常使用微信，能拿到它的四条途径

### L1 · 用户界面（零技术，人工可见）

| # | 途径 | 操作 | 是否群发级 |
|---|---|---|---|
| 1 | **公众号「历史消息」页** | 手机：进入公众号 → 右上角人像 → 查看历史消息<br>PC 微信：公众号会话 → 历史消息 | ✅ **唯一在界面上以"批次"为结构呈现的入口**（背后是 `mp/profile_ext?action=home`） |
| 2 | **会话里的多图文折叠** | 群发消息下方「余下 N 篇」→ 点开 | ✅ 直接展开该批 `idx 1..N` |
| 3 | **转发 / 收藏到「文件传输助手」** | 逐篇转发 | ✅ 链接**保留 `chksm`**，是拿到"干净群发链接"最稳的人工方式 |
| 4 | 搜一搜 → 公众号 | 搜索号名 → 文章列表 | ❌ 文章级、不全、无 `chksm` |

> 注意 1 和 2 的区别：历史消息页是**按批次分组**的（一次群发一个卡片，卡片里 1–8 篇），
> 而搜一搜是**按文章平铺**的。后者拿不到批次边界，也就无从判断"这批到底几篇"。

### L2 · 客户端本地数据（正常登录，非官方 API）

| # | 途径 | 说明 | 是否群发级 |
|---|---|---|---|
| 5 | **PC 微信本地消息库** | 关注目标号后，每次群发在本地落一条 `appmsg`（`type=49`），XML 里含 `<url>`（带 `chksm`），且有批次 `msgid`。3.9.x 在 `Msg/Multi/MSG*.db` | ✅（**首篇**，同批其余篇需再请求一次 `appmsglist`） |
| 6 | 手机本地库 / 通知栏监听 | 本地库需 root；通知栏只有标题，拿不到 URL | ⚠️ 部分 |

**这条是最容易被低估的：个人微信号能关注的公众号上限约 1000 个**（好友 + 公众号合计约 5000）。
也就是说——

> **一个号就能关注全部 145 个清华号。** 不需要 145 个号，一个就够。

这让"号池"门槛从"买号养号"降到"一台常开电脑 + 一个号"。
代价是：账号必须 24h 在线，掉线/封号就漏，所以要配多个号轮换兜底。

### L3 · 官方 / 半官方接口

| # | 途径 | 能力边界 | 是否群发级 |
|---|---|---|---|
| 7 | 公众号后台「超链接」搜索（`cgi-bin/appmsg`） | 登录态下可搜任意号往期文章；**有调用额度、频繁会封** | ❌ 文章级；只能做冷启动回填 |
| 8 | 微信开放平台「第三方平台」（代运营授权） | **只能拿到授权给自己的号** | ❌ 145 个不相干高校号不可能都授权 → 排除 |
| 9 | 公众平台「素材 / 群发」接口 | 只有自己的号 | ❌ 无关 |
| 10 | 微信「搜一搜」开放接口 | 不对外 | ❌ |

**微信从来没有开放过"任意公众号文章列表"的公开 API。**
这是这件事的根本困难：官方渠道在结构上就不给你这个能力，所以所有方案本质都是"模拟一个用户"。

### L4 · 协议层（灰 / 黑）

| # | 途径 | 说明 |
|---|---|---|
| 11 | iPad 协议 / 安卓 hook / 桌面协议 | 直接收 sync 消息，**秒级**拿到群发 XML，含批次 `msgid` 与首篇 URL。可支撑号池规模化 |

这一层是商业数据供应商的主力实现方式，也是"能不能做大"的分水岭。

## 2. 对方通道的三个假设

### 假设 A：多号池 + `mp/profile_ext` 分钟级轮询 —— 我认为概率最高

**支撑证据：**

| 观测 | 含义 |
|---|---|
| `chksm` 100%、`idx` 1–8 齐全 | 只有**列表接口**是这个形状（推送只给首篇、搜索不给 `chksm`） |
| 同批 `published_at` 完全相同（含秒） | 时间取的是**批次级 `sent_time`**，不是逐篇 `ct` |
| 冷启动能回填约 120 天 | 只有列表接口能翻页回填；推送拿不到历史 |
| `last_sync` **每 62 秒**推进一次 | 轮询调度器节拍，不是事件驱动 |
| 145 号 × 62 秒 ≈ **8400 次/小时** | 单凭据必死（我们 10-10 那次 3 个号就撞 `200013`）→ **必须多号分摊** |

最后一行就是"消耗挺多资金"的算术：**不是买数据贵，是让几十个号活着贵。**

### 假设 B：号池消息推送 + 列表接口补全批

- 推送 `xml` 只带首篇 URL，要拿同批其余篇必须再请求一次 `appmsglist` —— 与观测的"全 `idx`"不冲突。
- 延迟可接近秒级，几乎不漏。
- **但**：62 秒的固定节拍更像轮询；且冷启动回填 120 天仍必须靠列表接口。
  → 更可能是"A 为主、B 做加速"，而不是纯 B。

### 假设 C：买商业数据供应商 API（新榜/清博一类）

**反证（较强，三条）：**

1. **站点没有任何阅读量 / 点赞 / 评论字段**（291 条样本，`read_num`/`like_num`/`comment_count` 命中 0）。
   而商业公众号数据 API 卖的核心指标恰恰就是阅读量。
2. 我实测**无会话裸开文章页 HTTP 200、正文完整、`appmsgBarData.read_num` 静态为空**——
   说明"自建裸抓"本来也拿不到阅读量。它的字段缺失与"自建裸抓"完全自洽。
3. `url` 被**重新规范化**（参数重排为字母序 `__biz, chksm, idx, mid, sn`，且没有 `scene`/`uin`/`key`/`pass_ticket` 残留）
   → 是**解析字段后重建 URL**，不是照抄 `content_url`。同时正文中位 4458 字、图片全部转 webp 自托管、
   `ai_summary`/`subjects`/`english` 全是自造字段 —— 一条完整自建管道的指纹。

→ 即便上游真买了列表，"正文 + 加工"也一定是自己的。**列表从哪来，仍是唯一不能确证的一环。**

### 明确排除的假设

| 假设 | 排除理由 |
|---|---|
| 第三方平台授权 | 145 个不相干高校号不可能都授权给它 |
| 搜一搜 / 搜狗微信 | 文章级、约 10 条上限、无 `chksm` |
| 公众号后台超链接搜索 | 额度撑不起分钟级；只能做回填 |
| 微信读书通道（we-mp-rss 那类） | 小时级延迟、限流严、无阅读量，撑不起 62 秒节拍 |

## 3. 我的判断，和诚实的边界

**判断**：**A 为主**（多号池轮换 + 分钟级轮询列表接口），B 可能作为加速，C 不能完全排除。

**无法确证的**（只有作者知道）：具体有多少号、号从哪来、是官方接口还是 iPad 协议、
有没有买供应商的列表。这些不影响我们抄机制，只影响我们判断"要不要也烧这个钱"。

**方法论上值得记一笔**：这次能收敛到 A，靠的不是猜，是三条硬指纹——
`chksm` 覆盖率、同批时间是否同源、以及**"缺少哪些字段"**。
最后一条最容易被忽略：**没有阅读量，本身就是一条强证据。**

## 4. 对我们（university-know）的可执行结论

| 目标 | 能不能抄 | 怎么做 |
|---|---|---|
| "不漏"的机制 | ✅ 能 | `history --watch` 已实现（第一页增量 + 去重账本 + 缺口重试） |
| 分钟级频率 | ❌ 不能 | 单凭据 30 分钟~3.5 小时过期，且 3 个号就撞限流 |
| 长期无人值守 | ⚠️ 有条件 | 见下 |
| 正文 + AI 加工 | ✅ 能 | 这部分完全不依赖微信通道，性价比最高 |

**唯一低成本能同时满足"长期 + 不漏"的路**：一个号关注 40 个目标号 + PC 微信本地库读取。
技术上完全可行（一台常开 Windows 就够）。

**但必须说清楚代价**：这条路要读微信本地数据库，属于**修改/注入客户端**，
违反微信用户协议，**封号是真实风险**，且一旦封号，整条管道断掉。
这是产品决策，不是技术决策——建议先用"低频 `--watch` + 手动 `getmsg` 补漏"跑一段时间，
统计"基本不漏"能不能满足需求，再决定要不要碰这条路。

## 附：怎么自己验证一份数据的来源

拿到任何一份微信文章数据，按这张表对一遍就能判断它的出身：

1. 抽 20 条，看 `idx` 是否出现 2–8 → 有 = 群发级；全是 1 = 只拿了首篇或文章级
2. 看 `url` 有没有 `chksm` → 有 = 列表接口产物
3. 找同 `mid` 的多篇，比 `published_at` → 完全一致 = 批次时间；各不同 = 逐篇 `ct`
4. 看有没有 `read_num` → 有 = 有会话态或买了供应商；无 = 裸抓
5. 看 `url` 参数是否被重排/清洗 → 重排 = 解析后重建，说明作者懂结构

前三条定"是不是群发级"，后两条定"通道有没有会话态"。
