# 用 wxmp 接入微信公众号

面向要给「XX 知道」补全**官方微信公众号**内容的人。目标是：不靠官网转载，直接把某个公众号
最近的推文成批抓回来，合并进 `data/<校区>.json`，在页面上以「微信公众号」来源分组展示。

> **本文讲的是「公众号链路」（不稳定）**，它和「官网链路」（稳定）在磁盘上完全分开：
> 本文提到的所有文件（cookies / token / 名单 / fakeid / 中间产物）都在 **`_work/wechat/`** 里，
> 而 `refresh.py` / `fetch_campus.py` 的产物在 `_work/` 根下。两条链路只往同一份
> `data/<校区>.json` 里追加，所以页面合一，但任何一条断了都不影响另一条。
> 完整目录对照见 [目录结构.md](目录结构.md)。
>
> 老版本把这些文件放在 `_work/` 根下，首次运行 `fetch_wechat.py` 会**自动迁移**到
> `_work/wechat/`，读取时也会回退旧位置，升级不会丢东西。

---

## 0. 它现在是流水线的第三步

公众号抓取已经接进无人值守入口，不再是单独的脚本：

```bash
python cloud_update.py --with-wechat          # 清华 → 三校 → 公众号 → 重建页面
python cloud_update.py --wechat-only          # 只跑公众号这一步
python cloud_update.py                        # 默认**不跑**公众号（原因见第 9 节）
```

`cloud_update.py` 会把它的上千行进度收进 `_work/run.log`，终端只留一行结论，
并把三种「看起来成功但实际没拿到内容」的情况翻译成人话，例如：

```
⚠ 公众号：被微信**账号级限流**(ret=200013 freq control)，本轮没有拉到任何文章列表，
  已保留旧数据。……解禁后重跑即可（fakeid 已缓存，不会再走搜索）
```

### 0.1 一个重要改动：名单里的 `max` 会被外部文件覆盖

早期版本里，`_work/wechat/wxmp-accounts-<校区>.json` 写成 **`{"浙江大学": {"max": 15}}`**
（「名称 → 参数」写法）时，如果这个名字在内置 `WECHAT_CONFIG` 里也有，
外部给的 `max` 会被**静默丢掉**，退回 `--count` 的默认值。

现在外部名单是**更新**语义：同名条目的 `max` / `fakeid` 会用外部的值覆盖。
所以下面三种写法效果一致，随便用哪种。

## 1. 为什么需要单独一个脚本

微信公众号**没有公开的文章列表接口**，所以原来 `fetch_campus.py` 只能被动发现内容：
只有当某篇公众号文章出现在学院官网页面里时，才会被顺手抓走。

`wxmp` 走的是另一条路——**微信公众平台后台接口**（`searchbiz` 搜号 + `appmsg` 拉历史文章列表）。
它需要登录后的 cookies，因此单独放在 `fetch_wechat.py`，不与纯公开抓取混在一起。

```
                 ┌── 公开链接（无凭据）──→ fetch_wechat.py --public-seed ─┐
官方公众号文章 ──┤                                                      ├─→ data/<校区>.json ─→ index.html
                 └── 后台接口（需 cookies）→ fetch_wechat.py（wxmp）─────┘
```

两条路产出的 item 结构**完全一致**（`dt.sg = "wechat"`），页面上都归入「微信公众号」来源分组。

### 1.1 API 模式下也会补抓种子链接

`fetch_campus.py` 会读 `_work/wechat/wechat-<校区>.txt` 逐篇抓正文；`fetch_wechat.py` 在 API 模式下
**也会把这份种子清单里尚未入库的链接补抓一遍**（`--no-seed-fallback` 可关）。
这样「名单外的号」「本轮被限流的号」的内容不会因为走了 API 模式就漏掉。

## 2. 安装

```bash
pip install wxmp          # 需要 Python >= 3.10
```

> `refresh.py` / `fetch_campus.py` 仍只用标准库，**只有本脚本**需要 wxmp。
> 注意 wxmp 会连带装 pydantic / pandas / requests / fake-useragent / loguru / tqdm，
> 体积不小。它的**公开种子模式不需要 wxmp**（只用到 `urllib`），所以没装也能跑。

## 3. 拿到 cookies（API 模式的关键）

微信公众号后台接口必须登录后才能访问，步骤：

1. 用浏览器登录 <https://mp.weixin.qq.com/>（自己注册一个订阅号即可，无需粉丝）；
2. 按 `F12` → **Network** → 刷新页面 → 点任意一个 `cgi-bin/...` 请求；
3. 在 **Request Headers** 里找到 **`Cookie:`**，**右键 → Copy value**（整行，很长）；
4. 存成下面任一文件（推荐第①种，整行粘贴即可，脚本自动解析）：

   | 文件 | 说明 |
   |---|---|
   | `_work/wechat/wxmp-cookie-header.txt` | **推荐**：把整行 `Cookie: ...` 原文粘进去（带不带 `Cookie:` 前缀都行） |
   | `_work/wechat/wxmp-cookie-header-<校区>.txt` | 分校区版本，优先于全局 |
   | `_work/wechat/wxmp-cookies.json` | 老格式：JSON `{"wxuin": "...", "slave_sid": "...", ...}` |

   关键字段：`wxuin`、`slave_sid`、`slave_user`、`slave_bizuin`、`data_ticket`、`bizuin`。
   另外页面 URL 里的 `token=xxxx`（一串数字）如果自动获取失败，可存到
   `_work/wechat/wxmp-token.txt` 作为手动 token。

5. 验证：

   ```bash
   python fetch_wechat.py --dry-run
   ```

   输出 `dry-run：cookies 有效，token = xxxxx` **只说明文件被读懂了、token 有了**，
   ⚠ 不说明会话还活着——过期的 cookie 也会打印这句（详见 3.2 的警告框）。
   要确认会话真的可用、且没被限流，跑：

   ```bash
   python tools/wxmp_spider.py diag --campus zju
   ```

> cookies 有时效（通常几天）。过期后重新登录复制一份覆盖即可。
> 本脚本**不会**上传或外传 cookies，只在本机请求微信。

### 3.1 重要：`appmsg` 列表接口有账号级限流

微信对**「拉某个号的历史文章列表」**这个接口（`cgi-bin/appmsg`）有**账号级频率限制**：

- 触发后返回 `ret=200013`（`freq control`），**与参数、频率无关**，是账号维度的限流；
- **新登录 / 长期未使用**的公众平台账号，几乎必然先被限流一段时间，通常需**等待数小时至 1 天**解禁；
- 期间 **`searchbiz`（搜索公众号）完全正常**，只有拉列表被拒；
- 所以正确姿势是：**先用完整名单把 fakeid 全部锁定缓存**（这一步不受限流影响），
  等限流解禁后直接跑抓取即可，无需再搜索。

脚本已内置识别：遇到 200013 会打印明确提示、退避重试几次，仍失败则跳过该号、
**不写坏数据**。等几小时或次日重跑 `python fetch_wechat.py` 即可。

> **⚠ 2026-10 更正（重要，先读 10.13）**：上面这套「等几小时就好」只对**旧的账号级限流**成立。
> 2026-07-30/31 起微信把「跨公众号拉文章列表」这个**能力**收紧了——新登录的号
> **第一页第一条**就返回 `200013`，**等多久都不恢复**，换账号也没用。
> 判定办法：`tools/wxmp_spider.py diag`，或看 `_work/wechat/wxmp-diag-*.json` 里的
> `verdict`。`account` 且换了凭据仍复现 → 属于接口级，别再等，直接走 10.13 的三条替代路。
>
> 另：`cgi-bin/appmsgpublish` 在今天（2026-10-24）的实测里同样存在但同样受限，
> 旧的「它返回 200009 所以也不可用」说法已过期。

### 3.2 更省事的取法：扫码自助登录（不用 F12 手工复制）

手工复制 Cookie 最容易出错的不是复制本身，而是**复制了不完整的字段**（少了
`data_ticket` / `xid` 之类），服务端拿到的就是个"半登录"会话，行为很怪。
2026-10 移植 pkucli 方案时补了自助登录，把这件事变成扫码：

```bash
PY="C:/Users/Kevin/.workbuddy/binaries/python/envs/default/Scripts/python.exe"

# ① 扫码（终端会画出二维码，同时存一份 jpg）
$PY tools/wxmp_spider.py --home _work/wxmp-spider login

# ② 导出成主链路认的 Cookie 头（第 2 份凭据；覆盖要加 --force）
$PY tools/wxmp_spider.py --home _work/wxmp-spider export-cookie \
    --to _work/wechat/wxmp-cookie-header-pool2.txt --write-token

# ③ 判定这份 cookie 到底活没活、有没有被限流（**这一步才是真校验**）
$PY tools/wxmp_spider.py --home _work/wxmp-spider diag --campus zju

# ④ 主链路干跑一遍（只搜号、不写数据）
$PY fetch_wechat.py --dry-run --campus zju
```

> ⚠ **别把 `--dry-run` 当活性校验**。它只检查"token 拿没拿到"（`fetch_wechat.py:1984`），
> 而 token 还能从 `wxmp-token.txt` 里的旧值兜底——所以**过期的 cookie 也会打印
> 「cookies 有效」**。2026-10-24 用 10-10 那份早已 `200003` 的 cookie 实测复现了这个假阳性。
> 真正会打 `searchbiz` 的是 `diag`，先看它的结论，再看 `--dry-run`。

两条命令的分工：`diag` 回答的是**"这份凭据能不能用、被限在哪一级"**
（`credential_expired` / `account` / `target` / `ok`）；
`--dry-run` 回答的是**"主链路读不读得懂这个文件"**。`diag` 报 `ok`/`target` 才值得跑真正的一轮。

> 第 ② 步的 `pool2` 是刻意选的：它不会覆盖你现有的第 1 份凭据，而是作为轮换池的第二格
> （见 10.3）。直接写 `wxmp-cookie-header.txt` 也行，但那会顶掉旧凭据。
> `--write-token` 是可选的，主链路本来就会从首页跳转里自动提取 token，
> 只有当自动提取失败（`200009` 一类）时才需要它兜底。

## 4. 运行

```bash
python fetch_wechat.py                       # 三校全抓，写入 data/ 并重建页面
python fetch_wechat.py --campus zju          # 只抓浙大（zju / sjtu / xjtu）
python fetch_wechat.py --count 10            # 每个号最多取 10 篇（默认 15）
python fetch_wechat.py --pages 2             # 每个号最多翻 2 页（每页 5 篇）
python fetch_wechat.py --no-content          # 不抓正文，只用列表摘要（快、稳）
python fetch_wechat.py --no-seed-fallback    # API 模式下不补抓种子链接
python fetch_wechat.py --no-import           # 只抓取，结果落在 _work/wechat/wechat-items-<校区>.json
python fetch_wechat.py --import-only         # 不联网，用上次结果导入并重建页面
python fetch_wechat.py --cookies my.json     # 指定 cookies 文件

# 没有 cookies 时的降级路径：用公开文章链接当种子逐篇抓正文
python fetch_wechat.py --public-seed --public-max 80
```

**没有 cookies 时**脚本不会报错，而是自动降级为「公开种子」模式：读取
`_work/wechat/wechat-<校区>.txt`（以及 `data/` 里已有的 wechat 链接）、逐篇抓公开正文，
走**完全相同**的入库 / 展示链路。补齐 cookies 后，API 模式会自动接管并按号成批拉取。

## 5. 配置要抓哪些公众号

### 5.1 为什么可以放心用「完整名称」

微信公众平台的**昵称是全平台唯一的**——同一个昵称只能被一个号注册（改名后旧名也不会立刻释放）。
所以我们**按完整昵称精确匹配**就能唯一命中目标号，然后锁定它的 `fakeid`。
`fakeid` 一旦确定，拉文章列表就与昵称无关了，因此**名称里不含「浙大 / 交大」等关键词的号**
（如「竺院团学汇」「浙里等宁」「ZJUPES」）也能被稳定收录。

匹配规则（脚本按此顺序判定）：

1. 名单里给出的完整昵称 → 去空白 / 全角转半角 / 统一大小写后**精确相等** → 收录；
2. 命中后把 `fakeid` 缓存到 `_work/wechat/wxmp-fakeid.json`，之后**不再依赖搜索**（号改名、搜索被限流都不怕）；
3. `filter` 正则**只作兜底**：万一没精确命中（搜到擦边号），才用它判断昵称是否属于本校，避免误收同名社会号。

> 注意：`searchbiz` 是**模糊搜索**，搜「浙江大学」会返回「浙江大学校友总会」「浙江大学本科生院」等一堆，
> 所以脚本不是"取第一个"，而是**在结果里挑规范名完全相等的那个**。这也是为什么给**完整昵称**最稳。

### 5.2 推荐：把完整名单写进外部文件

不必改脚本，把名单放这里即可（会自动与内置配置合并）：

| 文件 | 作用 |
|---|---|
| `_work/wechat/wxmp-accounts.json` | 全局，所有校区共用 |
| `_work/wechat/wxmp-accounts-<校区>.json` | 分校区（如 `wxmp-accounts-zju.json`），优先合并 |

支持三种写法，任选其一：

```json
// ① 纯名称数组（最省事）
["浙江大学", "浙江大学本科招生", "竺院团学汇", "浙里等宁", "ZJUPES"]

// ② 带参数
{ "accounts": [ {"name": "浙江大学", "max": 15}, {"name": "竺院团学汇", "max": 10} ] }

// ③ 名称 → 参数（可选 fakeid，填了就跳过搜索）
{ "浙江大学": {"max": 15}, "竺院团学汇": {"max": 10, "fakeid": "MzA3Mjk2NzE..."} }
```

### 5.3 或者：直接改脚本内置清单

编辑 `fetch_wechat.py` 顶部的 `WECHAT_CONFIG`。**加一个号 = 加一个 dict**：

```python
WECHAT_CONFIG = {
    "zju": {
        "campus_name": "浙大知道",
        "filter": r"浙江大学|浙大|ZJU",          # 仅兜底
        "accounts": [
            {"name": "浙江大学", "max": 15},
            {"name": "竺院团学汇", "max": 10},     # 名称不含关键词也 OK
            {"name": "浙里等宁", "max": 8},
        ],
    },
    # "xxx": {"campus_name": "XX知道", "filter": r"XX大学|XX", "accounts": [...]},
}
```

新增一个**校区**只要：① 在 `WECHAT_CONFIG` 加一个键（键名 = `data/<key>.json` 的文件名）；
② 保证 `data/<key>.json` 存在。页面校区切换栏会自动认这个新数据文件。

### 5.4 名单外的公开种子号

即使某个号不在名单里，只要它的文章链接出现在 `_work/wechat/wechat-<校区>.txt` 里，
且**标题**含本校关键词，在「公开种子」模式下也会被收录（名单只影响 API 模式的按号抓取）。

## 6. 合并规则与数据安全

- **按文章链接去重**：`i` 字段就是文章 URL，同名条目覆盖、新条目追加，历史条目保留；
- **90 天保留期**：发布超过 90 天的条目会在写入和生成页面时自动清除（时间未知的不清）；
- **写入保护**：复用 `refresh.py` 的原子写入 + `.bak` 备份机制；
- **来源注册表**：每个公众号在 `source_registry` 里登记一条（`kind = "wechat-wxmp"`），
  页面「信息来源」抽屉会显示它的条数与状态徽标（最近更新 / 无新内容 / 采集失败 / 待接入）；
- **`last_import` 是结构化 dict**：与 `refresh.py` / `fetch_campus.py` 口径一致
  （早期版本写的是字符串 `"fetch_wechat.py / wxmp · 新增 0 条"`，会让页面与
  `cloud_update.py` 摘要读不出「新增/更新」两列，已统一）。

### 6.1 与 `fetch_campus.py` 会不会重复抓同一篇？

不会入库两次，但**同一篇会被网络请求两次**。原因是两个脚本都会读
`_work/wechat/wechat-<校区>.txt`：

| 脚本 | 怎么处理这个清单 |
|---|---|
| `fetch_campus.py` | 清单里每篇都抓一遍正文（作为「手工补充来源」） |
| `fetch_wechat.py` | API 模式下**只补抓尚未入库**的那些（`--no-seed-fallback` 可关） |

两条路产出的 `i` 都是文章 URL，所以合并端按 `i` 去重，页面不会出现两条。
想彻底省掉重复请求，二选一：
* 把清单只交给一个脚本（例如从 `fetch_campus.py` 撤掉，全靠 `fetch_wechat.py`）；
* 或给 `fetch_campus.py` 传 `--wechat-file /dev/null` 之类指向空文件。

## 7. 页面展示位置

抓来的文章在页面上有三处可见：

1. **来源筛选**：工具栏「微信公众号」分组下会多出这些号，点击可只看某个号；
2. **卡片列表**：卡片上的来源名即公众号名，详情弹窗里有正文摘录与「阅读原文」；
3. **信息来源抽屉**：看到每个号的条数与最近状态；已登记但没抓到文章的号显示为「待接入」。

## 8. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `获取 token 失败` | cookies 过期或复制不全 | 重新登录公众平台，覆盖 cookies 文件 |
| 拉列表全部 `ret=200013` | 账号级限流（freq control） | 属正常，**等数小时至 1 天**再跑；期间搜号不受影响 |
| `ret=200009` | 走的是 `appmsgpublish` 接口 | 同样等解禁；本脚本主用 `appmsg` |
| `搜索「XX」失败` | 号名不精确 / 接口限流 | 用**完整官方昵称**；降低频率、隔一会再跑 |
| 搜到同名社会号 | 名字重名（擦边号） | 收紧 `filter` 正则，或直接填 `fakeid` |
| 名单里的号没抓到 | 摸不到精确匹配 | 核对完整昵称；或直接在名单里补 `fakeid` |
| 改了外部名单的 `max` 没生效 | 旧版本会静默丢掉 | 已修复（外部名单现在会覆盖内置值）；不行就直接传 `--count` |
| `fakeid` 变了 / 抓错号 | 搜索返回了别的号 | 删掉 `_work/wechat/wxmp-fakeid.json` 里对应项，重跑 |
| `每轮取回 0 篇` | 该号近期没更新 / 接口风控 | 属正常；确认 cookies 与号名，稍后再试 |
| 正文为空 | 文章是图片/视频号内容 | 只入库标题与摘要，属正常 |
| 文章被删（含 `tempkey=`） | 原文已失效 | wxmp 的 `is_valid_article_link` 会判为无效，跳过 |
| `未能加载 wxmp` | 没装 wxmp（或解释器不对） | `pip install wxmp`；注意要用**同一个** Python 解释器。没有它也能跑公开种子模式 |

## 9. 合规提醒与"为什么云端默认不开"

- 只抓**公开**可读内容；API 模式仅用**你自己**登录的凭据，不要共享或外借他人 cookies；
- 控制请求频率（所有等待都走 `gentle_sleep()`，在基准值 ±35% 内随机抖动，
  而不是固定间隔——见第 10.5 节），不要暴力刷接口；
- 抓回的内容版权归原作者与发布单位所有，本页面仅作展示与检索，**请勿用于商业用途**。

### 9.1 云端定时任务里为什么默认关掉公众号

`cloud_update.py` 只有在显式 `--with-wechat`（云函数里是 `WITH_WECHAT=1`）时才跑这一步，
原因是它在无状态云函数里有两个硬障碍：

| 障碍 | 说明 |
|---|---|
| **cookies 是账号凭据** | 只有你浏览器登录公众平台才有，几天就过期。放进函数环境变量 = 把账号凭据长期放在云端 |
| **wxmp 依赖链** | pydantic / pandas / requests / fake-useragent / loguru / tqdm，与「阿里云侧零第三方依赖」的打包方式冲突，还要挂 Layer |
| **无持久盘** | `_work/wechat/wxmp-fakeid.json` 这类缓存每轮都会随沙箱销毁 —— 好在这不会丢数据（丢了只是重新搜索） |

**推荐做法**：官网抓取（清华 + 三校）留在云端定时跑，**公众号留给本机**手动或本机定时任务跑。
两者写的是同一份 `data/<校区>.json`，靠「按 `i` 只增不减合并」天然可以交替进行 ——
云端不认识公众号那些 `wx:` 来源，但 `refresh.import_items` 会保留它们。

只有确实需要在云端跑时才：
1. 在 **Linux** 环境打包：`python deploy/serverless/package.py --with-wxmp`；
2. 把 cookies 放进函数包（**注意凭据风险**），或改用环境变量注入；
3. FC 控制台设 `WITH_WECHAT=1`。

## 10. 限流（ret=200013）：为什么"等一天"不是解法

这是公众号链路最容易被误解的一点，值得单独讲清楚。

### 10.1 之前的问题

早期版本遇到 `200013` 的处理是：识别 → 本轮中止 → 提示「等数小时至 1 天解禁」。
问题在于**有些限流等不好的**——它会一直持续，等到第二天重跑还是 0 篇，
然后你又被告知"再等等"。整个链路就成了死循环。

根子在于当时把所有 `200013` 都当成了同一种东西，于是只能给出一种建议。

### 10.2 两种粒度，处置方式完全不同

现在脚本会把限流**分粒度判定**并分别记录（`_work/wechat/wxmp-blocked.json`）：

| 粒度 | 怎么判定 | 处置 |
|---|---|---|
| **账号级** | 连续 3 个号取回 0 篇，**且本轮没有任何号成功** | 换一份凭据，**等无效** |
| **fakeid 级** | 连续 3 个号取回 0 篇，**但本轮有号是成功的** | 只坏在这几个号上，记入名单 6 小时内跳过 |

判定逻辑很朴素但有效：如果这份 cookies 连一个号都搞不定，那是**凭据**的问题；
如果它还能搞定别的号，那是**那几个号**的问题。两者混为一谈时，
你就只会得到"等一天"这种没用的建议。

### 10.3 解法一：凭据轮换池

账号级限流**唯一的解法是换一个登录账号**。把多份 cookies 放进 `_work/wechat/` 即可：

```
wxmp-cookie-header.txt            ← 第 1 份（原有命名，照常生效）
wxmp-cookie-header-pool2.txt      ← 第 2 份
wxmp-cookie-header-pool3.txt      ← 第 3 份
```

最省事的写法是把所有行塞进**同一个文件**，一行一份：

```
_work/wechat/wxmp-cookie-header-pool.txt
```

脚本按**日期**决定用哪一份（同一天多次运行结果一致，出问题可复现），
并且发现当前这份最近被限过时会**自动跳到下一份**。

```bash
python fetch_wechat.py --cred-index 1     # 手工指定用第 2 份
```

配套改动：`fakeid` 缓存也**按凭据分文件**存（`wxmp-fakeid-pool2.json`）。
原因是 fakeid 不是公开常量，而是「某个登录账号搜出来的结果」——
把 A 账号搜到的 fakeid 直接喂给 B 账号去拉文章，在微信看来就是
「B 突然开始访问一个它从没搜过的号」，这正是风控的典型特征。

### 10.4 解法二：公开合集源（零凭据、不受限流）——**推荐优先用**

`appmsg` 有账号级限流，但**公开合集接口没有**：

```
GET /mp/appmsgalbum?action=getalbum&__biz=<biz>&album_id=<id>&f=json
```

2026-10-14 用真实 `album_id` 实测：**`ret=0`，无需任何登录态**，直接返回文章列表
（标题 / 链接 / `create_time`），因此**限流期间依然可用**。

#### 合集 ID 不用人工找，脚本会自动发现

微信把合集链接直接印在文章页里：

```
mp/appmsgalbum?__biz=<biz>&action=getalbum&album_id=<id>#wechat_redirect
```

所以链路是：

```
公开种子的文章页  →  自动解析出 (__biz, album_id)  →  枚举合集文章  →  抓正文
```

**只要有一篇该号的文章链接，就能自动找到它的合集**，不需要维护白名单。
（`extract_album_refs()` 把 `__biz` 与 `album_id` 限定在「同一个链接内」配对，
避免页面别处的 `__biz` 被误配。）

用法：

```bash
python fetch_wechat.py --albums                  # 正常抓取 + 合集补充（去重后合并）
python fetch_wechat.py --albums-only             # 完全不用 cookies，只抓合集
python fetch_wechat.py --albums-only --album-pages 4   # 每个合集多翻几页
```

实跑样例（西安交大，**无 cookies**，10 个种子链接）：

```
· 从 10 篇文章页自动发现合集… → 发现 3 个合集
    - 学院新闻: 取回 40 篇，收录 40 篇
    - 学生风采: 取回  6 篇，收录  6 篇
    - 校友故事: 取回 19 篇，收录 19 篇
· 合集合计 65 条          ← 抓到了正文（dt.tx 有完整内容）
```

**10 条种子 → 65 篇带正文**，全程零凭据、零 `appmsg` 调用。

#### 翻页实测有效

`continue_flag=1` 时，带上一页末条的 `msgid` / `itemidx` 再请求即可续取，每页 10~20 条：

```bash
--album-pages 4    # 每集最多翻 4 页
```

「新闻动态」「浙大等你」「竞赛展演荣誉」等合集都翻出了第二页（+20 篇）。

#### ⚠ `chksm` 是能不能抓正文的关键（受控实测）

微信对文章页链接分三种，**同一条文章**做了对照：

| 链接形式 | 例子 | 结果 |
|---|---|---|
| 短链 | `/s/XLsEsQOyo4qwtekckfDT2A` | ✅ 3.7 MB，正常 |
| **长链带 `chksm`** | `/s?__biz=..&mid=..&sn=..&chksm=..` | ✅ 3.6 MB，正常 |
| 长链**缺** `chksm` | `/s?__biz=..&mid=..&sn=..&scene=21` | ❌ 17 KB 验证码墙 |

差别**只在 `chksm`**。后果有两个：

- ✅ **合集接口返回的链接带 `chksm`，能抓正文** → 全量内容可用；
- ❌ 文章末尾「往期回顾」里的链接**没有** `chksm`，抓不动 →
  只能拿标题做**展示/跳转**，不能拿来继续扩链（所以链接图无法递归）。

#### 手工指定（可选）

不想依赖自动发现，也可以直接配 `_work/wechat/wxmp-albums.json`：

```json
{
  "albums": [{"biz": "MzA5...", "album_id": "1234567890", "name": "招生简章"}],
  "zju":    ["MzAx...:9999999999"]
}
```

> `albums` 是**全局**列表；按校区名分组的写法只对那个校区生效。
> 缩写 `"biz:album_id"` 和完整对象两种写法都认。
> **有清单就优先用清单，没有才去自动发现。**

#### 边界（要清楚）

- 合集里只有作者**手工整理进去**的文章，不是全量历史 → 它是**补充源**，
  不是 `appmsg` 的完全替代（但对「某个学院号持续更新」这个场景已经很好用）。
- 一个文章页只能发现**它所属的那一个**合集；账号级「列出全部合集」的接口
  需要登录态（`action=getalbumlist` → `ret=-3 no session`），拿不到。
  想多覆盖就多给几个不同文章的种子链接。
- **当 `appmsg` 被限流时，脚本会自动改走合集源兜底**，不需要人工干预。
- 2026-07 之后这条路的权重变高了：后台拉列表被接口级收紧（10.13），合集成了
  **唯一还能拿到"某个号连续几期"的通道**。前提是那个号自己建了合集。

### 10.5 解法三：请求节奏加抖动

原来每一步都是固定间隔（`sleep(1.0)` / `sleep(1.5)`）。
固定间隔本身就是个特征：一个"人"不会每隔正好 1.000 秒点一次接口，脚本才会。
现在所有等待都走 `gentle_sleep()`，在 ±35% 范围内随机。

这不是对抗风控，而是**别让自己的行为特征过于醒目**，同时让服务端压力更平滑。

### 10.6 兜底顺序

一次运行会按这个顺序找内容，前面拿不到就往后走：

```
appmsg（有 cookies，全量历史）        ← 2026-07 起大概率第一页就 200013，见 10.13
   ↓ 被限流 / 没凭据 / 接口级收紧
合集源（零凭据，只含手工整理的文章）    ← 现役主力
   ↓ 那个号没建合集
搜狗微信索引（零凭据，按相关度，见 10.13.1）  ← 现役补充；须当场抓正文
   ↓ 也没有
公开种子链接（逐篇抓正文）
   ↓ 也没有
上次缓存（保留旧数据，不写空结果）
```

> 前两级是脚本自动走的；搜狗这一级目前是**独立命令**（`sogou`），
> 没有接进 `fetch_wechat.py` 的自动兜底——因为它的链接是分钟级签名的，
> 放进批处理会大批量失效，反而不如人工按需跑一条。

### 10.7 诊断

```bash
python fetch_wechat.py --list-accounts      # 看名单与 fakeid 缓存
python fetch_wechat.py --search-only        # 只搜 fakeid（搜索接口不受 appmsg 限流影响）
cat _work/wechat/wxmp-blocked.json          # 看谁被限过、什么时候、什么粒度

# 一步给出判定结论（账号级 / fakeid 级 / 正常 / 凭据过期），报告落到 _work/wechat/wxmp-diag-*.json
python tools/wxmp_spider.py diag --campus zju
python tools/wxmp_spider.py diag --name 浙江大学 --name 西安交通大学

# 完全不登录，只看"哪些端点还活着、缺什么"（回应"接口是不是被废弃了"这类传言）
python tools/wxmp_spider.py probe
python tools/wxmp_spider.py probe --format json      # 落档对比用
```

`probe` 打的是 7 个端点的零凭据矩阵，判读规则只有四句：
**404=真删了；200003 / -3=接口在、只缺凭据；200013=被限或能力收紧；
HTML 的「验证」=环境墙、「错误」=缺 hid/cid。** 详见 10.13 / 10.14。

`diag` 是 2026-10 调 pkucli 方案时顺带做的：它按 10.2 的判定规则跑一遍
（`warmup` → 1 次 `searchbiz` → 每个号拉一页），直接告诉你属于哪一种，
不用自己对比 `wxmp-blocked.json`。它**只读**，不改 `wxmp-blocked.json`——
那个状态文件属于主链路，诊断行为不该影响它的跳过逻辑。

`--search-only` 值得单独记一笔：**`searchbiz` 不受 `appmsg` 的限流影响**。
所以即使是账号级限流期间，也能把名单里所有号的 fakeid 先锁定下来，
等换好凭据（或解禁）后直接抓取，省掉一整轮搜索。

### 10.8 仍然解决不了的情况

诚实说明：如果**只有一个**公众平台账号、且它被账号级限流，
那么在没有第二份凭据的情况下，**`appmsg` 这条路就是走不通的**，只能靠合集源供数。
这是微信侧的账号级限制，脚本层面无法绕过——能做的只是
① 把损失降到最小（自动降级到合集源、不写空结果、保留旧数据）；
② 让你在准备好第二份凭据后**一条命令恢复**。

不过第 ① 条现在比过去有力得多：合集源能拿到**正文**（`chksm` 链接可抓），
并且**合集 ID 自动发现**，所以限流期可以纯靠 `--albums-only` 维持更新，
不需要等到换上第二份 cookies。代价是**覆盖面**：只有被作者整理进合集的文章才有。

### 10.9 关于「模拟用户操作」（桌面自动化）——评估结论

限流逼出来的另一个想法是：**干脆用桌面自动化模拟真人操作**（点微信客户端、
或用浏览器打开文章），这样服务端看到的就是"正常用户"。

结论是**不做**，理由已单独成文，见
[`公众号聚合方案评估.md` 第 10 节](公众号聚合方案评估.md#10-模拟用户操作桌面控件--浏览器自动化可行性评估)：

| 子路线 | 本机实测 | 结论 |
|---|---|---|
| 自动化微信客户端界面（wxauto 类） | 本机微信 **4.1.15.55**，UIAutomation 已完全失效 | ❌ 已死，且拿不到批量历史 |
| 给微信客户端注入调试通道（`--remote-debugging-port` / Frida） | 内嵌运行时 `RadiumWMPF` 25560/25799，**超出主流工具适配区间**；默认关闭调试通道 | ❌ 红线最硬，后果落在**个人微信号**上 |
| 独立浏览器自动化（Playwright） | 依赖全未安装（环境干净） | ⚠ 只能补单篇正文，**留作人工兜底** |

一句话：桌面自动化补的是"最后一公里"（正文），而这条链路缺的是"第一公里"（列表）；
而正文这条，**合集源已经零凭据拿到了**。

### 10.10 关于「让大模型看屏幕 + 点鼠标」（GUI 智能体）

再进一步的想法是：不写死脚本，让**多模态大模型看截图、自己决定点哪里**，
通过模拟鼠标键盘去微信里搜索、分享、取链接（业内称 Computer Use / GUI Agent）。

结论同样**不做**，见
[`公众号聚合方案评估.md` 第 11 节](公众号聚合方案评估.md#11-让大模型看屏幕--点鼠标视觉驱动的-gui-智能体可行性评估)。
要点：

- **技术成立**（单步元素定位准确率 94.2%），**但对本项目不成立**：
  完整的百步桌面任务成功率只有 **42.5%**，而"取一篇链接"要 20~30 步；
- **决定性反例**：2025-12 豆包手机助手自动操作微信，**账号被强制下线**，
  随后豆包下线了该功能——它同样是"视觉理解 + 模拟真人操作"、不 Hook 不注入；
- 规范 1.2.6 禁的是**"自动化操作"这个行为**，不是某种技术实现，VLM 不会因为"更像人"就豁免；
- 它还会**把整块屏幕（含聊天记录）送出本机**，这是脚本方案没有的风险。

**但这条思路留下一个真正有用的出口**：微信"复制链接"给的通常是**短链**，
而短链**本来就能抓**（`/s/XLsEsQOyo4qwtekckfDT2A` → 3.73 MB，正文完整）。
所以正确形态是**人工点两下复制链接 + 脚本监听剪贴板自动入库**
（本机 `Get-Clipboard` / `Set-Clipboard` 实测可用）——
省掉的是两下点击，保住的是账号。

### 10.11 关于「实体机器人坐在电脑前」

再想到极致就是：**机械臂当手、摄像头当眼睛**，让一台机器人真的"坐"在电脑前操作
（第 11 节思路的物理化终点）。

结论仍是**不做**，见
[`公众号聚合方案评估.md` 第 12 节](公众号聚合方案评估.md#12-有手有眼的实体机器人坐在电脑前可行性评估)。
这次的理由是一个**悖论**：

- 业界真有先例——**Selenium 作者 Jason Huggins 创办的 Tapster** 就是干这个的，
  它的存在理由是"**要自动化一个你根本没有接口的封闭 App**"（如 iOS 上的他人 App）；
- **而本项目有接口**（合集接口零凭据、一次拿 10~20 条带 `chksm` 的链接）；
- 更关键：**机器人"不累、动作完全一致"这个最大卖点，恰好是行为风控要找的特征**。
  反作弊领域的结论是——**检测的是"输入的熵值"，不是"输入的来源"**：
  真人点击间隔标准差 >15 ms，宏 <5 ms；"无论你使用的是什么硬件，都会被标记为异常"。
  机械臂的重复误差是**系统性**的，在这条维度上比软件脚本**更醒目**。
- 规范定性也没变：1.2.6 禁的是"**自动化操作**"这个行为，不是执行装置。

一句话：**与其让机器人坐在电脑前，不如让真人坐在电脑前点两下。**

### 10.12 那「注销公众号 → 用同一个微信号重新注册」呢？——不解决，而且更贵

被限流之后最容易想到的一招是：把现在这个号注销掉，用同一个微信号/身份证重新申请一个，
换个干净的 bizuin 继续抓。**结论：不解决，大概率还会立刻再撞一次。**

**为什么换号"看起来"有用。** `200013` 挂在**登录用的那个公众号**（bizuin）上，
不是挂在个人微信号（wxuin）上，所以确实存在"换号 = 换额度"这回事——
10.3 的凭据轮换池就是靠这个生效的。

**为什么重新注册反而不划算。**

| 环节 | 实际代价 |
|---|---|
| 新号同样是"新登录账号" | 本文件 3.1 已实测：**新登录/长期未用的账号几乎必然先被限流数小时至 1 天**。你换来的不是解禁，是**重新排队** |
| 注销冻结期 | 按粉丝量：≤1000 粉丝 7 天、1000–1 万 15 天、1 万–10 万 30 天、>10 万 60 天；期内可撤销 |
| 最终确认 | 冻结期结束后管理员还要在 7 天内确认，逾期**自动恢复账号**（等于白折腾） |
| 资源释放 | 注销完成后还要约 7 天系统释放身份信息，**期间原身份注册不了新号** |
| 名称 | 原名称有 15 天保护期，别人（以及你自己换主体）都用不了 |
| 清零项 | 粉丝、素材库、认证状态全部作废，且**不可逆** |
| 特殊情况 | **被永久封禁的号根本不能注销**，还一直占着你的身份证注册名额 |

也就是说：为了绕一次"几小时到一天"的限流，你至少要付**两周左右**的真空期
（这半个月里一个号都没有），再加一次性的粉丝/素材清零。**用两周换一天，是亏的。**

**唯一值得注销的情况**：这个号本来就不要了——历史违规、主体已注销、或确定不再运营，
注销的目的是**腾出身份证注册名额**，而不是解限流。反过来，为了解限流去注销，
是把一个"可恢复的额度问题"变成"不可逆的账号损失"。

**成本从低到高的正确顺序**（都在本文件里有对应实现）：

1. **接口测试号**（`mp.weixin.qq.com/debug/cgi-bin/sandbox?t=sandbox/login`）——扫码即得，
   不走注册审核，是 pkucli README 明确说"test account works"的那条路；
   但它的**图文编辑/超链接找号**权限本项目尚未实测，属于"两分钟就能试、试错成本为零"的先手棋。
2. **加第二份 cookies**（10.3 轮换池）——如果手上本来就有第二个能登录后台的号，
   这是唯一真正有效的解法，且脚本已支持按日期轮换、被限自动跳、fakeid 缓存按凭据分文件。
3. **合集源兜底**（10.4）——零凭据、不受账号级限流，限流期用它维持更新。
4. 降频与分时段（10.5）——抑制额度消耗速度，不解决已经触发的限流。

一句话：**限流是额度问题，不是身份问题；注销换身份不解决额度，只会把额度问题升级成账号问题。**

### 10.13 2026-07-30 之后：接口没被删，但「拉列表」这个能力被关了

网上流传的说法是「`cgi-bin/appmsg` 接口已被废弃 / 腾讯把接口关了」。
实测下来这句话**一半对一半错**，而且错的这一半会把人引向错误处置（等解禁、换号、甚至注销重注册）。

#### 先分清三个东西

| 名称 | 是什么 | 2026-10-24 实测 |
|---|---|---|
| `cgi-bin/appmsg?action=list_ex` | 老的「图文素材 / 历史消息」列表 | 接口**在**，业务码正常返回 |
| `cgi-bin/appmsgpublish?sub=list` | 「发表记录」列表（pkucli 用的那个） | 接口**在**，业务码正常返回 |
| 跨公众号拉列表这个**能力** | 上面两个接口共用的后端权限 | **2026-07-30/31 起收紧** |

**「接口被删」这个说法可以直接排除**：不带任何凭据请求，两个 CGI 都返回
`{"base_resp":{"ret":200003,"err_msg":"invalid session"}}`（HTTP 200，`application/json`）——
这是「没登录」，不是「没这个接口」。作为对照，随便编一个路径
`/cgi-bin/appmsg_not_exist_xyz` 返回的是 **HTTP 404、0 字节**。
删掉的路由是 404，被限的接口是 200003 / 200013。

#### 「操作太频繁」才是真相

那张流传的截图里，编辑器弹窗写的是「**操作太频繁，请稍后再试**」——这不是下线提示，
这正是 `200013`（freq control）在**前端**的样子。把「被限流」读成「接口谢幕」，
是这类文章最常见的误判，因为两者在界面上都表现为「点了没反应」。

#### 时间线

| 时间 | 事件 |
|---|---|
| 2026-05-31 | 出现「appmsg 已谢幕」的文章（就是截图那篇），此时多数人遇到的是高频调用的 200013 |
| 2026-07-30/31 | **至少三个互不相关的开源项目同时报告**：跨公众号文章列表在**第一页、零结果**就返回 200013 |
| 同期 | `wechat-article-exporter`（12k star）因上游接口关闭停止维护 |
| 2026-10-10 | 本项目实测复现：zju 前 3 个号全 200013（见 10.8） |
| 2026-10-24 | 复测确认接口存在、`searchbiz` 仍正常、单个公众号搜索与单篇正文均正常 |

**判据是「分裂现象」**：同一个 token 下，`searchbiz`（搜号）成功、单篇正文成功、
**只有拉列表失败**。账号级限流不会这样分裂；这是能力级的权限变化。
另一个判据是：**换账号、重扫码都不恢复**，且失败发生在第一页第一条（不是翻到第 N 页才被限）。

#### 所以现在能用的三条路

| 路线 | 凭据 | 覆盖 | 状态 |
|---|---|---|---|
| 公开合集 `mp/appmsgalbum` | 无 | 只覆盖**自己建了合集**的号，含全文 | 10.4，已实测 `ret=0` |
| **搜狗微信索引** | 无 | 按**关键词**命中，不能枚举某号全部（实测 20 条里属于目标号仅 3 / 1 条） | 10.13.1 已实现，但定位是"发现"不是"枚举"，见 10.15 |
| 单篇 `/s/{token}` 短链 | 无 | 只要拿到链接就能拿全文 | 已实测 3.5 MB、`js_content` 正常 |

#### 10.13.1 搜狗微信：新的零凭据发现源

`tools/wxmp_spider.py sogou` 已实现，链路是：

```
weixin.sogou.com/weixin?type=2&query=...
  → 结果页 <li id="sogou_vr_..._box_N">
  → /link?url=... 跳转页（需拼 `url += '...'` 片段，并删掉 @ 占位符）
  → mp.weixin.qq.com/s?src=11&timestamp=...&signature=... 签名短链
  → 正文 #js_content
```

```bash
PY="C:/Users/Kevin/.workbuddy/binaries/python/envs/default/Scripts/python.exe"
$PY tools/wxmp_spider.py sogou "浙江大学 招生" -n 10                    # 只列标题/号/日期
$PY tools/wxmp_spider.py sogou "浙江大学 招生" -n 4 --body --md-dir _work/wechat/sogou-md   # 连正文
```

2026-10-24 实测：搜索 4 条 → 4 条链接全部解析成功 → 4 篇正文全部落地
（13082 / 1160 / 566 / 3454 字符），产物在 `_work/wechat/sogou-md/`。
其中 566 字符那篇是**图片版招生简章**，正文本来就只有附件名，不是抓漏。

三个必须记住的限制：

1. **不能当全量历史**。搜狗只收录部分号，排序按相关度而非时间；要做「某号最近 10 篇」，
   先 `sogou "号名"` 看有没有，命中率不稳定。
2. **链接是分钟级时效**。`timestamp` + `signature` 签名，几分钟后失效，
   **必须当场抓正文**，不能只存链接留到明天用。
3. **反爬是「会话起点」判据，不是频率判据**。实测同一个 IP：先访问 `weixin.sogou.com/`
   拿到 `SUID` cookie 再点跳转链，4/4 成功；**不预热直接点 /link，4/4 全挂**在
   antispider。代码里的 `_sogou_warm()` 就是干这个的，别删。连续请求仍会触发验证码，
   一批 10~30 条就该停。

#### 10.13.2 一条容易踩的坑：查询串链接会被墙

| 链接形式 | 实测 |
|---|---|
| `/s/{token}` 短链 | HTTP 200，3.5 MB，有 `js_content` ✅ |
| `/s?__biz=...&mid=...&sn=...`（无 `chksm`） | HTTP 200 但只有 31 KB，**无 `js_content`**，是验证码/环境校验页 ❌ |

所以「存下来的链接」≠「能打开的链接」。本项目合集源产出的链接带 `chksm` 所以能用；
从别处抄来的、手工拼的长链大概率打不开——这也是为什么不建议自己拼 URL。

#### 对我们的结论

**别再指望后台拉列表了。** 它现在的定位应该降级为「有凭据时顺手试一下」，
主链路必须建立在 10.4 合集 + 10.13.1 搜狗 + 单篇短链这三条零凭据路上。
这也意味着 10.12 里「注销换号」的讨论在 2026-07 之后**更没有意义**——
问题从「额度」变成了「能力」，换身份解决不了能力。

### 10.14 Hook 监听 / 底层协议：有机会，但机会只在一处

被 10.13 堵住之后，思路自然会转向「绕过 HTTP 接口」：Hook 客户端、逆私有协议。
**结论先说**：这三条路里只有一条值得做，而且它的目标不是"破解协议"，是**取一个 cookie**。

#### 先看今天的端点矩阵（`tools/wxmp_spider.py probe`）

```
端点                   HTTP      ret  判定         含义
appmsg                200   200003  要凭据        接口在，只是没 session
appmsgpublish         200   200003  要凭据        接口在，只是没 session
searchbiz             200   200003  要凭据        接口在，只是没 session
profile_ext.getmsg    200       -3  要 session   要 wap_sid2 一类凭据（服务端数到 0 个 cookie）
profile_ext.home      200           环境校验墙     要微信内环境 / 客户端 cookie 才放行
homepage              200           存活          返回 36 KB HTML
appmsgalbum           200    10004  存活          活着但参数不全
```

三条最值得注意的信息：

1. **`mp/profile_ext?action=getmsg` 是活的**，回 `{"ret":-3,"errmsg":"no session","cookie_count":0}`。
2. **`cookie_count` 是服务端自己数出来的**——我塞一个假 `wap_sid2` 进去，它立刻变成 `cookie_count:1`，
   但仍然 `no session`。也就是说：**它只缺"一个真的 cookie"**，不缺别的。
3. `profile_ext?action=home` 直接给 2034 字节、`<title>验证</title>` 的墙。

这就是 Hook 的全部机会所在：**`wap_sid2` 只能从客户端里拿**。

#### 顺带排掉一个看起来很美的替代：公众号主页

`/mp/homepage?__biz=...` 无需任何凭据就能返回 36 KB 页面，里面内嵌
`var data={"appmsg_list":[{title, link, cover, sendtime, author, ...}]}`——看着像完美解。
实测覆盖率不行：

| 账号 | 结果 |
|---|---|
| 浙大先生（`MjM5NDgxNTQwNQ==`） | 6 条，最新 **2024-05**（是"栏目"不是时间线） |
| 号 A | 3 条，全是 **2020-07-03** |
| 号 B / 号 C | 42 KB、`<title>错误</title>`（**没配主页的号直接报错**） |

而且它给的 `link` 是 `?__biz=&mid=&sn=&scene=19`，**没有 chksm**，实测打开只有 17 KB 验证页、
无 `js_content`。**元数据能拿，正文拿不到，覆盖还只有少数号**——只能当补充，不能当主线。

#### mmtls 到底管什么（这段能省掉很多冤枉路）

| 通道 | 协议 | 能不能 MITM | 你要的东西在不在里面 |
|---|---|---|---|
| 手机/PC 微信 ↔ 微信接入层（收发消息、长连接） | **mmtls**（自研，TLS1.3 改 + 固定 PSK 双向认证） | 不能，除非 hook 或拿密钥 | 订阅号**推送**在这里 |
| 微信内置浏览器 → `mp.weixin.qq.com`（文章、主页、列表） | **标准 HTTPS** | **能**（装证书就行） | 文章**列表和正文**在这里 |

**关键推论**：想拿"文章列表"，根本不需要碰 mmtls。那层重武器是为"收推送"准备的。
所以"底层协议"这条路对当前需求属于**射程错位**——成本极高，打的是另一个靶子。

#### 三条路线，只有一条值得

| 路线 | 能拿到 | 成本 | 维护风险 | 值不值 |
|---|---|---|---|---|
| **A. 抓 `wap_sid2`**（安卓副号 + mitmproxy/HttpCanary，微信里点「查看历史消息」，抄 Cookie） | **全量历史列表**（唯一入口），正文另抓 | 一台常在线安卓机或模拟器 + 一次性人工登录；cookie 有 TTL，要定期续 | cookie 绑设备/UA，请求频率一高就 `验证` 墙；副号有封号风险 | ✅ **唯一值得** |
| B. PC 微信 hook（读本地 DB：WeChatFerry 一类） | 已关注号**推送过的**消息（标题+链接+摘要），历史浅 | 中；但 PC 微信 4.x 重写后老 hook 大面积失效 | 版本升级即挂，需持续跟版本 | ⚠️ 只在"只要最新几篇"时考虑 |
| C. 私有协议（padlocal / ipad 类商业协议端） | 与 B 相同（只能收推送） | **最高**：月费 + 协议端托管 | 生态在萎缩、封号率最高 | ❌ 不值得 |
| D. Hook mp 后台前端 JS（重放编辑器请求） | 什么都没有 | 低 | — | ❌ 无效：服务端拒的是 bizuin 的跨号权限，参数再真也 200013 |

#### 如果真要走 A，最小可行实验

1. **副号**（绝对别用主号）、一台安卓机或模拟器，装 mitmproxy 证书；
2. 在微信里打开目标公众号 → 点「查看历史消息」→ 抓 `mp/profile_ext?action=home` 或
   `action=getmsg` 那次请求的 **Cookie（`wap_sid2`）** 与参数（`uin` / `key` / `pass_ticket`）；
3. 用 `python tools/wxmp_spider.py probe` 确认基线，再带 cookie 打 `action=getmsg` 翻页；
4. **低频**（每号每分钟 1 次以内）、**cookie 只在本机**、**过期就重新人工登一次**。

> 合规提醒：Hook 个人微信 / 逆向客户端违反微信用户协议，可能导致**封号**，且 cookie 等同密码。
> 本项目的凭据文件已在 `.gitignore` 里，本轮又补了 `_work/wxmp-spider*/`（扫码会话目录）
> 和 `_work/wechat/sogou-md/`——别把任何 cookie 提进仓库。

#### 对我们这个项目的判断

**不做 Hook。** 理由是需求侧的：

- 站点要的是「近 90 天内、标题 + 日期 + 分类 + 跳转链接」，**不是全文归档**；
- 零凭据三路（合集 / 搜狗 / 单篇短链）已经能覆盖"某号最近几篇 + 正文"；
- Hook 换来的核心增量是"全量历史"，而这个增量对 90 天窗口的价值很低。

**什么时候才值得翻这张牌**：① 必须拿到"某号最近 10 篇"而合集和搜狗都覆盖不到；
② 愿意长期维护一台常在线设备。两个条件同时成立，再考虑 A。

一句话：**Hook 的目标不是 mmtls，是 `wap_sid2`；而 `wap_sid2` 只解决"全量历史"，
不解决"我们其实只需要最近几篇"。**

### 10.15 「某号全部新发布链接」：只有一条硬路径

先把话说准：**10.13 的三条零凭据路能"发现"文章，但不能"枚举某个号的全部新发布"。**
这条得自己更正，因为实测数据很难看。

#### 搜狗的真实覆盖率（2026-10-24 实测）

| 查询词 | 两页共 20 条结果里，真正属于该号的 |
|---|---|
| 浙江大学 | **3 条**（其余 17 条是第三方号在提"浙江大学"） |
| 西安交通大学 | **1 条** |

原因很简单：搜狗是**按关键词搜文章内容/标题**，不是按号列文章。所以它适合"我发现了一篇好文"，
不适合"我要这个号今天发的全部文章"。而且它连"按号看"的入口都关了：

- `type=1`（搜公众号）→ 页面只有"暂无"；
- `tsn=1`（一天内）→ 直接被重定向回首页，0 条。

#### 唯一能"枚举"的接口：`mp/profile_ext?action=getmsg`

2026-10-24 实测它的响应是：

```json
{"base_resp":{"ret":-3,"errmsg":"no session","cookie_count":0},"ret":-3,"errmsg":"no session","cookie_count":0}
```

塞一个假 `wap_sid2` 进去，`cookie_count` 立刻变 `1`，但仍然 `no session`。
**它不验签、不要 token、不要后台登录，只缺一个真的客户端 cookie。** 这就是全部门槛。

拿到之后，一条请求就能翻 10 条，`can_msg_continue=1` 继续翻，`offset` 递增——
这是公众号**全部已发布文章**，不只是最近几篇。

#### 用法（代码已就位，只差一次抓包）

```bash
PY="C:/Users/Kevin/.workbuddy/binaries/python/envs/default/Scripts/python.exe"

# 1) 手机微信 → 打开该号任意文章 → 右上「…」→「查看公众号」→「查看历史消息」
# 2) 手机接 mitmproxy / HttpCanary，抓那次 /mp/profile_ext?action=home 或 getmsg 的 Cookie
# 3) 整行存成文件（一行 `Cookie: ...` 就行）
#    注意这个文件已被 .gitignore 覆盖（wxmp-cookie-header*.txt / wxmp-wap-cookies.txt）

# 4) 拉列表（--name 会自动用 wxmp-fakeid.json 里的 fakeid 当 biz）
$PY tools/wxmp_spider.py history --name 浙江大学 -n 20
$PY tools/wxmp_spider.py history --name 浙江大学 --since 2026-10-01 -o _work/wechat/history-zju.json

# 想直接给 biz 也行（fakeid 与 __biz 同值）
$PY tools/wxmp_spider.py history --biz MjM5NDgxNTQwNQ== -n 10
```

输出每条含 `title / link / digest / author / datetime / idx / msgid`，
`link` 里带 `chksm`（所以正文可直接用 `scrape` 或 `sogou --body` 那条路抓，不会被验证墙挡）。

**"新"怎么判**：`history` 输出的顺序就是发布时间倒序，拿 `link` 和上一轮存下来的集合做差集即可。
建议落 `_work/wechat/history-<校区>.json`，每轮覆盖前先 diff。

#### 几个实测确认的细节

| 问题 | 实测结论 |
|---|---|
| 需要 `uin` / `key` / `pass_ticket` 吗？ | 服务端只报 `no session`+`cookie_count`，说明它查的是 cookie；参数可留空，但地址栏里有就带上更稳 |
| cookie 能活多久 | 官方未公开；实践上数天到数周，失效表现为 `ret=-3` 或 HTML「验证」页 |
| 频率 | 每号每分钟 ≤ 1 次翻页足够（一页 10 条）；一个号 90 天约 9~15 页，一次跑完即可 |
| 会不会封号 | 这是**读客户端同一个接口**，不是逆向。风险主要是"异常频率 + 非微信 UA"，所以限速 + 用微信 UA |
| 失效报错长什么样 | `getmsg 失败 ret=-3（no session —— wap_sid2 不对或已过期…）`，脚本已内置这句提示 |

#### 为什么不用 10.14 的 Hook/协议

`wap_sid2` 就在 `mp.weixin.qq.com` 的**标准 HTTPS** 请求头里，一次抓包即可，
不需要 hook 客户端、不需要碰 mmtls。换句话说：**要"全部链接"，成本最低的不是 Hook，
是让手机微信自己发出那个请求，你在旁边记下它的 cookie。**

#### 如果你连一次抓包都不想做

那就只能接受"抽样"：合集（有就全）+ 搜狗（覆盖 15% 量级）+ 正文内链扩展（从已有文章的
"往期推荐"里再抽），三者合起来能覆盖一部分，但**永远不保证"这个号今天发的都拿到了"**。
这种方案的定位是"看得到热点"，不是"不漏一篇"。要"不漏"，只有上面那条路。

### 10.16 用 PC 微信还是手机微信抓 `wap_sid2`：能不能、怎么做、什么风险

**结论：PC 微信可以，而且比手机省事——但成败取决于三个"能不能"，必须先自测。**

#### 先看你机器的实际情况（2026-10-24 实测）

| 项 | 结果 |
|---|---|
| 微信版本 | **4.1.15.56**（`C:/Program Files\Tencent\Weixin\Weixin.exe`） |
| 内置浏览器 | `WeChatAppEx.exe` 独立进程（多开），4.x 起公众号文章/网页由它渲染 |
| 抓包工具 | 未安装（Fiddler / Charles / Reqable 都没有） |
| 系统代理 | `ProxyEnable=0`，但登记了 `127.0.0.1:7897`（有个本地代理软件） |

两点解读：

- `WeChatAppEx` 的存在是**好消息**：它是标准 Chromium 分支（XWeb），走**系统代理**，
  4.x 上抓 PC 微信网页流量的通行做法就是 MITM 这个进程。
- `127.0.0.1:7897` 是**坏消息**：抓包时如果它还在抢流量，会形成"微信 → Fiddler → Clash → 网"的双层代理，
  常见结果是 Fiddler 里只看到一堆 CONNECT 隧道、解不开。**先关掉它，或让 Fiddler 的 upstream 指向它。**

#### PC 端能不能成的三个自测（按顺序，10 分钟内出结论）

1. **证书能不能被接受**：Fiddler 开 HTTPS 解密、根证书装进「受信任的根证书颁发机构」，
   然后 PC 微信随便打开一篇公众号文章。Fiddler 里出现明文 `mp.weixin.qq.com` 就算过；
   只有 `Tunnel to ...:443` 或证书报错，就是被 pinning 了 → **直接改走手机**。
2. **请求里有没有 `wap_sid2`**：在明文请求的 `Cookie` 头里找 `wap_sid2=`。
   有 → PC 端完全够用；没有（只有 `rewardsn` / `wxtokenkey` 这类游客 cookie）→ PC 端拿不到，改手机。
3. **能不能触发目标请求**：PC 微信里点公众号 → 「查看历史消息」，Fiddler 过滤
   `mp.weixin.qq.com` + `profile_ext`，出现 `action=home` 或 `action=getmsg` 就对了。

> 判断标准只看第 2 条：**`wap_sid2` 才是能不能拉全量列表的唯一凭据**。
> 前两条都过、第 2 条没有，说明 PC 端只是个"游客浏览器"，白折腾。

#### PC 端步骤（Windows，最省事的顺序）

```text
1. 装 Reqable（国内网络更省事）或 Fiddler Classic
2. 开启 HTTPS 解密 → 导出根证书 → 安装到「受信任的根证书颁发机构」
3. 确认系统代理指向抓包工具（Fiddler 默认自动设置），并临时关掉 127.0.0.1:7897
4. PC 微信 → 打开目标公众号任一文章 → 「查看历史消息」→ 在历史列表里往下滚两屏
5. 抓包工具里过滤 mp.weixin.qq.com，找 action=home / action=getmsg 的那条
6. 右键该请求 → Copy → **Copy as cURL**，整段存成 curl.txt，然后：
   python tools/wxmp_spider.py cookie-from-curl -f curl.txt
   （自动抽 Cookie + uin/key/pass_ticket，**先检查有没有 wap_sid2**，再打印下一步命令）
7. 只用 Copy Request Headers 也行：把 `Cookie:` 那一行存成
   _work/wechat/wxmp-wap-cookies.txt（该文件已被 .gitignore 覆盖）
8. 立刻验证：python tools/wxmp_spider.py history --name 浙江大学 -n 3
9. 收尾：关抓包、恢复系统代理、**删除刚装的根证书**
```

第 6 步的 `cookie-from-curl` 是专门为这条路写的：它会把 `%3D%3D` 这类 URL 编码还原、
对长值做掩码（不把整串凭据打到终端），并且**只要 Cookie 里没有 `wap_sid2` 就直接警告**——
这正是"PC 端白折腾"最常见的失败形态。

#### 手机端步骤（PC 自测失败时）

Android（推荐，最稳）：

```text
1. 装 Reqable / HttpCanary；安装它的用户证书（Android 7+ 装在"用户证书"即可，
   微信对 mp.weixin.qq.com 不做 pinning，不需要 root）
2. 手机 Wi-Fi 代理指向电脑的 8888（或用手机端 App 直接本机抓）
3. 微信里打开目标号文章 → 右上「…」→「查看公众号」→「查看历史消息」
4. 抓 mp/profile_ext?action=home 的 Cookie（含 wap_sid2）
5. 传到电脑存成 _work/wechat/wxmp-wap-cookies.txt，同步第 8、9 步
```

iOS：用 Stream / QuantumultX 抓，注意要在「通用 → 关于本机 → 证书信任设置」里**手动开启**
对该根证书的完全信任，否则微信里全是明文失败。

#### 风险清单（按"会不会出事"排序）

| 风险 | 具体表现 | 怎么降到最低 |
|---|---|---|
| **账号被限/被封** | 微信用户协议禁止"使用非官方客户端或自动化工具"批量获取内容；高频拉列表会被判异常，轻则功能限制，重则封号 | **用副号，不要主号**；每号每分钟 ≤ 1 次翻页；一批 20~30 个号分两天跑完；不要 7×24 挂着 |
| **cookie 泄露 = 账号被接管** | `wap_sid2` + `uin` 组合足以冒充会话，贴到群里/提交进仓库等于把号交出去 | 只存本机；`_work/wechat/wxmp-wap-cookies*.txt` 已在 `.gitignore`；不要发截图（截图里常带 Cookie 头） |
| **证书带来的本机风险** | 装了根证书后，任何持有该私钥的程序都能解密本机 HTTPS；Android 用户证书对全机生效 | **用完立刻删证书**；Android 可在"加密与凭据 → 用户凭据"里移除；Windows 在 certmgr.msc 删 |
| **代理配置残留** | 抓完忘关系统代理 → 电脑整机断网/变慢 | 抓完先关抓包工具，再确认 `ProxyEnable=0` |
| **验证墙 / IP 被封** | 频率一高，`getmsg` 直接返回 HTML「验证」页，之后连文章页都难打开 | 撞到就停 30 分钟；换网络出口（如手机热点）再试 |
| **版权与合规** | 批量抓全文再分发，属于转载 | 本项目只存**标题 + 日期 + 链接**，正文按需单篇抓，不做全文镜像 |

#### 一个"风险窗口最小"的用法

不要长期持有 cookie。正确姿势是**一次性使用**：

1. 抓一次 → 跑完这一轮全量（每个号 90 天约 9~15 页）；
2. 落 `_work/wechat/history-<校区>.json`；
3. **删掉 cookie 文件**，下次要更新再抓一次（几分钟的事）。

这样账号在"被抓包"这件事上的暴露时间只有几分钟，而不是整月挂着。

#### 如果连这一次都不想抓

那就回到 10.15 结尾的结论：只能"抽样"（合集 + 搜狗 + 内链扩展），
能看到热点，但不保证某号新发的每一篇都拿到。**"不漏"和"零操作"这两件事，目前无法同时成立。**

#### 10.16.1 手机抓包需要什么：最小清单

**只需要三样，不需要电脑、不需要 root、不需要改路由器。**

| # | 需要 | 具体选型 | 说明 |
|---|---|---|---|
| 1 | 一台手机 | **Android 8~13 最省事**；iOS 也能做 | Android 13 以后对用户证书更严，但微信 webview 一般仍认 |
| 2 | 抓包 App | Android：**Reqable**（免费版够用）；iOS：**Stream**（免费） | **不要用 HttpCanary**，2021 就停更了，新系统上兼容性差 |
| 3 | 证书 | App 内置 CA，装一次 + 信任 | 这是唯一"有技术含量"的一步，见下 |

可选但建议：

- **副号**（不要用主号登录微信）；
- 手机能上网就行，Wi-Fi 或 4G 都可以（App 是本地 VPN 模式，不依赖电脑在同一局域网）。

> 为什么推荐 VPN 模式的 App：微信在某些版本会**绕过系统 Wi-Fi 代理**，导致"代理式抓包"里一条请求都看不到；
> VPN 模式在系统层截流量，App 用不用代理都能抓到。

#### 10.16.2 六步操作（Android + Reqable）

```text
1. 装 Reqable → 首次启动按引导装 CA 证书：
   设置 → HTTPS 抓包 → 安装证书 → 选「VPN 和应用」（Android）
2. 开抓包（右上角 ▶），确认状态是"运行中"
3. 微信 → 打开目标号任意一篇文章 → 右上「…」→「查看公众号」→「查看历史消息」
4. 在历史列表里往下滚 1~2 屏（这会触发翻页请求，能多拿到 uin/key 一类参数）
5. 回 Reqable → 搜索框输入 profile_ext → 点开命中项
6. 长按请求 → 「复制为 cURL」（或复制整段请求头）
   → 用「文件传输助手」发到电脑，存成 curl.txt
```

iOS + Stream 的区别只有两处：装完证书要去**「设置 → 通用 → 关于本机 → 证书信任设置」**
把该根证书的开关**手动打开**（不打开的话微信里全是明文失败）；其余步骤一致。

#### 10.16.3 抓到手之后确认三个字段

| 字段 | 在哪 | 期望值 |
|---|---|---|
| `action=getmsg` 或 `action=home` | 请求 URL | 二者之一；`home` 是页面、`getmsg` 是列表数据 |
| `wap_sid2=` | 请求头 Cookie | **必须有**，没有就白抓 |
| `uin=` / `key=` / `pass_ticket=` | 请求 URL | 有就一起带上，没有也能试 |

然后一条命令收口（会自动检查 `wap_sid2`）：

```bash
python tools/wxmp_spider.py cookie-from-curl -f curl.txt
python tools/wxmp_spider.py history --name 浙江大学 -n 3
```

#### 10.16.4 抓不到怎么办（按出现频率排序）

| 现象 | 原因 | 处理 |
|---|---|---|
| 微信里文章打不开 / 一直白屏 | 证书没信任 | Android 重装到「VPN 和应用」；iOS 去"证书信任设置"开开关 |
| 抓包列表里全是 `Tunnel to ...:443`、没有明文 | HTTPS 解密没开 / 证书未生效 | 开 App 的 HTTPS 解密；重启微信（杀掉进程）再试 |
| 一条 `mp.weixin.qq.com` 都没有 | 走的是系统代理但微信绕过了 | 换成 VPN 模式的抓包 App |
| 有 `profile_ext` 但 Cookie 里没 `wap_sid2` | 抓到的是游客请求（没登录态） | 确认微信是登录状态；重新点一次「查看历史消息」再抓 |
| 抓到 `getmsg` 但返回 `-3` | cookie 不完整（可能只抓到一半头） | 复制**整段**请求头，或改用 Copy as cURL |
| 拿到 cookie 后仍 `ret=-3` | 请求没带微信 UA | `history` 已内置微信 UA，别自己用 curl 裸跑 |
| Android 14 上抓不到微信 | 系统对用户证书更严 | 换旧一点的安卓机，或 root 后装系统证书（不推荐） |
| 抓几次就跳「验证」页 | 频率高了 | 停 30 分钟；换热点出口 |

> 一句话：**手机抓包的门槛不在设备，在"证书有没有被信任 + 抓的是不是 VPN 模式"这两点。**
> 这两点过了，剩下就是复制一段文本。

### 10.18 对标「清华知道」：它的"不漏 + 长期"是怎么成立的

10.17 解决的是"能不能抓到一次"。真正的问题是**能不能长期、且一篇不漏**。
对标 `https://pkuknow.cn/thu` 的拆解单独成篇：
**`docs/pkuknow拆解-不漏篇与长期自动化.md`**。

三条可验证的结论：

| 观察 | 数字 | 含义 |
|---|---|---|
| 来源与规模 | 195 源（微信 145 + 官网 50）、3175 条、约 120 天 | 是完整管道，不是临时脚本 |
| 同步节奏 | `last_sync` 每 **62 秒**推进一次 | 分钟级，靠 10 条缓冲吸收漏轮 |
| 采集形态 | 238 条微信样本 `idx` 覆盖 1–8、100% 带 `chksm` | 拿的是**群发级列表**（getmsg 那一类），不是搜狗/合集 |
| 正文加工 | 9/10 全文、正文中位 4458 字、图片本地化 webp、`ai_summary` 10/10 | 全文 + AI 结构化才是它的产品力 |

**它比我们多的东西分两类**：

1. **通道**（抄不了）：145 号 × 分钟级 ≈ 每天 4 万+ 次列表请求。我们单个 `wap_sid2`
   在 3 个号上就撞过 `200013`；作者也直说"抓取微信的数据需要消耗挺多资金"。
2. **工程**（能抄）：第一页增量轮询 + 去重账本 + `pending/failed/metadata_only` 状态 +
   来源健康 `ok/no_recent` + 正文图片本地化 + AI 字段抽取。

**我们已落地的第一块**：`history --watch`（每轮只拉第一页、去重、只输出新增），
按 2 小时 × 40 号 = 480 次/天（20 次/小时）跑，靠 10 条缓冲不会漏。

**结论**：免费条件下"不漏"能成立（低频轮询），"长期"不能（凭据会过期）；
两者同时成立只有付费通道或自建号池。所以别照着 5 分钟 × 全量抄——那是拿钱换来的频率。

### 10.19 「群发级列表」从哪来：正常途径 vs 对方通道

10.18 说的是"它做到了不漏 + 长期"，这一节回答**那份数据本身从哪流出来的**。
完整版见 **`docs/群发级列表-获取途径与通道原理.md`**。

**先定义**：一次群发 = 一个 `mid` + `idx 1..8` + 批次 `sent_time` + `chksm`。
实测清华站 291 条样本：**38% 的批次是多图文，只取首篇会丢 40% 的文章**。

**正常使用微信的四条途径**：

| 层 | 途径 | 群发级? |
|---|---|---|
| 界面 | 公众号「历史消息」页 / 会话「余下 N 篇」/ 转发链接 | ✅（人工操作） |
| 客户端 | **PC 微信本地消息库**（关注后落 `appmsg`） | ✅（仅首篇，余篇需补一次请求） |
| 官方接口 | 后台超链接搜索 / 第三方平台授权 / 公众平台 | ❌ 文章级，且拿不到别人的号 |
| 协议层 | iPad 协议 / 安卓 hook | ✅ 秒级 |

**关键数字**：个人微信号关注公众号上限约 **1000** ⇒ **一个号就装得下全部 145 个清华号**。
所以"号池"的门槛不是买 145 个号，是**让 1~几个号活着**。

**对方通道的判据**（三条硬指纹，都不是猜的）：

1. `chksm` 291/291 全覆盖 + `idx 1..8` 齐全 ⇒ 列表接口（`getmsg` 家族）的形状
2. 同 `mid` 内 `published_at` **连秒都相同** ⇒ 时间取批次 `sent_time`，不是逐篇 `ct`
3. **没有任何阅读量/点赞字段** ⇒ 无会话态；我实测无会话裸开文章页 200 且
   `appmsgBarData.read_num` 静态为空，两者完全自洽

配合 `last_sync` 62 秒节拍 + 145 号规模 ⇒ 最可能是 **多号池 + `mp/profile_ext` 分钟级轮询**。
"消耗挺多资金"不是买数据贵，是**让几十个号活着贵**。

**对我们的含义**：机制能抄（`--watch` 已做），频率抄不了（单凭据 30 分钟~3.5 小时就过期）。
唯一低成本同时满足"长期 + 不漏"的是 PC 微信本地库路线，但它属于修改客户端、违反用户协议、
有真实封号风险 —— 这是产品决策，不是技术决策。

### 10.20 方案 A 的落地形态：号池 + 配额 + 冷却

10.19 判定"对方是多号池轮询"，这一节把它做成我们能跑的东西。
完整设计见 **`docs/方案A-多号池分钟级轮询.md`**。

**核心算术**（每号按 120 次/小时保守估）：

| 轮询周期 | 目标号数 | 请求/小时 | 需要活号 |
|---|---|---|---|
| 2 小时 | 40 | 20 | **1** |
| 10 分钟 | 40 | 240 | **2** |
| 62 秒 | 145 | 8420 | **约 70** |

→ 80 秒级不是"145 个号盯 145 个号"，是**几十个号轮换**。这就是对标站点的成本结构。

**最反直觉的一条结论**：`getmsg` 第一页返回 10 条**批次**，而高校号平均每天只发 1~2 次，
所以**一天查一次也不会漏**（10 条缓冲 ≈ 5 天）。

> **"不漏"几乎免费，"实时"才花钱。** 你要买的不是完整，是时效。

**已落地**（`tools/wxmp_pool.py`，25 项测试）：

  **五个字段必须同源**，混搭必 `-3`（这个坑很容易被误判成"号废了"）
- 选号 `argmin(used/quota, last_used)`；配额按整点对齐跨窗清零

- **一次任务固定用一个号跑完**，只在失败时换（换号后从 offset 0 重来，靠链接去重保证不重复）
- `state.json` 原子替换，任务计划程序并发跑也不会读到半截

### 10.21 号池里"被封"到底封的是什么

10.20 把号池做出来了，这一节说清代价。完整版见 **`docs/号池账号风险.md`**。

**先拆词**：日常说的"号被封了"混了三层，恢复代价差三个数量级——

| 层 | 丢了要多久补 | 会不会牵连别的号 |
|---|---|---|
| 会话（`wap_sid2`+参数） | 重抓，几分钟 | 不会 |
| 账号（一个微信号） | 补号/申诉，几天~永久 | **会** |
| 主体（一张身份证下所有号） | 不可恢复 | 全部 |

我们日常遇到的 `200013`、`-3`、验证墙**全部只损第一层**。把 `200013` 当"号废了"
是这类项目最常见的误判——它会让你不断丢还能用的凭据，还掩盖真正的原因。

**六级梯度**：`200013` 限流 → `-3` 失效 → 验证墙（HTML/滑块）→ **账号异常（微信弹窗）**
→ 限制登录 → 永久封禁。前三级是"被当爬虫"，后三级是"被当坏人"，**两套系统、触发条件不同**。
只读公开文章 + 低频 + 单号，落在前三级，是可控的。

**最反直觉的一条**：最大风险源不是频率，是**环境跳变**。`wap_sid2` 在手机微信里
生成，却被搬到 PC/服务器上用 `requests` 打——网络、客户端、行为序列三处都不一致。
这解释了"为什么有时第一次请求就撞墙"。所以风险主要跟"你换了环境去用这个会话"相关，
而不是"你打了多少次"。

**号池恰恰是这条的反面**：它把 N 份会话从各自真实环境抽出来，集中到一个新环境打。
**能叠加多少配额，就同质化到什么程度。**

**连坐有官方依据**：微信公告明文"封禁与该主体**所有相关账号**""同步**追溯关联账号**"。
四通道按强度：实名主体 > 手机/银行卡 > 设备 > IP。前三条靠"别用主号、别同机切号"躲开，
**IP 这条躲不掉**（只有一条宽带）。所以硬规则是：**池号与主号绝不共用设备/出口**。

**建议上限 5 个号**。≤5 还在"像个人"的区间；>5 进入"多会话 + 同出口 + 同节奏 + 同目标集"
的集群特征，跟你多慢无关。

**已落地熔断**（`wxmp_pool.py`，35 项测试）：撞墙 → 单号 4 小时 + 记 trip；
30 分钟内 3 次 → **整池停 1 小时**，`acquire` 直接拒绝、`list_history` 不换号直接抛。
理由：撞墙说明出口被认出来了，换号等于把好号一个个送进同一个被标记的通道。

```bash
python tools/wxmp_spider.py pool --status   # 含熔断器状态
python tools/wxmp_spider.py pool --resume   # 换过出口/降过频再开闸
```
