# 用 wxmp 接入微信公众号

面向要给「XX 知道」补全**官方微信公众号**内容的人。目标是：不靠官网转载，直接把某个公众号
最近的推文成批抓回来，合并进 `data/<校区>.json`，在页面上以「微信公众号」来源分组展示。

> **本文讲的是「公众号链路」（不稳定）**，它和「官网链路」（稳定）在磁盘上完全分开：
> 本文提到的所有文件（cookies / token / 名单 / fakeid / 中间产物）都在 **`_work/wechat/`** 里，
> 而 `refresh.py` / `fetch_campus.py` 的产物在 `_work/` 根下。两条链路只往同一份
> `data/<校区>.json` 里追加，所以页面合一，但任何一条断了都不影响另一条。
> 完整目录对照见 [目录结构.md](目录结构.md)。
>
> 老版本把这些文件放在 `_work/` 根下，首次运行 `fetch_wechat.py` 会**自动迁移**到
> `_work/wechat/`，读取时也会回退旧位置，升级不会丢东西。

---

## 0. 它现在是流水线的第三步

公众号抓取已经接进无人值守入口，不再是单独的脚本：

```bash
python cloud_update.py --with-wechat          # 清华 → 三校 → 公众号 → 重建页面
python cloud_update.py --wechat-only          # 只跑公众号这一步
python cloud_update.py                        # 默认**不跑**公众号（原因见第 9 节）
```

`cloud_update.py` 会把它的上千行进度收进 `_work/run.log`，终端只留一行结论，
并把三种「看起来成功但实际没拿到内容」的情况翻译成人话，例如：

```
⚠ 公众号：被微信**账号级限流**(ret=200013 freq control)，本轮没有拉到任何文章列表，
  已保留旧数据。……解禁后重跑即可（fakeid 已缓存，不会再走搜索）
```

### 0.1 一个重要改动：名单里的 `max` 会被外部文件覆盖

早期版本里，`_work/wechat/wxmp-accounts-<校区>.json` 写成 **`{"浙江大学": {"max": 15}}`**
（「名称 → 参数」写法）时，如果这个名字在内置 `WECHAT_CONFIG` 里也有，
外部给的 `max` 会被**静默丢掉**，退回 `--count` 的默认值。

现在外部名单是**更新**语义：同名条目的 `max` / `fakeid` 会用外部的值覆盖。
所以下面三种写法效果一致，随便用哪种。

## 1. 为什么需要单独一个脚本

微信公众号**没有公开的文章列表接口**，所以原来 `fetch_campus.py` 只能被动发现内容：
只有当某篇公众号文章出现在学院官网页面里时，才会被顺手抓走。

`wxmp` 走的是另一条路——**微信公众平台后台接口**（`searchbiz` 搜号 + `appmsg` 拉历史文章列表）。
它需要登录后的 cookies，因此单独放在 `fetch_wechat.py`，不与纯公开抓取混在一起。

```
                 ┌── 公开链接（无凭据）──→ fetch_wechat.py --public-seed ─┐
官方公众号文章 ──┤                                                      ├─→ data/<校区>.json ─→ index.html
                 └── 后台接口（需 cookies）→ fetch_wechat.py（wxmp）─────┘
```

两条路产出的 item 结构**完全一致**（`dt.sg = "wechat"`），页面上都归入「微信公众号」来源分组。

### 1.1 API 模式下也会补抓种子链接

`fetch_campus.py` 会读 `_work/wechat/wechat-<校区>.txt` 逐篇抓正文；`fetch_wechat.py` 在 API 模式下
**也会把这份种子清单里尚未入库的链接补抓一遍**（`--no-seed-fallback` 可关）。
这样「名单外的号」「本轮被限流的号」的内容不会因为走了 API 模式就漏掉。

## 2. 安装

```bash
pip install wxmp          # 需要 Python >= 3.10
```

> `refresh.py` / `fetch_campus.py` 仍只用标准库，**只有本脚本**需要 wxmp。
> 注意 wxmp 会连带装 pydantic / pandas / requests / fake-useragent / loguru / tqdm，
> 体积不小。它的**公开种子模式不需要 wxmp**（只用到 `urllib`），所以没装也能跑。

## 3. 拿到 cookies（API 模式的关键）

微信公众号后台接口必须登录后才能访问，步骤：

1. 用浏览器登录 <https://mp.weixin.qq.com/>（自己注册一个订阅号即可，无需粉丝）；
2. 按 `F12` → **Network** → 刷新页面 → 点任意一个 `cgi-bin/...` 请求；
3. 在 **Request Headers** 里找到 **`Cookie:`**，**右键 → Copy value**（整行，很长）；
4. 存成下面任一文件（推荐第①种，整行粘贴即可，脚本自动解析）：

   | 文件 | 说明 |
   |---|---|
   | `_work/wechat/wxmp-cookie-header.txt` | **推荐**：把整行 `Cookie: ...` 原文粘进去（带不带 `Cookie:` 前缀都行） |
   | `_work/wechat/wxmp-cookie-header-<校区>.txt` | 分校区版本，优先于全局 |
   | `_work/wechat/wxmp-cookies.json` | 老格式：JSON `{"wxuin": "...", "slave_sid": "...", ...}` |

   关键字段：`wxuin`、`slave_sid`、`slave_user`、`slave_bizuin`、`data_ticket`、`bizuin`。
   另外页面 URL 里的 `token=xxxx`（一串数字）如果自动获取失败，可存到
   `_work/wechat/wxmp-token.txt` 作为手动 token。

5. 验证：

   ```bash
   python fetch_wechat.py --dry-run
   ```

   输出 `dry-run：cookies 有效，token = xxxxx` 即说明配置正确。

> cookies 有时效（通常几天）。过期后重新登录复制一份覆盖即可。
> 本脚本**不会**上传或外传 cookies，只在本机请求微信。

### 3.1 重要：`appmsg` 列表接口有账号级限流

微信对**「拉某个号的历史文章列表」**这个接口（`cgi-bin/appmsg`）有**账号级频率限制**：

- 触发后返回 `ret=200013`（`freq control`），**与参数、频率无关**，是账号维度的限流；
- **新登录 / 长期未使用**的公众平台账号，几乎必然先被限流一段时间，通常需**等待数小时至 1 天**解禁；
- 期间 **`searchbiz`（搜索公众号）完全正常**，只有拉列表被拒；
- 所以正确姿势是：**先用完整名单把 fakeid 全部锁定缓存**（这一步不受限流影响），
  等限流解禁后直接跑抓取即可，无需再搜索。

脚本已内置识别：遇到 200013 会打印明确提示、退避重试几次，仍失败则跳过该号、
**不写坏数据**。等几小时或次日重跑 `python fetch_wechat.py` 即可。

> 补充：`cgi-bin/appmsgpublish`（另一个"发布记录"接口）在同样条件下返回 `200009`，
> 也不是可用的替代路径。限流只能等。

## 4. 运行

```bash
python fetch_wechat.py                       # 三校全抓，写入 data/ 并重建页面
python fetch_wechat.py --campus zju          # 只抓浙大（zju / sjtu / xjtu）
python fetch_wechat.py --count 10            # 每个号最多取 10 篇（默认 15）
python fetch_wechat.py --pages 2             # 每个号最多翻 2 页（每页 5 篇）
python fetch_wechat.py --no-content          # 不抓正文，只用列表摘要（快、稳）
python fetch_wechat.py --no-seed-fallback    # API 模式下不补抓种子链接
python fetch_wechat.py --no-import           # 只抓取，结果落在 _work/wechat/wechat-items-<校区>.json
python fetch_wechat.py --import-only         # 不联网，用上次结果导入并重建页面
python fetch_wechat.py --cookies my.json     # 指定 cookies 文件

# 没有 cookies 时的降级路径：用公开文章链接当种子逐篇抓正文
python fetch_wechat.py --public-seed --public-max 80
```

**没有 cookies 时**脚本不会报错，而是自动降级为「公开种子」模式：读取
`_work/wechat/wechat-<校区>.txt`（以及 `data/` 里已有的 wechat 链接）、逐篇抓公开正文，
走**完全相同**的入库 / 展示链路。补齐 cookies 后，API 模式会自动接管并按号成批拉取。

## 5. 配置要抓哪些公众号

### 5.1 为什么可以放心用「完整名称」

微信公众平台的**昵称是全平台唯一的**——同一个昵称只能被一个号注册（改名后旧名也不会立刻释放）。
所以我们**按完整昵称精确匹配**就能唯一命中目标号，然后锁定它的 `fakeid`。
`fakeid` 一旦确定，拉文章列表就与昵称无关了，因此**名称里不含「浙大 / 交大」等关键词的号**
（如「竺院团学汇」「浙里等宁」「ZJUPES」）也能被稳定收录。

匹配规则（脚本按此顺序判定）：

1. 名单里给出的完整昵称 → 去空白 / 全角转半角 / 统一大小写后**精确相等** → 收录；
2. 命中后把 `fakeid` 缓存到 `_work/wechat/wxmp-fakeid.json`，之后**不再依赖搜索**（号改名、搜索被限流都不怕）；
3. `filter` 正则**只作兜底**：万一没精确命中（搜到擦边号），才用它判断昵称是否属于本校，避免误收同名社会号。

> 注意：`searchbiz` 是**模糊搜索**，搜「浙江大学」会返回「浙江大学校友总会」「浙江大学本科生院」等一堆，
> 所以脚本不是"取第一个"，而是**在结果里挑规范名完全相等的那个**。这也是为什么给**完整昵称**最稳。

### 5.2 推荐：把完整名单写进外部文件

不必改脚本，把名单放这里即可（会自动与内置配置合并）：

| 文件 | 作用 |
|---|---|
| `_work/wechat/wxmp-accounts.json` | 全局，所有校区共用 |
| `_work/wechat/wxmp-accounts-<校区>.json` | 分校区（如 `wxmp-accounts-zju.json`），优先合并 |

支持三种写法，任选其一：

```json
// ① 纯名称数组（最省事）
["浙江大学", "浙江大学本科招生", "竺院团学汇", "浙里等宁", "ZJUPES"]

// ② 带参数
{ "accounts": [ {"name": "浙江大学", "max": 15}, {"name": "竺院团学汇", "max": 10} ] }

// ③ 名称 → 参数（可选 fakeid，填了就跳过搜索）
{ "浙江大学": {"max": 15}, "竺院团学汇": {"max": 10, "fakeid": "MzA3Mjk2NzE..."} }
```

### 5.3 或者：直接改脚本内置清单

编辑 `fetch_wechat.py` 顶部的 `WECHAT_CONFIG`。**加一个号 = 加一个 dict**：

```python
WECHAT_CONFIG = {
    "zju": {
        "campus_name": "浙大知道",
        "filter": r"浙江大学|浙大|ZJU",          # 仅兜底
        "accounts": [
            {"name": "浙江大学", "max": 15},
            {"name": "竺院团学汇", "max": 10},     # 名称不含关键词也 OK
            {"name": "浙里等宁", "max": 8},
        ],
    },
    # "xxx": {"campus_name": "XX知道", "filter": r"XX大学|XX", "accounts": [...]},
}
```

新增一个**校区**只要：① 在 `WECHAT_CONFIG` 加一个键（键名 = `data/<key>.json` 的文件名）；
② 保证 `data/<key>.json` 存在。页面校区切换栏会自动认这个新数据文件。

### 5.4 名单外的公开种子号

即使某个号不在名单里，只要它的文章链接出现在 `_work/wechat/wechat-<校区>.txt` 里，
且**标题**含本校关键词，在「公开种子」模式下也会被收录（名单只影响 API 模式的按号抓取）。

## 6. 合并规则与数据安全

- **按文章链接去重**：`i` 字段就是文章 URL，同名条目覆盖、新条目追加，历史条目保留；
- **90 天保留期**：发布超过 90 天的条目会在写入和生成页面时自动清除（时间未知的不清）；
- **写入保护**：复用 `refresh.py` 的原子写入 + `.bak` 备份机制；
- **来源注册表**：每个公众号在 `source_registry` 里登记一条（`kind = "wechat-wxmp"`），
  页面「信息来源」抽屉会显示它的条数与状态徽标（最近更新 / 无新内容 / 采集失败 / 待接入）；
- **`last_import` 是结构化 dict**：与 `refresh.py` / `fetch_campus.py` 口径一致
  （早期版本写的是字符串 `"fetch_wechat.py / wxmp · 新增 0 条"`，会让页面与
  `cloud_update.py` 摘要读不出「新增/更新」两列，已统一）。

### 6.1 与 `fetch_campus.py` 会不会重复抓同一篇？

不会入库两次，但**同一篇会被网络请求两次**。原因是两个脚本都会读
`_work/wechat/wechat-<校区>.txt`：

| 脚本 | 怎么处理这个清单 |
|---|---|
| `fetch_campus.py` | 清单里每篇都抓一遍正文（作为「手工补充来源」） |
| `fetch_wechat.py` | API 模式下**只补抓尚未入库**的那些（`--no-seed-fallback` 可关） |

两条路产出的 `i` 都是文章 URL，所以合并端按 `i` 去重，页面不会出现两条。
想彻底省掉重复请求，二选一：
* 把清单只交给一个脚本（例如从 `fetch_campus.py` 撤掉，全靠 `fetch_wechat.py`）；
* 或给 `fetch_campus.py` 传 `--wechat-file /dev/null` 之类指向空文件。

## 7. 页面展示位置

抓来的文章在页面上有三处可见：

1. **来源筛选**：工具栏「微信公众号」分组下会多出这些号，点击可只看某个号；
2. **卡片列表**：卡片上的来源名即公众号名，详情弹窗里有正文摘录与「阅读原文」；
3. **信息来源抽屉**：看到每个号的条数与最近状态；已登记但没抓到文章的号显示为「待接入」。

## 8. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `获取 token 失败` | cookies 过期或复制不全 | 重新登录公众平台，覆盖 cookies 文件 |
| 拉列表全部 `ret=200013` | 账号级限流（freq control） | 属正常，**等数小时至 1 天**再跑；期间搜号不受影响 |
| `ret=200009` | 走的是 `appmsgpublish` 接口 | 同样等解禁；本脚本主用 `appmsg` |
| `搜索「XX」失败` | 号名不精确 / 接口限流 | 用**完整官方昵称**；降低频率、隔一会再跑 |
| 搜到同名社会号 | 名字重名（擦边号） | 收紧 `filter` 正则，或直接填 `fakeid` |
| 名单里的号没抓到 | 摸不到精确匹配 | 核对完整昵称；或直接在名单里补 `fakeid` |
| 改了外部名单的 `max` 没生效 | 旧版本会静默丢掉 | 已修复（外部名单现在会覆盖内置值）；不行就直接传 `--count` |
| `fakeid` 变了 / 抓错号 | 搜索返回了别的号 | 删掉 `_work/wechat/wxmp-fakeid.json` 里对应项，重跑 |
| `每轮取回 0 篇` | 该号近期没更新 / 接口风控 | 属正常；确认 cookies 与号名，稍后再试 |
| 正文为空 | 文章是图片/视频号内容 | 只入库标题与摘要，属正常 |
| 文章被删（含 `tempkey=`） | 原文已失效 | wxmp 的 `is_valid_article_link` 会判为无效，跳过 |
| `未能加载 wxmp` | 没装 wxmp（或解释器不对） | `pip install wxmp`；注意要用**同一个** Python 解释器。没有它也能跑公开种子模式 |

## 9. 合规提醒与"为什么云端默认不开"

- 只抓**公开**可读内容；API 模式仅用**你自己**登录的凭据，不要共享或外借他人 cookies；
- 控制请求频率（所有等待都走 `gentle_sleep()`，在基准值 ±35% 内随机抖动，
  而不是固定间隔——见第 10.5 节），不要暴力刷接口；
- 抓回的内容版权归原作者与发布单位所有，本页面仅作展示与检索，**请勿用于商业用途**。

### 9.1 云端定时任务里为什么默认关掉公众号

`cloud_update.py` 只有在显式 `--with-wechat`（云函数里是 `WITH_WECHAT=1`）时才跑这一步，
原因是它在无状态云函数里有两个硬障碍：

| 障碍 | 说明 |
|---|---|
| **cookies 是账号凭据** | 只有你浏览器登录公众平台才有，几天就过期。放进函数环境变量 = 把账号凭据长期放在云端 |
| **wxmp 依赖链** | pydantic / pandas / requests / fake-useragent / loguru / tqdm，与「阿里云侧零第三方依赖」的打包方式冲突，还要挂 Layer |
| **无持久盘** | `_work/wechat/wxmp-fakeid.json` 这类缓存每轮都会随沙箱销毁 —— 好在这不会丢数据（丢了只是重新搜索） |

**推荐做法**：官网抓取（清华 + 三校）留在云端定时跑，**公众号留给本机**手动或本机定时任务跑。
两者写的是同一份 `data/<校区>.json`，靠「按 `i` 只增不减合并」天然可以交替进行 ——
云端不认识公众号那些 `wx:` 来源，但 `refresh.import_items` 会保留它们。

只有确实需要在云端跑时才：
1. 在 **Linux** 环境打包：`python deploy/serverless/package.py --with-wxmp`；
2. 把 cookies 放进函数包（**注意凭据风险**），或改用环境变量注入；
3. FC 控制台设 `WITH_WECHAT=1`。

## 10. 限流（ret=200013）：为什么"等一天"不是解法

这是公众号链路最容易被误解的一点，值得单独讲清楚。

### 10.1 之前的问题

早期版本遇到 `200013` 的处理是：识别 → 本轮中止 → 提示「等数小时至 1 天解禁」。
问题在于**有些限流等不好的**——它会一直持续，等到第二天重跑还是 0 篇，
然后你又被告知"再等等"。整个链路就成了死循环。

根子在于当时把所有 `200013` 都当成了同一种东西，于是只能给出一种建议。

### 10.2 两种粒度，处置方式完全不同

现在脚本会把限流**分粒度判定**并分别记录（`_work/wechat/wxmp-blocked.json`）：

| 粒度 | 怎么判定 | 处置 |
|---|---|---|
| **账号级** | 连续 3 个号取回 0 篇，**且本轮没有任何号成功** | 换一份凭据，**等无效** |
| **fakeid 级** | 连续 3 个号取回 0 篇，**但本轮有号是成功的** | 只坏在这几个号上，记入名单 6 小时内跳过 |

判定逻辑很朴素但有效：如果这份 cookies 连一个号都搞不定，那是**凭据**的问题；
如果它还能搞定别的号，那是**那几个号**的问题。两者混为一谈时，
你就只会得到"等一天"这种没用的建议。

### 10.3 解法一：凭据轮换池

账号级限流**唯一的解法是换一个登录账号**。把多份 cookies 放进 `_work/wechat/` 即可：

```
wxmp-cookie-header.txt            ← 第 1 份（原有命名，照常生效）
wxmp-cookie-header-pool2.txt      ← 第 2 份
wxmp-cookie-header-pool3.txt      ← 第 3 份
```

最省事的写法是把所有行塞进**同一个文件**，一行一份：

```
_work/wechat/wxmp-cookie-header-pool.txt
```

脚本按**日期**决定用哪一份（同一天多次运行结果一致，出问题可复现），
并且发现当前这份最近被限过时会**自动跳到下一份**。

```bash
python fetch_wechat.py --cred-index 1     # 手工指定用第 2 份
```

配套改动：`fakeid` 缓存也**按凭据分文件**存（`wxmp-fakeid-pool2.json`）。
原因是 fakeid 不是公开常量，而是「某个登录账号搜出来的结果」——
把 A 账号搜到的 fakeid 直接喂给 B 账号去拉文章，在微信看来就是
「B 突然开始访问一个它从没搜过的号」，这正是风控的典型特征。

### 10.4 解法二：公开合集源（零凭据、不受限流）——**推荐优先用**

`appmsg` 有账号级限流，但**公开合集接口没有**：

```
GET /mp/appmsgalbum?action=getalbum&__biz=<biz>&album_id=<id>&f=json
```

2026-10-14 用真实 `album_id` 实测：**`ret=0`，无需任何登录态**，直接返回文章列表
（标题 / 链接 / `create_time`），因此**限流期间依然可用**。

#### 合集 ID 不用人工找，脚本会自动发现

微信把合集链接直接印在文章页里：

```
mp/appmsgalbum?__biz=<biz>&action=getalbum&album_id=<id>#wechat_redirect
```

所以链路是：

```
公开种子的文章页  →  自动解析出 (__biz, album_id)  →  枚举合集文章  →  抓正文
```

**只要有一篇该号的文章链接，就能自动找到它的合集**，不需要维护白名单。
（`extract_album_refs()` 把 `__biz` 与 `album_id` 限定在「同一个链接内」配对，
避免页面别处的 `__biz` 被误配。）

用法：

```bash
python fetch_wechat.py --albums                  # 正常抓取 + 合集补充（去重后合并）
python fetch_wechat.py --albums-only             # 完全不用 cookies，只抓合集
python fetch_wechat.py --albums-only --album-pages 4   # 每个合集多翻几页
```

实跑样例（西安交大，**无 cookies**，10 个种子链接）：

```
· 从 10 篇文章页自动发现合集… → 发现 3 个合集
    - 学院新闻: 取回 40 篇，收录 40 篇
    - 学生风采: 取回  6 篇，收录  6 篇
    - 校友故事: 取回 19 篇，收录 19 篇
· 合集合计 65 条          ← 抓到了正文（dt.tx 有完整内容）
```

**10 条种子 → 65 篇带正文**，全程零凭据、零 `appmsg` 调用。

#### 翻页实测有效

`continue_flag=1` 时，带上一页末条的 `msgid` / `itemidx` 再请求即可续取，每页 10~20 条：

```bash
--album-pages 4    # 每集最多翻 4 页
```

「新闻动态」「浙大等你」「竞赛展演荣誉」等合集都翻出了第二页（+20 篇）。

#### ⚠ `chksm` 是能不能抓正文的关键（受控实测）

微信对文章页链接分三种，**同一条文章**做了对照：

| 链接形式 | 例子 | 结果 |
|---|---|---|
| 短链 | `/s/XLsEsQOyo4qwtekckfDT2A` | ✅ 3.7 MB，正常 |
| **长链带 `chksm`** | `/s?__biz=..&mid=..&sn=..&chksm=..` | ✅ 3.6 MB，正常 |
| 长链**缺** `chksm` | `/s?__biz=..&mid=..&sn=..&scene=21` | ❌ 17 KB 验证码墙 |

差别**只在 `chksm`**。后果有两个：

- ✅ **合集接口返回的链接带 `chksm`，能抓正文** → 全量内容可用；
- ❌ 文章末尾「往期回顾」里的链接**没有** `chksm`，抓不动 →
  只能拿标题做**展示/跳转**，不能拿来继续扩链（所以链接图无法递归）。

#### 手工指定（可选）

不想依赖自动发现，也可以直接配 `_work/wechat/wxmp-albums.json`：

```json
{
  "albums": [{"biz": "MzA5...", "album_id": "1234567890", "name": "招生简章"}],
  "zju":    ["MzAx...:9999999999"]
}
```

> `albums` 是**全局**列表；按校区名分组的写法只对那个校区生效。
> 缩写 `"biz:album_id"` 和完整对象两种写法都认。
> **有清单就优先用清单，没有才去自动发现。**

#### 边界（要清楚）

- 合集里只有作者**手工整理进去**的文章，不是全量历史 → 它是**补充源**，
  不是 `appmsg` 的完全替代（但对「某个学院号持续更新」这个场景已经很好用）。
- 一个文章页只能发现**它所属的那一个**合集；账号级「列出全部合集」的接口
  需要登录态（`action=getalbumlist` → `ret=-3 no session`），拿不到。
  想多覆盖就多给几个不同文章的种子链接。
- **当 `appmsg` 被限流时，脚本会自动改走合集源兜底**，不需要人工干预。

### 10.5 解法三：请求节奏加抖动

原来每一步都是固定间隔（`sleep(1.0)` / `sleep(1.5)`）。
固定间隔本身就是个特征：一个"人"不会每隔正好 1.000 秒点一次接口，脚本才会。
现在所有等待都走 `gentle_sleep()`，在 ±35% 范围内随机。

这不是对抗风控，而是**别让自己的行为特征过于醒目**，同时让服务端压力更平滑。

### 10.6 兜底顺序

一次运行会按这个顺序找内容，前面拿不到就往后走：

```
appmsg（有 cookies，全量历史）
   ↓ 被限流 / 没凭据
合集源（零凭据，只含手工整理的文章）
   ↓ 也没有
公开种子链接（逐篇抓正文）
   ↓ 也没有
上次缓存（保留旧数据，不写空结果）
```

### 10.7 诊断

```bash
python fetch_wechat.py --list-accounts      # 看名单与 fakeid 缓存
python fetch_wechat.py --search-only        # 只搜 fakeid（搜索接口不受 appmsg 限流影响）
cat _work/wechat/wxmp-blocked.json          # 看谁被限过、什么时候、什么粒度
```

`--search-only` 值得单独记一笔：**`searchbiz` 不受 `appmsg` 的限流影响**。
所以即使是账号级限流期间，也能把名单里所有号的 fakeid 先锁定下来，
等换好凭据（或解禁）后直接抓取，省掉一整轮搜索。

### 10.8 仍然解决不了的情况

诚实说明：如果**只有一个**公众平台账号、且它被账号级限流，
那么在没有第二份凭据的情况下，**`appmsg` 这条路就是走不通的**，只能靠合集源供数。
这是微信侧的账号级限制，脚本层面无法绕过——能做的只是
① 把损失降到最小（自动降级到合集源、不写空结果、保留旧数据）；
② 让你在准备好第二份凭据后**一条命令恢复**。

不过第 ① 条现在比过去有力得多：合集源能拿到**正文**（`chksm` 链接可抓），
并且**合集 ID 自动发现**，所以限流期可以纯靠 `--albums-only` 维持更新，
不需要等到换上第二份 cookies。代价是**覆盖面**：只有被作者整理进合集的文章才有。

### 10.9 关于「模拟用户操作」（桌面自动化）——评估结论

限流逼出来的另一个想法是：**干脆用桌面自动化模拟真人操作**（点微信客户端、
或用浏览器打开文章），这样服务端看到的就是"正常用户"。

结论是**不做**，理由已单独成文，见
[`公众号聚合方案评估.md` 第 10 节](公众号聚合方案评估.md#10-模拟用户操作桌面控件--浏览器自动化可行性评估)：

| 子路线 | 本机实测 | 结论 |
|---|---|---|
| 自动化微信客户端界面（wxauto 类） | 本机微信 **4.1.15.55**，UIAutomation 已完全失效 | ❌ 已死，且拿不到批量历史 |
| 给微信客户端注入调试通道（`--remote-debugging-port` / Frida） | 内嵌运行时 `RadiumWMPF` 25560/25799，**超出主流工具适配区间**；默认关闭调试通道 | ❌ 红线最硬，后果落在**个人微信号**上 |
| 独立浏览器自动化（Playwright） | 依赖全未安装（环境干净） | ⚠ 只能补单篇正文，**留作人工兜底** |

一句话：桌面自动化补的是"最后一公里"（正文），而这条链路缺的是"第一公里"（列表）；
而正文这条，**合集源已经零凭据拿到了**。

### 10.10 关于「让大模型看屏幕 + 点鼠标」（GUI 智能体）

再进一步的想法是：不写死脚本，让**多模态大模型看截图、自己决定点哪里**，
通过模拟鼠标键盘去微信里搜索、分享、取链接（业内称 Computer Use / GUI Agent）。

结论同样**不做**，见
[`公众号聚合方案评估.md` 第 11 节](公众号聚合方案评估.md#11-让大模型看屏幕--点鼠标视觉驱动的-gui-智能体可行性评估)。
要点：

- **技术成立**（单步元素定位准确率 94.2%），**但对本项目不成立**：
  完整的百步桌面任务成功率只有 **42.5%**，而"取一篇链接"要 20~30 步；
- **决定性反例**：2025-12 豆包手机助手自动操作微信，**账号被强制下线**，
  随后豆包下线了该功能——它同样是"视觉理解 + 模拟真人操作"、不 Hook 不注入；
- 规范 1.2.6 禁的是**"自动化操作"这个行为**，不是某种技术实现，VLM 不会因为"更像人"就豁免；
- 它还会**把整块屏幕（含聊天记录）送出本机**，这是脚本方案没有的风险。

**但这条思路留下一个真正有用的出口**：微信"复制链接"给的通常是**短链**，
而短链**本来就能抓**（`/s/XLsEsQOyo4qwtekckfDT2A` → 3.73 MB，正文完整）。
所以正确形态是**人工点两下复制链接 + 脚本监听剪贴板自动入库**
（本机 `Get-Clipboard` / `Set-Clipboard` 实测可用）——
省掉的是两下点击，保住的是账号。

### 10.11 关于「实体机器人坐在电脑前」

再想到极致就是：**机械臂当手、摄像头当眼睛**，让一台机器人真的"坐"在电脑前操作
（第 11 节思路的物理化终点）。

结论仍是**不做**，见
[`公众号聚合方案评估.md` 第 12 节](公众号聚合方案评估.md#12-有手有眼的实体机器人坐在电脑前可行性评估)。
这次的理由是一个**悖论**：

- 业界真有先例——**Selenium 作者 Jason Huggins 创办的 Tapster** 就是干这个的，
  它的存在理由是"**要自动化一个你根本没有接口的封闭 App**"（如 iOS 上的他人 App）；
- **而本项目有接口**（合集接口零凭据、一次拿 10~20 条带 `chksm` 的链接）；
- 更关键：**机器人"不累、动作完全一致"这个最大卖点，恰好是行为风控要找的特征**。
  反作弊领域的结论是——**检测的是"输入的熵值"，不是"输入的来源"**：
  真人点击间隔标准差 >15 ms，宏 <5 ms；"无论你使用的是什么硬件，都会被标记为异常"。
  机械臂的重复误差是**系统性**的，在这条维度上比软件脚本**更醒目**。
- 规范定性也没变：1.2.6 禁的是"**自动化操作**"这个行为，不是执行装置。

一句话：**与其让机器人坐在电脑前，不如让真人坐在电脑前点两下。**
