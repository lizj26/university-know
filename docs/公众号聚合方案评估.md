# 微信公众号聚合方案评估（对照外部三个提案）

本文评估三套外部提案（WeSum + GitHub Actions / we-mp-rss + Easy-RSS / JuFlow），
并对照本项目已有的 `fetch_wechat.py` 链路，给出「跟不跟、怎么跟」的结论。

> 结论先行：**三套都可行，但没有一套需要替换现有链路。**
> 其中第 1 套的数据源（Wechat2RSS 免费列表）经实测**基本不含高校/学院号**，
> 对本项目「只聚合几个学院公众号」的目标命中率极低；第 2 套与本项目已有能力**功能重叠**；
> 第 3 套超出需求范围。真正值得吸收的是「公开合集接口」这条零凭据补充路径。
>
> **后续补充（重要）**：外部三套的共同前提都是「换一个数据源」，
> 而本项目真正卡住的地方是**限流**——那是脚本层要自己解决的问题，换数据源解决不了。
> 针对限流的改动见 **第 7 节**。

---

## 0. 本项目现状（评估基线）

`fetch_wechat.py` 已经实现了一套可用的公众号抓取，且与官网链路解耦：

| 能力 | 实现 |
|------|------|
| 按昵称找号 | `wxmp` → `/cgi-bin/searchbiz`，昵称全平台唯一，精确匹配即命中 |
| 拉历史文章 | `wxmp` → `/cgi-bin/appmsg`，支持翻页、`--count/--pages` 限制 |
| 凭据 | `_work/wechat/wxmp-cookies.json`（全局）/`-<校区>.json`（覆盖），需 `wxuin` + `pass_ticket` |
| 限流处理 | 显式识别 `ret in (200013, 200003, -6)`，命中即整轮放弃，不污染数据 |
| 与主页面的关系 | 按 `i` 去重、90 天保留期，**追加**进 `data/<校区>.json` |
| 断链容错 | 无 cookies 时自动跳过联网、只做本地合并与重建页面 |
| 文件名隔离 | 公众号产物全在 `_work/wechat/`，清缓存/排查/备份互不牵连 |

关键差异：**本项目要的是「合并进自己的站点」，外部三套要的是「把摘要推给你看」。**
目标不同，因此评估重点不是「哪个项目更好」，而是「哪条能力值得借」。

| 语言/许可 | — | Python / MIT，2 star、8 fork（**很小众**） |
| 架构 | — | 单体 `main.py` |
| 摘要模型 | 通义千问（Qwen） | ✅ 支持，且**已扩展**为 OpenAI 兼容接口：智谱 GLM、Qwen、OpenAI、DeepSeek、Kimi 均可 |
| 推送目标 | 企业微信 robot / GitHub Gist | ✅ 正确 |

### 致命问题：数据源与需求不匹配

WeSum 自己不抓微信，它**消费 Wechat2RSS 的 RSS**。所以 WeSum 能不能用，完全取决于
Wechat2RSS 免费列表里**有没有你要的号**。

实测抓取 `https://wechat2rss.xlab.app/list/all.html` 的真实目录（共 **395** 个 feed）：

- 分节：**安全 / 开发 / 其他 / 用户提交**
- 整体取向偏 **技术、安全、投资、时评**
- 全部 395 个条目里，命中 `大学|学院|高校|中学|招生|研究生|学生会|团委|教务|图书馆` 的：

```
看雪学院      ← 安全培训机构，不是高校
广州图书馆    ← 公共图书馆
```

**只有 2 个，且没有一个是高校或学院。**

也就是说：**「几个学院公众号」这个目标，Wechat2RSS 免费列表里几乎必然找不到。**
它的「用户提交」节（42 个）可以提 PR 申请收录，但收录标准由维护者定，且更新周期 24 小时。

想要任意号，只能走**付费私有部署**（README 标注 15 元/月）；实测其
`/deploy/` 定价页与 README 表述一致。私有部署 = 你自己跑一个 Wechat2RSS 实例，
而 Wechat2RSS 私有部署**同样需要微信读书/公众号的登录凭据**——绕了一大圈，
**又回到了本项目 `wxmp` 凭据的同一类风险**，还多了一个要维护的服务和一笔月费。

### 结论

- ❌ **不建议采用。** 它是「RSS 摘要推送」方案，不是「内容入库」方案；
  且免费数据源覆盖不了高校号，付费私有部署换不来比现有 `wxmp` 更低的凭据风险。
- ✅ **可借鉴的一点**：它的**多模型 + OpenAI 兼容接口**设计很干净
  （`LLM_PROVIDER` / `LLM_BASE_URL` / `WECHAT_MODEL` 三个变量切换服务商）。
  本项目**若**将来要做「文章 AI 摘要」，照这个接口形状设计即可，不必引入整个项目。
- ⚠️ **注意**：DeepSeek 给的仓库地址是错的。照它说的去 fork，会直接 404。
  这类「看起来具体、实际不存在」的地址，是本次评估里最需要警惕的信号。

## 2. 🥈 we-mp-rss + Easy-RSS

### 实测核实

| 项 | 说法 | 实测 |
|----|------|------|
| 仓库 | `rachelos/we-mp-rss` | ✅ 真实存在，活跃 |
| 技术栈 | — | Python / FastAPI + Vue |
| 端口 | `-p 8001:8001` | ✅ 一致 |
| 默认账号 | `admin` / `admin@123` | ✅ 一致 |
| 授权方式 | 扫码授权 | ✅ 基于微信读书登录态 |
| 部署 | `docker run -d ... ghcr.io/rachelos/we-mp-rss:latest` | ✅ 一行可跑 |

### 与本项目的关系：**功能重叠**

we-mp-rss 的原理是「用登录态调微信接口拉历史文章」——**这正是本项目
`fetch_wechat.py` 已经在做的事**（`wxmp` → `searchbiz` / `appmsg`）。

差别只在形态：

| 维度 | we-mp-rss | 本项目 `fetch_wechat.py` |
|------|-----------|-------------------------|
| 凭据来源 | 扫码（微信读书登录态） | 浏览器 cookies（`wxuin`/`pass_ticket`） |
| 产物形态 | RSS + Web 阅读器 | 直接合并进 `data/<校区>.json` |
| 运行方式 | 常驻 Docker 服务 | 跑完即退的脚本，可进 CI |
| 主页展示 | 它自己的阅读界面 | **本项目自己的站点**（已做按需加载） |

对本项目而言，引入 we-mp-rss 意味着：多一个常驻服务、多一套数据库、
再把它的 RSS 解析回自己的 JSON——**净增复杂度，能力没有变多。**

### 结论

- ❌ **不建议引入。** 与现有链路同构，属于重复建设。
  而且它走的是微信读书入口，**风险明显高于现有方案**（用户协议明文禁止、
  频控更严、要号池、速度慢 20 倍）——详见 **第 8 节**。
- ⚠️ **「扫码取凭据」这个看起来的优点也要打折扣**：扫码确实比手动复制 cookies 省事，
  但换来的是把**微信读书登录态**交给第三方服务持有，而部分实现还要经第三方中转。
  风险面没有变小，只是换了个位置。

## 4. 公开合集接口（无需登录）——已采纳并验证

这是本次评估里**唯一一条新增的、可直接增强现有链路的能力**，且 DeepSeek 并未提出。
（现在它已经作为限流期的兜底源实现进 `fetch_wechat.py`，见第 7 节。）

```
GET https://mp.weixin.qq.com/mp/appmsgalbum?action=getalbum&__biz=<biz>&album_id=<id>&f=json
```

**第一轮**只验证到「接口可达、无需凭据」（用占位参数拿到 `ret:10004`）。
**第二轮**从文章页里解析出**真实 `album_id`**，把成功路径也跑通了：

```
ret=0，直接返回 article_list（标题 / 链接 / create_time）
合集标题示例：学生风采(6) / 新闻动态(10+20) / 校友故事(10+9) / 强国担当(10+20) / 浙大等你(10+20)
```

还实测出两条关键事实：

1. **`album_id` 不需要人工找** —— 微信把合集链接印在文章页源码里
   （`mp/appmsgalbum?__biz=..&action=getalbum&album_id=..`），
   所以有任意一篇该号的文章就能自动发现它的合集。
2. **`chksm` 决定能不能抓正文** —— 合集返回的链接带 `chksm`，可抓；
   文末「往期回顾」的链接没有 `chksm`，会吃验证码墙（详见第 7 节）。
3. **翻页可用** —— `continue_flag=1` 时带 `msgid`/`itemidx` 续取，每页 10~20 条。

实跑（西安交大，**无 cookies**，10 个种子）：**→ 3 个合集 → 65 篇带正文**。

价值与限制：

| | |
|---|---|
| ✅ 优点 | **零凭据、零限流风险**，不受 `ret=200013` 影响，不怕 cookies 过期 |
| ✅ 优点 | 合集 ID **自动发现**，不需要人工维护白名单 |
| ✅ 优点 | 返回的链接带 `chksm`，**能抓到正文**（不只是标题） |
| ✅ 契合 | 学院公众号常把「招生简章 / 讲座通知」做成合集，正好是站点想收录的内容 |
| ❌ 限制 | 只能拿到**作者手工整理进合集**的文章，不是全量历史 |
| ❌ 限制 | 一个文章页只暴露**它所属的那一个**合集；账号级「列出全部合集」需要登录态（`ret=-3`） |

**已落地**：作为 `fetch_wechat.py` 的**补充源**（而非替代）——
在 cookies 失效或限流期间，合集链路仍能持续供数。

```bash
python fetch_wechat.py --albums                # 正常抓取 + 合集补充
python fetch_wechat.py --albums-only           # 只用合集，完全不碰 cookies
python fetch_wechat.py --albums-only --album-pages 4
```

## 6. 总结

| 方案 | 可行性 | 建议 |
|------|--------|------|
| 🥇 WeSum + Actions | 技术上可行，**但数据源覆盖不了高校号** | ❌ 不采用；仅借鉴其多模型接口设计 |
| 🥈 we-mp-rss + Easy-RSS | 完全可行，**但与 `fetch_wechat.py` 功能重叠** | ❌ 不引入；仅借鉴扫码取凭据的思路 |
| 🥉 JuFlow | 可行，**但超出「只要公众号」的需求** | ❌ 暂不采用，留待多平台需求出现 |
| 📚 公开合集接口 | **实测可行、无需登录** | ✅ **已采纳**，作为限流期的兜底源 |

**一句话**：这三个外部方案都没有触及本项目的真正瓶颈。
它们解决的是「换个地方取内容」，而本项目卡住的地方是——**微信对 `appmsg` 接口的账号级限流，
不是「内容不够多」，而是「这一份凭据已经拉不动了」**。
这个问题只能在脚本层解决，换数据源、换阅读器、换聚合平台都绕不过去（详见第 7 节）。

## 7. 关于限流的补充（外部方案都没解决的问题）

外部三套方案放在一起看，有一个共同点：它们都在**换数据源的位置**
（Wechat2RSS 的 RSS、we-mp-rss 的扫码登录态、JuFlow 的多平台聚合），
没有一套在**解决方案层面的限流**。

而本项目真正的瓶颈恰恰是限流。所以「现有方案无法解决限流」这个判断是对的——
但它不是「要换方案」的理由，而是「要在现有链路上补三块东西」的理由。

### 7.1 之前错在哪：把两种限流当成一种

早期实现里所有 `200013` 都被当成同一回事，于是只能给出一种建议：「等数小时至 1 天」。
但微信的限流至少有**两种粒度**：

| 粒度 | 特征 | 等待有用吗 |
|---|---|---|
| **账号级** | 这份登录态被盯上，**所有号都拉不到** | ❌ 无效，会持续 |
| **fakeid 级** | 只坏在个别号，**别的号照常能拉** | ⚠️ 通常自行恢复 |

把两者混为一谈的后果就是：明明是账号级（等不好的那种），却告诉用户"等一天"，
第二天重跑还是 0 篇，然后再等一天——死循环。

### 7.2 补的三块

| # | 改动 | 针对的粒度 |
|---|---|---|
| 1 | **凭据轮换池**：支持多份 cookies，按日期轮换、被限自动跳下一份 | 账号级 |
| 2 | **公开合集源**：零凭据 `appmsgalbum` 接口，限流期间照常可用 | 两者都能兜 |
| 3 | **分粒度判定 + 限流记忆**：区分账号级/fakeid 级，分别记录、分别建议 | 诊断 |

外加一块配套修正：**`fakeid` 缓存按凭据分文件**。
fakeid 不是公开常量，而是「某个登录账号搜出来的结果」，
把 A 账号的搜索结果直接喂给 B 账号去拉文章，在微信看来就是风控特征。

还有一项：**请求间隔加 ±35% 随机抖动**。固定间隔（每次都正好 1.000 秒）
本身就是脚本特征，改成区间更接近真人操作。

### 7.3 效果

- 账号级限流不再必然导致本轮到 0：有第二份凭据就自动换，没有就自动降级到合集源；
- 报告从笼统的「等一天」变成**可执行**的「准备第 2 个账号存成 `-pool2.txt`」；
- fakeid 级限流不再牵连整轮，只跳过个别号。

### 7.4 诚实的边界

如果**只有一份**凭据且它被账号级限流，那么 `appmsg` 这条路就是走不通的，
只能靠合集源供数。这是微信侧的账号级限制，脚本层面无法绕过。
能做的只是把损失降到最小，并在你准备好第二份凭据后一条命令恢复。

**所以：外部三套方案没有一个能替代这件事。** 它们解决的是"从哪取"，
而这里要解决的是"取不动了怎么办"。后者必须落在自己的链路上。

详细的实现与用法见 [`wxmp公众号接入.md` 第 10 节](wxmp公众号接入.md)。

## 8. 微信读书入口的风险（为什么最终没用它）

> **2026-10 更新**：本节的结论是在「后台接口还活着」的前提下写的。
> 现在 `searchbiz` / `appmsgpublish` 已被微信在接口层面封禁（见 13.4 的修正块），
> 「用后台接口拉任意号列表」这条路整体关门，微信读书路线反而成了**唯一仍活跃维护的
> 自部署路线**（继任项目 `rachelos/we-mp-rss`，2026-10 仍在推送；`cooderl/wewe-rss`
> 已于 2026-03 归档、其闭源中转 `weread.111965.xyz` 已 502，存量部署无解）。
> 所以下面的风险分析**一条都还有效**（协议、风控、号池、速度），但现在它们是
> 「这条路本身的成本」，而不是「相对更稳方案的额外成本」。
> 若要上：只用专用小号、严格限频、接受 80 小时级重扫授权的运维负担——
> 详见本轮《WeWe RSS 可行性》的结论，此处不重复。

这是外部方案的「第 2 条腿」：`we-mp-rss` / `wewe-rss` 抓公众号走的是**微信读书的网页内部接口**。
在第 2 节里我只说它「与现有能力重叠」，那还不够——**它的风险其实明显更高**。
下面每一条都来自实测或原文，不是推测。

### 8.1 它到底怎么工作

| 项 | 内容 |
|---|---|
| 列表 | `GET weread.qq.com/web/mp/articles?bookId=&offset=` |
| 正文 | `GET weread.qq.com/web/mp/content?reviewId=` |
| 凭据 | Cookie `wr_vid` / `wr_skey` / `wr_rt` |
| 错误码 | `-2010` 用户不存在 · `-2012` 登录超时 · `-2041` 认证风控 |

有意思的是 `reviewId` 的构造：形如 `<bookId>_<token>`，**token 段直接就是
`mp.weixin.qq.com/s/<token>` 的原文短链 token**。所以拿到列表就等于拿到了永久原文直链。

### 8.2 风险一：用户协议**明文禁止**（最硬的一条）

抓取 `https://weread.qq.com/web/copyright`《微信读书软件许可及服务协议》正文，
6.1.2 条逐款禁止：

| 条款 | 原文 |
|---|---|
| 6.1.2.1 | 修改、删除、**避开为保护知识产权而设置的任何技术措施** |
| 6.1.2.2 | **反向工程、反向汇编、反向编译**，或尝试提取源代码 |
| 6.1.2.4 | 使用插件、外挂或**非经腾讯授权的第三方工具/服务接入本软件和相关系统** |

第 7 条后果：可「警告、限制或禁止使用部分或全部服务、**账号封禁直至注销**」，
且「有权追究你的相关责任」；7.6 条：「用户应**独自承担**由此而产生的一切法律责任」。

**这跟公众平台 cookies 的性质不一样**：后者是「用自己账号后台的正常功能」，
前者是「用非授权第三方工具接入」。前者是灰色，**后者是白纸黑字的红线**。

### 8.3 风险二：账号（频控更严、要号池）

- 登录态短：`-2012` 过期频繁，社区有「约 72 小时」甚至有「一个半小时就得重登」的说法；
- 频控报告：「**单账号每天 50 次请求、单 IP 24 小时 300 次**」，项目作者自述
  「之前放宽到 300 次每天，**没两天接口就 gg 了**」；
- 「小黑屋」：操作密集直接封控 24 小时；
- 规模化结论是「**需要号池**」——即把多个真实微信账号投入轮换，
  **封号后果直接落在个人账号上**；
- 速度还慢：300 个号抓单日列表需 **6 小时以上**（公众平台后台方案约 20 分钟）。

### 8.4 风险三：法律（DMCA 前科，但要看清事实）

腾讯 **2026-01-08** 的 DMCA 投诉是真实的，我核对了原文：

- 依据 **17 U.S.C. §1201 反规避条款**；
- **一次处理 4,195 个仓库**（含整个 fork 网络）——GitHub 明确说明因涉及仓库超过 100 个，
  按整个网络处理；
- 点名 **32 个仓库，全部是微信聊天记录解密类**（`wechat-dump`、`WeChatMsg`、
  `SharpWxDump` 等）。

**关键澄清**：我逐词检索了那份投诉全文——`weread` / `微信读书` / `公众号` /
`mp.weixin` / `rss` **出现 0 次**。

所以准确表述是：**读书类项目目前没被点名下架过**。
但那套法律逻辑（绕过技术保护措施）是同一套，换个目标随时可以用。

### 8.5 风险四：供应链与隐私

- 「部分请求需要**通过第三方服务器中转**」——有项目被指半开源、含黑盒操作，
  意味着**你的读书登录态可能经过他人的服务器**；
- 社区明确警告：「如果需要扫码，那么请谨慎一些，因为你的**账号可能被充当号码池中的一份子**」；
- 部署地与常用登录地不一致 → 触发异地登录安全提醒。

### 8.6 那官方通道呢？它不给这个能力

微信读书有官方 Agent Skill（2026-05-17，`i.weread.qq.com/api/agent/gateway`，`wrk-` Key）：

- ✅ 走官方网关，**合法、有文档**；
- ✅ 搜索支持 `scope=4`（搜公众号文章），目录接口有 `isMPChapter` 标记；
- ❌ 但**只给标题和更新时间**——没有文章级封面、没有 `reviewId` 到原文直链的映射、
  **更没有正文接口**。

即：**公众号批量抓取被官方明确划在了边界外**。想拿完整内容，
`/web/mp/*` 那套内部接口仍然是唯一路径——而那正是 8.2 禁止的对象。

### 8.7 结论

**收益相同，风险全面更高。**

| 维度 | 公众平台后台（本项目） | 微信读书入口 |
|---|---|---|
| 能拿到 | 列表 + 正文 | 列表 + 正文（**相同**） |
| 合同 | 用自己账号的正常功能 | **明文禁止**（6.1.2 三款） |
| 频控 | 账号级限流，有缓解手段 | 限流 + 小黑屋 + **要号池** |
| 速度 | 300 号 / 约 20 分钟 | 300 号 / **6 小时以上** |
| 凭据暴露 | 只在你自己的机器上 | 可能**经第三方中转** |
| 账号后果 | 后台功能受限 | **微信账号被封** |

用微信读书换公众平台，是**用更大的风险换同一个结果**，不划算。
因此本项目维持 `appmsg` + 凭据池 + 合集源，不引入读书路线。

> 如果你出于别的用途确实要用读书接口：**绝不要用主力微信账号**，
> 并且优先只用官方 Agent Skill（合法、有边界），不要碰 `/web/mp/*` 内部接口。

## 9. 「推文里指向其他公众号的链接」——实测结果与直觉相反

有一个很自然的想法：**不抓内容，只把文章里出现的公众号文章链接展示出来当跳转入口**。
这样既不用 cookies、也不碰 `appmsg`。带着这个想法对 39 篇真实文章做了全量解析，结果是：

### 9.1 跨号链接几乎为零，绝大多数是「同号往期回顾」

| 类型 | 数量 |
|---|---|
| **同号**文章链接（该号自己的往期推荐） | **50 条** |
| **跨号**链接（真正指向别的公众号） | **1 条**（还是出现在微信平台页，不在正文） |

即：**「推文里链到别的公众号」这个前提，在学院号这个样本里基本不成立。**
正文里的链接绝大多数是文末的「往期回顾 / 相关阅读」，指向**同一个号**。

**但这反而更符合项目的实际需求** —— 往期回顾给的正是 `appmsg` 想给的东西
（该号的更多文章），而且是**零凭据**拿到的。

### 9.2 覆盖密度

| 指标 | 实测值 |
|---|---|
| 含往期链接的文章 | **8 / 39**（约 20%） |
| 有链接时每篇条数 | 3~5 条 |
| 锚文本是否带标题 | 部分带（如「化学生物协同物质创制…」），部分为空 |
| 平台样板链接 | 《名誉保护投诉指引》出现在 **39/39** 篇，必须过滤 |

### 9.3 致命限制：这些链接抓不动，所以**链接图无法递归**

往期回顾的链接是**缺 `chksm` 的长链**，实测会返回验证码墙（17 KB，加载 TCaptcha.js）。
它**在浏览器里点得开**，但**脚本抓不到**。后果：

- ✅ 「展示 + 跳转」可行（标题从锚文本就能拿到，根本不用抓目标页）；
- ❌ 不能靠「抓新发现的链接 → 再挖链接」逐层扩张。

同一条文章的受控对照（决定性证据）：

```
短链 /s/XLsEsQOyo4qwtekckfDT2A                                    → 3.73 MB ✅
长链 /s?__biz=..&mid=..&idx=..&sn=..&chksm=..                     → 3.59 MB ✅
长链 /s?__biz=..&mid=..&idx=..&sn=..（去掉 chksm，即往期链接形式）  → 17 KB 验证码墙 ❌
```

### 9.4 结论：这个思路**可以不做**，因为有更好的

「只展示跳转链接」本意是**放弃正文来换稳定性**。但第 4 节那套合集链路
**既不要凭据、又能拿到正文**（因为合集返回的链接带 `chksm`），
所以「退一步只展示链接」这一步**没必要退**：

| 方案 | 凭据 | 正文 | 递归扩链 |
|---|---|---|---|
| 展示往期跳转链接 | 无 | ❌ 无（只有标题） | ❌ 不能 |
| **合集链路（已采纳）** | **无** | ✅ **有** | ✅ 可翻页 |

> 如果将来确实需要一个「延伸阅读」的链接条，`extract_album_refs()` 那套解析
> 已经证明可以从文章页里稳定取到链接与标题；但那属于**锦上添花**，
> 不是解决「拿不到文章」的办法。

## 10. 模拟用户操作（桌面控件 / 浏览器自动化）——可行性评估

> **结论先行**：「模拟真人操作」听起来是最像"不会被拦"的路子，但拆开看是三条
> 完全不同的路线，**风险与收益差一个数量级**：
>
> - **A 条（自动化微信客户端界面）**：本机实测**已经死了**——微信 4.1.15.55 把
>   UI 自动化的路彻底堵死，而且它本来也拿不到批量历史文章。
> - **B 条（给微信客户端注入调试通道）**：技术上是唯一"真正能解决问题"的桌面方案，
>   但**红线最硬、后果最重**（落在**个人微信号**上），且本机运行时版本已超出主流工具适配区间。
> - **C 条（独立浏览器自动化）**：唯一可以谈的一条，**但它只是"配件"，不是主力**——
>   只能补单篇正文，拿不到列表，也进不了无人值守流水线。
>
> **最终建议：A、B 不做；C 只写进"人工兜底清单"，不工程化。**
> 桌面自动化解决的是"最后一公里"（正文），本项目缺的是"第一公里"（列表）。

### 10.1 三条子路线一览

| 子路线 | 典型工具 | 动谁 | 能否解决本项目瓶颈 | 结论 |
|---|---|---|---|---|
| **A** 客户端 UI 自动化 | wxauto / pywinauto / 坐标点击 + OCR | 微信客户端**界面** | ❌ 拿不到批量历史 | ❌ 不做（本机已失效） |
| **B** 注入式调试 | `--remote-debugging-port` / Frida (WMPFDebugger) | 微信客户端**进程** | ⭐ 能拿正文 + `appmsg_token` | ❌ 不做（红线最硬） |
| **C** 独立浏览器自动化 | Playwright / Selenium + 持久化 profile | 一个**普通浏览器** | ⚠ 仅能破 `chksm` 墙 | ⚠ 仅作人工兜底 |

### 10.2 A 条：自动化微信客户端界面——本机实测已经死了

**实测环境**（本机，2026-10-14）：Windows 11 + **微信 4.1.15.55**（`C:\Program Files\Tencent\Weixin`），微信正在运行。

| 探测项 | 实测结果 | 含义 |
|---|---|---|
| 微信版本 | **4.1.15.55** | 落在"UIAutomation 完全失效"区间（4.1.12+） |
| UI 渲染方式 | Qt Quick/QML（4.0.5 起从 Qt Widgets 迁移） | 界面经 OpenGL 渲染到单一画布，**控件不再有独立 HWND** |
| 老牌库状态 | wxauto 已于 **2025-10-28 归档停更**；wxauto4 亦标注停止更新 | 生态已经放弃这条路 |
| 退化方案 | 截图 + OCR + 坐标点击 | 速度以"分钟/篇"计 |

根因不是"库坏了"，而是**微信主动把 UI 从可访问性树里摘了出去**（本机版本正是这一代）：
UIA 工具连"输入框/消息列表/发送按钮"都枚举不到。

**就算它没死，也解决不了本项目的问题**：UI 自动化擅长"点按钮、发消息"，
不擅长"把某个号的几百篇历史文章批量导出"——那需要滚列表 + 逐篇打开 + OCR 正文，
既慢又脆。**这条路与需求根本错配。**

### 10.3 B 条：注入式调试——技术最诱人，风险最高

这条才是桌面方案里唯一"真的能解决问题"的。原理链条如下（本项目实测支撑）：

微信 PC 端打开公众号文章用的是**内嵌 Chromium**。只要给它加上
`--remote-debugging-port`，或用 **WMPFDebugger**（Frida hook `WeChatAppEx.exe`）
把 CDP 通道代理出来，就能做两件现有链路做不到的事：

1. **直接读内嵌浏览器里文章正文的 DOM** → 绕过 `chksm` 验证码墙；
2. **抓到微信自己发出的 `profile_ext?action=getmsg` 请求，连同 `appmsg_token` 一起复制出来**
   → 等于拿到该号的历史文章列表（`profile_ext` 与 `appmsg` 是两套接口，不受 `appmsg` 限流影响）。

**但本机实测直接否决了它：**

| 探测项 | 实测结果 |
|---|---|
| 内嵌运行时 | `RadiumWMPF`，目录 `…\xwechat\xplugin\plugins\RadiumWMPF\` 下 **25560 与 25799 两个版本并存** |
| 核心库 | **`flue.dll` 236 MB / 237 MB**（Chromium 系）、`xweb_elf.dll` |
| 进程命令行 | **没有** `--remote-debugging-port`（调试通道默认关闭） |
| DevTools 前端资源 | 目录里**只有** `wmpf_*.pak` / `locales/*.pak`，**没有** `devtools_resources.pak` |
| 主流工具支持区间 | WMPFDebugger 适配的内部版本约 **11581–19459**（最新适配列到 25715） |
| **本机版本** | **25560 / 25799** ← 处于边缘甚至超出区间 |

也就是说：要么等工具适配本机这个运行时版本，要么自己用 Frida 去 hook ——
后者已经是**逆向注入**了。

**红线（逐条命中，不是推测）：**

| 来源 | 条款 | 内容 |
|---|---|---|
| 《微信个人账号使用规范》 | **1.2.6** | 禁止"通过非腾讯开发、授权的第三方软件、插件、外挂、系统等……**进行自动化操作**，对微信软件及其组件、模块、**界面**、数据等进行**访问、读取或控制**" |
| 同上 | **1.2.7** | 禁止"**规避、破坏**微信软件设置的安全保护等技术措施" |
| 同上 | **1.2.4** | 禁止对"软件运行过程中**释放到任何终端内存中的数据**……复制、修改、挂接运行" |
| 微信安全中心公告 | 2026-03 | 明确"禁止使用各类外挂"，并做专项清理、阶梯式处理 |

> 1.2.6 那一条几乎是**逐字描述**了桌面自动化。这与"用自己公众平台后台的正常功能"
> 是**两个性质**：前者是白纸黑字的红线，后者是灰区。

**最要命的是后果落点不同：**

| | 接口方案（现状） | 客户端注入（B 条） |
|---|---|---|
| 失手后果 | 公众平台**后台功能**受限（限流） | **个人微信号**被限制登录 / 永久封禁 |
| 社区实测 | `ret=200013`，可换凭据或走合集 | Hook/注入类封号率 **>90%**；第三方多开 30%–50% |
| 追责特点 | 即时 | 风控有**历史回溯**，停用后仍可能被"秋后算账" |

**结论：性价比彻底为负。** 用"个人微信号被封"的风险，去换一份"正文 + 列表"，
而现有链路已经能免费拿到这两样（`appmsg` 有列表有正文，合集有正文）。
这是拿最重的筹码换已有的东西。

### 10.4 C 条：独立浏览器自动化——唯一能谈的，但它只是"配件"

这条**不碰微信客户端**：只用一个真实的 Chrome/Edge + 持久化 profile，
通过 Playwright / Selenium 去访问 `mp.weixin.qq.com`。

**它能解决的只有一件事——突破 `chksm` 验证码墙。**

现有 `fetch_html()` 是裸 `urllib` + 浏览器 UA，**不能执行 JS**，
所以「往期回顾」那种缺 `chksm` 的链接必然吃到 17 KB 验证码墙
（受控对照见第 9.3 节）。真实浏览器有 JS 执行环境与完整会话，能把这堵墙打开。

**它解决不了什么（必须说清楚）：**

- ❌ **拿不到链接。** 它只能"打开一个已知 URL"，不产出"这个号有哪些文章"。
  链接来源仍然只有三处：`appmsg` / 合集 / 公开种子——**第一公里它帮不上**。
- ❌ **不能递归扩链。** 破墙只对单篇有效；社区在批量场景下的一致结论也是同一句：
  真实浏览器自动化"**是其他路线的配件，而不是主力**"。

**与现有架构的冲突（这是项目层面的硬伤）：**

| 现状（本项目） | 桌面自动化要求 |
|---|---|
| GitHub Actions / EdgeOne 云函数，跑完即退 | 一台**常开 Windows** + 保持登录的浏览器 profile |
| 无界面、可并发、可无人值守 | 需要**可见桌面**（headless 更易被判为自动化） |
| 零运维 | 版本升级、弹窗、DPI、锁屏都会打断 |

**本机实测**：`playwright / selenium / pywinauto / uiautomation / PIL / cv2 / pytesseract`
**全部未安装** —— 环境是干净的，没有任何现成的自动化底座（这本身也说明项目一直没走这条路）。

**合理定位**：写进「**人工兜底清单**」，而不是工程化。即：偶尔有一两篇确实需要、
又被验证码墙挡住时，人工用浏览器打开复制，或跑一次**有头** Playwright 补单篇；
**不做常驻服务、不做批量、不进 CI。**

### 10.5 对比总表（含现有方案）

| 维度 | A 客户端 UI | B 注入式 | C 独立浏览器 | **现有方案**（appmsg + 合集） |
|---|---|---|---|---|
| 拿历史列表 | ❌ | ✅（借 `profile_ext` token） | ❌ | ✅ |
| 拿正文 | ❌（OCR） | ✅ | ✅（破墙） | ✅ |
| 本机当前可用性 | ❌ **已失效** | ⚠ 版本超出适配区间 | ✅ 需先装依赖 | ✅ **已在跑** |
| 需常开机器 | ✅ | ✅ | ✅ | ❌ |
| 可进 CI / 无人值守 | ❌ | ❌ | ❌ | ✅ |
| 合规 | ❌ 明文禁止 | ❌❌ 逆向 + 规避保护措施 | ⚠ 灰区（规避技术措施） | ✅ 用自己后台的正常功能 |
| 失手后果 | 微信账号 | **个人微信账号（最重）** | 无账号风险 | 后台功能受限，可恢复 |
| 维护成本 | 高（随版本崩） | 极高（随版本崩） | 中 | 低 |

### 10.6 建议

1. **A、B 两条不做。** A 本机已死且与需求错配；B 风险落在个人微信号上，换不来新能力。
2. **C 只作人工兜底**，列进清单，不写进流水线。
3. 真正值得补的**不是**桌面自动化，而是"路线三"的成熟实现思路：
   `wechat-article-exporter`（约 **12.8k star**，2026-08 仍在更新）走的是
   「自己注册一个订阅号 + 后台接口」，并用**约 96 个 Cloudflare Worker 组成代理池**
   摊薄单 IP 风险去抓正文。这套「后台接口 + 代理池」比任何桌面方案都更贴合本项目
   现有的 CI 架构，且完全落在"用自己账号后台的正常功能"这个合规框架内。
4. **若将来确实要做 C**：不加 stealth 补丁、不碰 Frida/注入/多开、
   **绝不用主力微信账号**、有头模式 + 人工扫码 + 极低频，且只抓已知链接。

### 10.7 一句话

桌面自动化的吸引力在于"看起来像真人，所以不会被拦"。实测下来的真相是：

> **动微信客户端的两条路（A/B），本机版本已经死了，且红线最硬、后果最重；
> 不动客户端的浏览器路线（C）只能补单篇正文，拿不到列表，也进不了 CI。**
>
> 它补的是"最后一公里"，而本项目缺的是"第一公里"。合集那条零凭据链路
> （第 4 节）在这两点上都更好 —— 所以**不必为了「模拟真人」付出账号代价**。

## 11. 让大模型「看屏幕 + 点鼠标」（视觉驱动的 GUI 智能体）——可行性评估

> 这是第 10 节想法的升级版：不用写死脚本，而是**让多模态大模型看截图、
> 自己想下一步点哪里**，再通过模拟鼠标键盘执行。业内叫 Computer Use / GUI Agent。
>
> **结论先行：技术完全成立，2026 年已经算成熟；但对本项目不建议。**三个理由：
>
> 1. **它没有绕开风险，反而有一个决定性反例**——大厂真做过这件事，结果是微信账号被**强制下线**；
> 2. **成功率数据不支持「批量」**——单步点击定位 94%，但**完整的百步任务只有 42.5%**；
> 3. **它多出一个原方案没有的风险面**——大模型要看的是**整块屏幕**，屏幕上有你的聊天记录。
>
> 但它留下一条**真正有价值的副产品**，见 11.5、11.6 —— 那才是这条路线里值得留下的东西。

### 11.1 技术是成立的：这条路确实成熟了

不能拿"模型看不懂界面"当理由否掉它。以开源的代表作 UI-TARS 系列公布的基准成绩为例：

| 基准 | 测什么 | UI-TARS-1.5 | OpenAI CUA | Claude 3.7 |
|---|---|---|---|---|
| ScreenSpot-V2 | 单步 GUI 元素**定位** | **94.2** | 87.9 | 87.6 |
| ScreenSpotPro | 复杂界面定位 | **61.6** | 23.4 | 27.7 |
| OSWorld（100 步） | **完整桌面任务**完成率 | **42.5** | 36.4 | 28.0 |
| Windows Agent Arena（50 步） | 完整任务完成率 | 42.1 | — | — |
| OSWorld（UI-TARS-1.5-**7B** 开源小模型） | 完整任务完成率 | 27.5 | — | — |

它**不依赖坐标硬编码**：认得"那个带软盘图标的蓝色矩形是保存"，位置挪 20 像素也照样点得中；
遇到窗口失焦、权限弹窗也有重试与降级机制。所以**第一步的可行性判断是：能做。**

问题全在后面。

### 11.2 决定性反例：大厂做过了，微信账号被强制下线

这是本次查证里最重要的一条，它把"模拟真人所以不会被拦"这个前提直接推翻了：

> **2025 年 12 月**，搭载豆包手机助手的工程样机上市。用户用它**自动操作微信**时，
> 出现**微信账号被强制下线**；淘宝与部分银行 App 也出现登录或支付受限。
> 随后**豆包下线了"操作微信"的功能**，并说明遇到支付、身份验证等环节会暂停、由用户接管。
> （来源：澎湃新闻 2025-12-03；虎嗅 2025-12）

请注意这个案例的性质——它**恰好就是本节讨论的方案**：

| | 豆包手机助手 | 你要做的事 |
|---|---|---|
| 技术手段 | 视觉理解 + 模拟点击 | 视觉理解 + 模拟点击 |
| 是否 Hook / 注入 / 改客户端 | **否** | **否** |
| 是否"模拟正常人操作" | **是** | **是** |
| 结果 | **账号被强制下线，功能被下线** | ？ |

**所以"因为不涉及协议破解，所以没有封号风险"是厂商话术，不是事实。**
社区里确实有文章这么写（"用 CUA 操作微信最大的好处是没有封号风险"），
也有商业软文自称"非侵入式、全合规"——但公开可查的真实案例是**掉线**。
判断这类说法时，看案例不看宣传。

**规范层面也要澄清一个常见误解**：《微信个人账号使用规范》1.2.6 禁止的是
"通过非腾讯开发授权的第三方软件……**进行自动化操作**，对微信软件及其组件、模块、**界面**、数据进行访问、读取或控制"。
它禁止的是**"自动化操作"这个行为**，不是"某种技术实现"。
**VLM 方案不会因为"更像人"就不再是自动化操作——它恰恰是最字面意义上的自动化操作。**

### 11.3 成功率数据不支持"批量"这个用法

把 11.1 那张表换个角度读，结论立刻变了：

| 观察 | 数字 | 含义 |
|---|---|---|
| 单步定位 | 94.2% | 看得准 |
| **完整任务（100 步）** | **42.5%** | **跑不完** |
| 完整任务（50 步） | 42.1% | 同上 |
| 7B 开源版完整任务 | 27.5% | 更差 |

而你要的这条任务链，**每一步都要模型重新看一张截图、想一次、点一次**：

```
打开微信 → 点搜索 → 输入公众号名 → 等结果 → 点进公众号
  → 找到「历史消息」/ 合集入口 → 滚动列表 → 逐篇点开
  → 点「…」→ 选「复制链接」/ 分享 → 回到列表 → 下一篇 …
```

这是 **20~30 步 / 篇**，不是一次调用。按 42.5% 的完整任务成功率折算，
**单篇跑通概率大约四成**，失败要人工介入；而且每步 1.2~1.8 秒延迟
（UI-TARS-2 实测 1200 ms），加上重试，**一篇要 1~3 分钟**。

**对照一下现有链路做同一件事的代价：**

| | GUI 智能体 | 合集接口（第 4 节） |
|---|---|---|
| 拿 10~20 条链接 + 正文 | 20~30 步 × N 篇，约 40% 成功率 | **1 次 HTTP 请求** |
| 耗时 | 每篇 1~3 分钟，还要人工救 | **< 1 秒** |
| 成本 | 每步一次多模态推理（token 计费） | **0** |
| 失败模式 | 视觉幻觉、列表滚动错位、弹窗 | 无 |
| 风险 | **账号** | 无 |

**用最贵的方式做最窄的事**——这就是本节的整体判断。

### 11.4 一个原方案没有的风险：屏幕本身就是数据

Computer Use 有一个脚本方案没有的特殊风险，Anthropic 在官方文档里专门提示过：

- **它会读取屏幕上的所有内容。** 截图上传给模型时，画面里不只是微信界面——
  还有弹出的聊天消息、系统通知、后台开着的文档与浏览器标签页。
  **这些会一并离开你的机器。**
- **提示注入。** 屏幕上的文字（网页、图片、聊天消息里的内容）都可能被模型当作"指令"，
  覆盖你原本的意图。Anthropic 明确建议：在**权限最小的专用虚拟机或容器**里跑。
- 豆包那个案例的另一半也值得注意：它最后选择**主动下线操作微信的功能**，
  并在支付、身份验证等环节改为暂停交还给人——这是目标平台风控给出的实际边界。

对本项目来说，"为了拿几个链接，把整块屏幕送出去"这笔账本身就不划算。

### 11.5 ⭐ 但它留下一条真正有价值的副产品

前面都在否。但这条路线里**有一点是真的有用**，值得单独拎出来：

**微信客户端"复制链接"给出的通常是短链**：`https://mp.weixin.qq.com/s/<token>`。

而短链**恰恰是能抓的**——第 9.3 节那次受控对照（同一条文章的三种链接形式）：

| 链接形式 | 结果 |
|---|---|
| **短链** `/s/XLsEsQOyo4qwtekckfDT2A` | ✅ **3.73 MB，正文完整** |
| 长链带 `chksm` | ✅ 3.59 MB |
| 长链缺 `chksm`（往期回顾那种） | ❌ 17 KB 验证码墙 |

也就是说：**这堵墙的出口不是"让模型点鼠标"，而是"拿到短链"。**
只要链接是从客户端"复制链接"出来的短链，现有 `fetch_html()` 直接就能抓正文——
**根本不需要 GUI 智能体那一整套东西。**

> 📌 **需要你花 30 秒验证一次**（这是唯一需要你动手的地方）：
> 在微信 PC 端打开任意一篇公众号文章 → 点右上角 `…` → 复制链接 →
> 看剪贴板里是 `mp.weixin.qq.com/s/xxxx`（短链，可用）
> 还是 `mp.weixin.qq.com/s?__biz=…&mid=…`（长链，要确认是否带 `chksm`）。
> 这一步决定 11.6 那个方案值不值得做。

### 11.6 最优解：把「点鼠标」这一步交回给人

既然墙的出口是"拿到链接"，而**让人自己点两下微信完全合规**，那么最合理的形态是：

```
人工：在微信里点开文章 → 「…」→ 复制链接        ← 两下，合规（这是你自己的正常使用）
   ↓
脚本：监听剪贴板 → 发现 mp.weixin.qq.com → 抓正文 → 去重入库
```

**本机能力实测**：`Get-Clipboard` / `Set-Clipboard` **可用** ✅
（`tesseract` / `magick` / `nircmd` / `AutoHotkey` 均未安装——但这方案一个都不需要。）

**为什么它的合规性质和 VLM 方案完全不同：**

| | 人工 + 剪贴板 | GUI 智能体 |
|---|---|---|
| 谁在操作微信 | **人**（用户本人的正常使用） | **第三方程序**（规范 1.2.6 的"自动化操作"） |
| 屏幕内容是否外传 | **否** | **是**（整块屏幕） |
| 失败代价 | 无 | **账号**（豆包案例） |
| 工程成本 | 几十行（读剪贴板 + 复用现有抓取） | 视觉模型 + 动作执行 + 重试编排 |
| 每篇人力 | 点两下 | 0（但要盯着救 60% 的失败） |

**关键区别在于：用户自己动手操作微信，是允许的；让程序替他操作，才是被禁止的那件事。**
"省下的那两下点击"换不来一个账号。

### 11.7 结论

| 问题 | 回答 |
|---|---|
| 技术上能不能做？ | **能**，而且 2026 年已经成熟（定位 94%、有开源实现） |
| 该不该做？ | **不该。** 有大厂实测掉线的反例；完整任务成功率仅 42.5%，撑不起批量 |
| 它比脚本方案更安全吗？ | **不。** 规范禁的是"自动化操作"这个行为，不是实现方式 |
| 那"从客户端拿链接"这条路是不是死的？ | **不是。** 出口是**短链**（短链可抓），实现方式是**人工复制 + 脚本读剪贴板** |
| 建议 | 不做 GUI 智能体。若要人工兜底，就做 11.6 那个几十行的剪贴板助手 |

一句话：**GUI 智能体解决的是"没有接口时怎么操作界面"，而本项目的问题从来不是"操作不了界面"，
而是"批量、无人值守、不能赔上账号"。前者的长处在这里一项都用不上，后者的每一条都踩中。**

## 12. 「有手有眼的实体机器人坐在电脑前」——可行性评估

> 这是第 11 节思路的物理化终点：**机械臂当手、摄像头当眼睛**，
> 让一台机器人真的"坐"在电脑前点鼠标、敲键盘，去微信里搜索并分享文章、取链接。
>
> **结论先行：这个思路在业界有正经先例，不是异想天开——Selenium 的作者真的造过这种机器人，
> 而且至今在被医疗设备公司和测试公司使用。但它在这里不成立**，原因是一个很漂亮的悖论：
>
> **机器人最大的卖点（不知疲倦、动作高度一致），恰恰是行为风控最容易识别的特征。**
> 反作弊领域十几年得出的结论是：**风控检测的是"输入的熵值"，不是"输入的来源"。**

### 12.1 先承认：这不是异想天开，业界真有这个东西

**Tapster**（tapster.io）——由 **Selenium / Appium 的作者 Jason Huggins** 创办，
做的是鞋盒大小的机器人，用机械手指去点真实手机的屏幕。它存在的理由是硬的：

| 为什么需要这种机器人 | 说明 |
|---|---|
| **自动化"你不拥有、也没写过的 App"** | iOS 的自动化 API 极封闭，**无法**自动化别人的 App——这时只有机器人能做 |
| 测真实环境交互 | 真实传感器、触屏延迟、与物理世界联动（POS 机、开灯、开车门） |
| 设备认证 | 手机厂商与运营商用它做真机的认证测试 |
| 一致性 | 官方表述："Robots work like a human, **but don't get tired**" |

有医疗设备公司（Orthogonal）用它做医疗器械软件测试，
也有测试外包公司（TestDevLab）自己 3D 打印了一台（取名 "Tappy"）。
**所以"让机器人替我操作电脑"是被严肃验证过的工程方案——这一点必须先承认。**

### 12.2 但它的存在理由，恰好是本项目不具备的

把上表逐条对照本项目：

| Tapster 需要机器人的理由 | 本项目的情况 |
|---|---|
| App 没有可用的自动化接口 | **有**——公开合集接口零凭据可用，一次拿 10~20 条带 `chksm` 的链接 |
| 要测真实传感器 / 物理交互 | 不需要，抓的是网页文本 |
| 要自动化"别人的封闭 App" | 公众号文章**本身就是网页**，有 HTTP 出口 |
| 要每次执行完全一致（回归测试） | 本项目要的是**遍历未知数量**的文章，是采集，不是回归测试 |

**机器人解决的是"根本没有接口时怎么办"。而本项目的问题从来不是没有接口。**

### 12.3 ⭐ 那个悖论：机器人的优点，正是风控要找的特征

这是本节最值得记住的一点。游戏反作弊领域早已把"物理外挂"（玩家用真硬件、但自动操作）研究透了：

| 检测维度 | 真人操作 | 宏 / 自动化 |
|---|---|---|
| 移动轨迹 | 细微抖动、拐点自然，无绝对直线 | 完美直线或固定曲线 |
| **点击间隔标准差** | **> 15 ms** | **< 5 ms** |
| 加速度 | 随场景动态变化 | 全程恒定 |

反作弊方的原话（ESP 公开的四维防御体系）：

> **"反作弊系统并不关心你的鼠标驱动是否经过了'物理模拟'伪装，它只关心一件事：输入序列的熵值。"**
> "**无论你使用的是什么硬件，都会被标记为异常。**"
> "当你的操作逻辑超越了生理随机性，任何硬件驱动都无法成为你规避封禁的护身符。"

现在再读一遍 Tapster 的卖点：

> "Robots will **consistently** perform the same actions. **Without the constraints of a workday or lunch breaks**,
> robots reduce variability in testing."

**这是同一件事的两种说法。** 对测试工程师，它是"消除变异"；对风控系统，它是"低熵、非人类"。

更微妙的是：机械臂的误差是**系统性误差**——同一个动作重复 100 次几乎完全一致；
而人类是**随机生理抖动**。所以**机械臂在熵值维度上比软件脚本还要醒目**，
因为它把"一致性"做到了极致。

游戏侧的实测数据也吻合：硬件模拟类脚本的检测周期是 **3~14 天**，
且"操作异常度"（历史行为突变）与"举报量级"会显著加速触发。

**所以：机器人能骗过客户端软件层的检测（Tapster 已经证明了这一点），
但对行为层的风控完全无效。而微信的账号级限流与"强制下线"，恰恰发生在行为这一层。**

### 12.4 物理层还有它自己的代价

| 项 | 软件截图 + 模拟点击 | 机器人（摄像头 + 机械臂） |
|---|---|---|
| 视觉输入 | 屏幕像素直读，无损 | 摄像头拍屏：**摩尔纹、反光、色偏、几何畸变**，比截图更差 |
| 单次点击耗时 | 约 10 ms | **1~3 秒**（移动 + 下压 + 回位），慢 100~300 倍 |
| 精度稳定性 | 像素级，无漂移 | 需标定；温度、震动、机械间隙导致**漂移**，要定期重标 |
| 工作空间 | 无限制 | 必须覆盖本机 **3072×1920** 的屏幕范围，精度要求高 |
| 成本 | 0 | 可用级机械臂 **¥8k~20k**，外加几十到上百小时工程 |
| 本机现状 | 已具备 | 实测：**无任何串口 / COM 口设备**；只有笔记本内置摄像头 |

考虑到 11.3 节那条已经存在的结论——**完整 GUI 任务成功率只有 42.5%**，
而机器人把视觉输入质量**进一步降低**（拍屏 ≠ 截图）、把单步耗时**放大 100 倍**，
成功率只会更低、更慢。

**用一个小型机器人工程项目，去替代一行 `pyautogui.click()`，而且做得更差。**

### 12.5 规范定性：一个字都没变

《微信个人账号使用规范》1.2.6 禁止的是：
"通过非腾讯开发、授权的第三方软件、插件、外挂、**系统**等……**进行自动化操作**，
对微信软件及其组件、模块、**界面**、数据进行访问、读取或控制。"

**它约束的是"自动化操作"这个行为，不是"用什么装置执行"。**
机械臂仍然是"非腾讯授权的第三方系统"在执行自动化操作。换了执行装置，条款一个字都没变。

> 类比：用机械臂替你按电梯按钮，电梯当然检测不到——但如果物业规定"不许代按"，
> 它仍然是被规定约束的行为。**"检测不到"和"被允许"是两件事。**

### 12.6 顺带说清一个便宜 100 倍的中间形态

如果真正的诉求是"让输入来自真实硬件"，那**不需要机械臂**：
一个 **USB HID 设备**（树莓派 Pico / Arduino 伪装成键鼠）产生的是**完全真实的 HID 报文**，
操作系统与微信看到的就是一个正常的鼠标键盘。成本约 ¥50~200，速度比机械臂快 100 倍。

但它同样不行，而且理由和前两条一样：

1. 仍落在 1.2.6 的"第三方系统进行自动化操作"里；
2. 在游戏领域它正是重点打击对象，检测手段就是 12.3 那套**行为熵分析**；
3. 最根本的——**它同样不解决成功率（42.5%）和"第一公里"（拿列表）的问题。**

### 12.7 结论

| 问题 | 回答 |
|---|---|
| 技术上能不能做？ | **能。** 业界有成熟先例（Tapster，Selenium 作者所做） |
| 为什么别人做、我们不做？ | 那个先例的动机是"**App 根本没有接口**"；本项目有零凭据接口 |
| 它最大的优点是什么？ | 不累、动作完全一致——**而这恰好是行为风控要找的特征** |
| 它比脚本更安全吗？ | 骗得过客户端检测，**骗不过行为层**；微信的限流正在行为层 |
| 规范上有区别吗？ | **没有**，禁的是"自动化操作"这个行为，不是执行装置 |
| 成本？ | ¥8k~20k + 上百小时，且比软件方案更慢、更不准 |
| 建议 | **不做。** 与其让机器人坐在电脑前，不如让**真人**坐在电脑前点两下 |

一句话：

> **这个方案的每一分努力，都花在"让操作看起来像人"上；
> 而真正卡住这条链路的两件事——"一次拿到一批链接"和"别被封号"——
> 它一件也解决不了：前者它比接口慢 100 倍，后者它连方向都不对。**
>
> 如果哪天真遇到一个"没有任何接口、且必须自动化"的封闭 App，
> 那时请回头看 Tapster——**那一刻它才是正确答案。**

## 13. 反例：pkuknow.cn 是怎么做到的（2026-10-19 实测拆解）

> 触发：一个反问 —— 「**为什么这个网站就能聚合公众号信息？**」
>
> 结论先说：**它没有特殊通道。它用的就是我们 `fetch_wechat.py` 里写的同一套接口。**
> 差别在「只抓最近 7 天 + 精选几十个号 + 每天一次」，而我们一直在追「全量历史」。

### 13.1 它的数据长什么样（实测首页）

| 指标 | 实测值 |
|---|---|
| 首页体积 | 173,416 字节（数据内嵌在 HTML 里） |
| 公众号账号数 | **24 个**（`source_id` 去重，全部 `wa_` 前缀） |
| 记录数 | **293 条**（`id` 去重） |
| 采集日期 | `collected_on` = 2026-10-12 ~ **2026-10-19**（**7 天窗口**） |
| 发布时间范围 | 2026-10-14 12:00 → **2026-10-19 21:40** |
| URL 形态 | **完整长链**，带 `__biz` / `mid` / `idx` / `sn` / **`chksm`** |
| 采集延迟 | 21:40 发布的文章，22:23 已被抓取 —— **约 43 分钟** |

**这是实时、自动、带完整参数的增量采集**，不是人工搬运。

### 13.2 字段里的三条线索：它有 LLM 后处理

单条记录的真实结构（节选）：

```json
{
  "requires_registration": true,
  "collected_on": "2026-10-19",
  "id": "wx_750dac122cc4562caec230bfbd762a6c",
  "source_id": "wa_10e5784ef8f2b18c0bef49c0c2b329f7",
  "source_name": "北大元培人",
  "title": "元气班团 | “蜡绘青春”手作沙蜡活动",
  "published_at": "2026-10-19T21:40:00+08:00",
  "url": "https://mp.weixin.qq.com/s?__biz=...&mid=...&idx=2&sn=...&chksm=...#rd",
  "category": "文体活动",
  "intent_group": "activity",
  "english": { "title": "...", "source_name": "PKU Yuanpei People" }
}
```

三个非抓取字段，暴露了它的加工层：

| 字段 | 含义 | 说明 |
|---|---|---|
| `requires_registration` | 是否**需要报名** | 从正文里判断出来的 —— **这正是学生最关心的** |
| `category` / `intent_group` | 分类 / 意图 | 「文体活动」「activity」 |
| `english` | 中英双语标题 | 机器翻译 |

### 13.3 它抓的是哪些号：全是学生组织

实测到的 24 个号（`source_id` 去重后的中文名）：

> 北大元培人 · 北京大学招生办 · 北大音乐剧社 · 化学你我 · 元火动漫社 · 北京大学学生会 ·
> 信风 · 北大史学人 · 北大团委 · 爱徒步的PKUer · 北大猫协 · 北大山鹰社MAPKU · 北大哲学人 ·
> 北京大学爱心社手语分社 · 北京大学百周年纪念讲堂 · 北京大学研究生会 · 北大铁协 · 工映青春 ·
> PKU医预之家 · 大信科 · 北大心理人 · 荣药青年 · 爱心驿站 · PKU言之有物

**没有任何一个是「校新闻网」那种宣传号** —— 全是院系、学生会、社团、讲座场馆。
**这正是「学生活动」的发布源。** 它选题就选对了。

### 13.4 底层原理：同校开源工具把话说透了

北大有个开源 CLI `pkuinfo/pkucli`，其中的 `info-spider` crate 的源码注释原文：

> **工作原理：登录 mp.weixin.qq.com 后台 → 新建文章 → 超链接面板 → 搜索公众号 → 列出文章。**
> **全过程模拟正常用户点击顺序，最大限度贴近真人行为，降低被风控的概率。**

对应的命令：

```
info-spider login                # 微信扫码登录公众号后台
info-spider search "人民日报"     # 搜公众号，拿 fakeid
info-spider articles --name "X"  # 按 fakeid 翻页列文章
info-spider scrape <url>         # 单篇转 Markdown
```

关键点：**auth 是「自己的订阅号后台扫码登录」，不是个人微信 cookies。**
访问路径是「编辑文章时插入超链接」这个**后台正常功能**——所以它不是爬虫对抗，是**用后台自带的能力**。
配合 `--delay-ms`（默认 1500ms + 0~50% 抖动）压低频率。

> ### ⚠️ 2026-10 修正（已被外部多源证实：接口层面封禁，不只是入口收起）
>
> 上面这段成立的前提已经**不存在了**。2026-07-30 前后，微信把公众号后台
> 「跨公众号文章列表」这条链路（`searchbiz` 搜号 + `appmsgpublish`/`appmsg`
> 列文章）在**接口层面**封掉了——不是只对个人主体收起入口，而是所有主体一起没。
> 佐证（均为 2026-07~10 的一手材料）：
>
> - `rachelos/we-mp-rss` issue #442（2026-08）的工具清单明确标注：
>   **「公众号后台超链接接口方案 —— Caution 2026.07.30 官方已封」**，
>   同时注明该方案「每 2-3 天需重新扫码登录」
> - 1.2 万星的 WeChat Article Exporter（走同一条后台接口）2026-07-30 停止维护，
>   线上版域名只开到 10-30（techmoon 报道）
> - `ret=200013` 在同期的多份独立故障报告里语义已变：
>   同一登录态「搜索成功但列表必失败」（lovstudio 对微信编辑器现网代码的分析），
>   即**列表能力被单独收回**，不是频控误伤
> - 本项目 2026-10-19 用 `tools/dev/probe_wx_perm.py` 试跑时，
>   既有 cookies 本身已过期（首页被踢回 `loginpage`），未能直接测出边界，
>   但外部证据已足够定论，不再为验证而消耗账号
>
> **结论：pkucli `info-spider` 的 `search` / `articles` 两条命令在现网已无实际用途**
> （`scrape` 单篇转 Markdown 仍可用）。第 13.7 的复刻计划随之作废，
> 「用后台自带能力」这个说法请不要再引用。


### 13.5 关键事实：我们其实一直在同一条路上

`fetch_wechat.py` 第 15 行的模块注释，写的是：

> `wxmp` 走的是**公众平台后台**接口（`searchbiz` 搜号 + `appmsg` 拉历史文章列表）

`docs/wxmp公众号接入.md` §3 写的取凭据方式：

> 用浏览器登录 <https://mp.weixin.qq.com/>（**自己注册一个订阅号即可，无需粉丝**）

代码里的调用（`fetch_wechat.py`）：

```python
def search_biz(self, query, begin=0, count=10):      # action=search_biz
def list_articles(self, fakeid, begin=0, count=5, ...):  # action=list_ex
```

**同接口、同凭据体系、同 auth 流程。** 我们的名单里也早就有「学生会 / 团委 / 学生处 / 灵韵音乐剧社 / 星弦幻协 / 魔协」。

### 13.6 那为什么我们没做成？三处差异

| 维度 | pkuknow.cn | 本项目 |
|---|---|---|
| **抓取范围** | 最近 **7 天**（`collected_on` 只有 7 个日期） | 每号 `--count 15` × `--pages 3`，且想覆盖三校 |
| **账号数** | **24 个**（单校，且是精选学生号） | 3 校 40+（含大量官方宣传号） |
| **运行状态** | 每天 1 次，线上稳定 | **默认关闭**（README：「不再抓公众号内容」） |
| **环境就绪** | 已跑通 | **`wxmp` 库本机未安装**（实测 `No module named 'wxmp'`） |
| **后处理** | LLM 分类 + 报名标记 + 翻译 | 无 |

**真实原因是三条叠加，不是单一技术障碍：**

1. **量定得太大** —— 追「每号翻到底」才会撞上 `ret=200013`，而它只要最近几天的新文章
2. **开关是关的** —— 为了让站点"只抓官网"，把 `WECHAT_ACCOUNTS` 置空了
3. **依赖没装** —— `wxmp` 库从未在本机安装，API 模式从没真正跑通过

### 13.7 修正后的结论

**前面第 10~12 节否掉的是「绕过接口」的路（桌面自动化 / GUI 智能体 / 机械臂），那些结论仍然成立。
但「走后台接口」这条路——从来没被否掉，只是被关掉了，而 pkuknow 是它跑得通的活证明。**

> 补一句前提：这条路要求登录账号**在后台能看到「选择其他公众号」**。
> 若 13.4 的修正块被实测证实（个人主体已无此入口），则「换认证主体号」是唯一出路，
> 或者把公开合集升为主路。别在个人号上反复试。

要复刻它的形态，需要四件事（**都不需要新技术**）：

| 步骤 | 做什么 | 障碍 |
|---|---|---|
| 1 | `pip install wxmp` | 无 |
| 2 | 扫码登录自己的订阅号后台，导出 cookies 到 `_work/wechat/wxmp-cookie-header.txt` | **需要用户本人扫码**（AI 不能代做） |
| 3 | 名单换成「院系 + 学生组织 + 社团」为主，砍掉新闻网类 | 改 `wxmp-accounts-<校区>.json` |
| 4 | **降量**：每号只取最近 3~5 篇，每天跑 1 次 | 改 `--count 3 --pages 1` |

**再加一步就能追上它的体验**：给条目补 `requires_registration`（是否需报名）和分类 ——
这一步用现成的 LLM 就能做，不需要碰微信。

> 一句话：**它做到的事，我们的代码结构已经支持；差的是一次「装上、扫码、降量、换名单」。**
