# 目录结构与「三条链路」的分界

本项目同时抓三类信息源，它们的**稳定性差别很大**，所以在代码和磁盘上都是**完全分开**的：

| 链路 | 抓什么 | 稳定性 | 脚本 | 产物位置 |
|---|---|---|---|---|
| **官网链路**（稳定） | 官网 / 新闻网 / 通知公告 / 职能部门 | **稳定**：20 个源长期 `failed=0` | `fetch_campus.py`（+ `refresh.py --build-only` 建站） | `_work/`（根下） |
| **公众号链路**（不稳定） | 微信公众号历史推文 / 正文 | **不稳定**：受微信**账号级限流** `ret=200013` 影响，可能整轮拿不到东西 | `fetch_wechat.py` | `_work/wechat/` |
| **公开合集链路**（较稳定） | 公众号**公开合集**（作者手工整理的专题） | **较稳定**：零凭据、不调 `appmsg`，因此不受账号限流；但覆盖范围只限合集内文章 | `python -m albums`（`albums/` 包） | `_work/albums/` |
| **公开链接链路**（看天吃饭） | 文章页之间的链接网 + 搜狗微信搜索 | **不稳定**：搜狗会反爬；搜狗来源拿不到永久链接 | `python -m links`（`links/` 包） | `_work/links/` |

为什么分开：官网源失败是**个别站点**的问题（换地址即可）；公众号失败是**账号维度**的问题
（新登录/久未使用的公众平台账号要等数小时至 1 天）；合集失败是**单个合集**的问题
（`__biz`/`album_id` 失效而已）。把文件分开后：

- 清 `_work/` 不会碰到 cookies / 名单 / fakeid 缓存；
- 备份、排查、迁移任一条链路时互不牵连；
- 一眼就能看出"哪堆文件属于哪条链路"。

**三条链路最终都只往同一份 `data/<校区>.json` 里追加**（按 `i` 去重、90 天保留期），
所以**页面是合一的**，只是数据来源分开管理。注意合集链路**自己不写 `data/`**：
它只产出 `_work/albums/`，要入站必须显式 `python -m albums export` 再合并
（理由见 [albums/README.md](../albums/README.md)）。

## 一、顶层布局

```
university-know/
├── index.html                 ← 成品站点（首屏只内嵌轻量索引，正文按需取）
├── template.html              ← 页面模板（含 __NOTICE_DATA__ 占位符）
│
├── refresh.py                 ← 建站：把 data/*.json 拆成「轻量索引 + 按需分片」（也保留 pkuknow.cn 上游接口能力）
├── fetch_campus.py            ← 官网链路：浙大/上交/西交的官网 + 职能部门
├── fetch_wechat.py            ← 公众号链路：微信公众平台后台接口（wxmp）
├── albums/                    ← 公开合集链路：独立包，`python -m albums`（零凭据/零第三方库）
├── links/                     ← 公开链接链路：独立包，`python -m links`（种子/页内关联/搜狗）
├── cloud_update.py            ← 无人值守统一入口（默认只跑官网，--with-wechat 才跑公众号）
│
├── data/                      ← 三条链路的**共同**产物：合并后的 JSON（页面数据源）
│   ├── zju.json  sjtu.json  xjtu.json      ← 清华知道为外链，不落数据
│   ├── shard/                 ← 按需加载分片（refresh.py 自动生成，随页面一起部署）
│   │   ├── <校区>.json        ← 该校区全量：切到它时按需加载
│   │   └── <校区>-d.json      ← 详情增量：点开某条通知时才加载（正文/地点/主办）
│   └── *.json.bak             ← 每次覆盖前自动留的上一版（写入保护）

├── _work/                     ← 官网链路的中间产物（可整个删掉重建）
│   ├── items-<校区>.json      ← fetch_campus.py 的抓取结果（入库前可检查）

│   ├── albums/                ← ★ 公开合集链路专属目录（见下）
│   ├── links/                 ← ★ 公开链接链路专属目录（台账，整体 gitignore）

│   ├── unit_fetch.py          ← 标题/日期/正文抽取
│   ├── pipeline_test.py       ← refresh.py 写入保护与合并
│   ├── unit_wechat.py         ← 公众号名单/缓存/迁移
│   ├── test_handler.py        ← 云函数 handler 端到端（mock OSS）

│   ├── test_albums.py         ← 公开合集链路的离线单测（解析/分页/增量/分类对齐）
│   ├── test_links.py          ← 公开链接链路的离线单测（转义还原/可抓性/搜狗解析/台账）
│   ├── test_login_flow.py     ← 扫码登录 7 步受控演练（本地假后台，不联网）

├── tools/
```

### `_work/wechat/` —— 公众号链路的全部家当

```
_work/wechat/
├── wxmp-cookie-header.txt     ← ★ 登录后的 Cookie 整行（推荐这种写法，零转录错误）
├── wxmp-cookie-header-<校区>.txt  ← 可选，分校区版本（优先于全局）
├── wxmp-cookies.json          ← 老格式：JSON {"wxuin": "...", "slave_sid": "..."}
├── wxmp-token.txt             ← 可选：手动指定 token（自动取不到时用）
├── wxmp-accounts-<校区>.json   ← 要抓的公众号**完整昵称**名单（外部维护，不改代码）
├── wxmp-accounts.json         ← 全局名单（所有校区共用）
├── wxmp-fakeid.json           ← fakeid 缓存：锁定公众号后不再依赖搜索（可安全删）
├── wechat-<校区>.txt           ← 公开种子链接清单（一行一条，# 开头是注释）
└── wechat-items-<校区>.json    ← 抓取中间产物（--no-import 时的落点）
```

### `_work/albums/` —— 公开合集链路的全部家当

```
_work/albums/
├── state.json                 ← 增量水位（每个合集抓到哪个 msgid）+ 已见文章 key（可删：删了下次全量重抓）
├── discovered-<校区>.json     ← 从种子文章页 / 搜狗开页挖到的合集（**入库**：重挖要几十次 3.5MB 请求）
├── albums-<校区>.json         ← 抓取产物：合集元信息 + 文章列表 + 每个合集的健康状态（累计，不会被增量轮覆盖掉；**不入库**，fetch 一分钟重建）
└── site-<校区>.json           ← `export` 导出的站点 item 结构（纯派生，可删）
```

与 `_work/wechat/` 的关键差别：这里**没有任何凭据**，删掉整个目录最多损失一次抓取时间，
不会丢 cookies / 名单 / fakeid。它读 `_work/wechat/wechat-<校区>.txt` 里的种子链接（只读），
但**不写**该目录。

### `_work/_archive/` —— 旧备份归档

`_bak_1011/`、`_bak_1014/` 这类手工备份目录已压成 `_work/_archive/bak-*.tar.gz` 留档
（`_bak_*/` 与 `_work/_archive/` 都在 gitignore 里）。要追溯到某一轮的历史快照时解包看，
不再让它们占着仓库根目录。

### `_work/links/` —— 公开链接链路的台账

```
_work/links/
├── library-<校区>.json        台账：A 档（有永久链接）/ B 档（只有标题/号/日期）
├── report-<校区>.json         统计：每校区多少篇、每个发布者多少篇、时间跨度
├── albums-found-<校区>.json   从文章页挖到的合集（与 albums 的发现清单同步）
└── publishers-<校区>.csv      发布者表格（report --csv 生成）
```

这一层与 albums 的关系是**数据交接**而非代码依赖：

```
links harvest ──写──▶ _work/albums/discovered-<校区>.json ──读──▶ albums fetch
albums fetch  ──写──▶ _work/albums/albums-<校区>.json     ──读──▶ links harvest
```

> **旧布局兼容**：早期版本把上面这些文件直接放在 `_work/` 根下。首次运行
> `fetch_wechat.py` 时会**自动迁移**到 `_work/wechat/`（不覆盖新位置已有文件），
> 并且读取时仍会**回退**看一眼旧位置，所以升级不会丢 cookies / 名单 / 缓存。

## 二、哪些文件是"生成物"，哪些是"手工文件"

| 类别 | 文件 | 能不能删 |
|---|---|---|
| **成品** | `index.html` | 删了跑 `python refresh.py --build-only` 重建 |
| **数据** | `data/*.json` | **不能删**（是历史基线）；`*.json.bak` 可删（只是上一版备份） |
| **官网中间产物** | `_work/items-*`、`_work/registry-*`、`_work/run.log` | 可删，跑一次 `fetch_campus.py` 重建 |
| **公众号中间产物** | `_work/wechat/wechat-items-*`、`wxmp-fakeid.json` | 可删（fakeid 会重新搜索） |
| **合集中间产物** | `_work/albums/*` | 可删（重跑 `python -m albums fetch` 重建，约 1 分钟） |
| **链接台账** | `_work/links/*` | 可删（重跑 `python -m links harvest` 重建，几十分钟；已在 gitignore） |
| **合集清单** | `albums/albums.json` | **不能删**（手工维护的校区归属；自动发现的部分在 `_work/albums/discovered-*`） |
| **公众号凭据/名单** | `_work/wechat/wxmp-cookie-header.txt`、`wxmp-accounts-*.json`、`wechat-<校区>.txt` | **不能删**（手工维护；删了要重新登录/重写名单） |
| **官网补充源** | `_work/sources-<校区>.json` | **不能删**（手工维护；本项目当前还没有这个文件） |
| **模板** | `_work/sources.example.json` | 可删（纯参考，不被加载） |
| **测试** | `tests/*.py` | **不能删**（回归基线，改完代码先跑） |
| **留档** | `build/reports/*`、`tools/oneshot/*` | 可删（仅追溯用） |

## 三、三条链路怎么各跑各的

```bash
# 官网链路（稳定，日常就靠它）
python fetch_campus.py                # 浙大/上交/西交
python refresh.py --build-only        # 不联网，用 data/*.json 重建页面
python cloud_update.py                # 抓取 + 重建，一条命令搞定，只输出摘要

# 公众号链路（不稳定，按需跑）
python fetch_wechat.py                # 用 wxmp 按号抓（需 cookies）
python fetch_wechat.py --campus zju   # 只抓一个校区
python cloud_update.py --wechat-only  # 等价：只跑公众号这一步
python cloud_update.py --with-wechat  # 官网 + 公众号一起跑

# 公开合集链路（较稳定，零凭据；限流期也能跑）
python -m albums discover             # 从种子文章页发现合集（只需一次）
python -m albums list                 # 看已发现哪些合集、上次抓到哪
python -m albums fetch                # 增量抓（首次会自动先发现；每集翻到上次位置就停）
python -m albums fetch --all-pages    # 补历史：翻到合集末尾
python -m albums check                # 自检：接口还通不通、字段还在不在
python -m albums export --campus zju  # 产出站点 item 结构（本包不写 data/）

# 公开链接链路（看天吃饭：搜狗会反爬；能发现新号，但多数只有元数据）
python -m links harvest --all               # 合集 + 种子 + 搜狗元数据
python -m links harvest --all --probe-albums 20   # 开页挖合集（高杠杆，随后要跑 albums fetch）
python -m links report  --all --top 20      # 有多少篇、发布者都有谁
python -m links export  --all --merge      # 接进站点：并入 data/<校区>.json（写前留 .bak）
python refresh.py --build-only             # 重建 index.html + 分片
```

**合集侧有一条时效门槛**：`albums/albums.json` 的 `max_age_days=60` ——
只看最近 60 天内有更新的合集（判据是合集里最新一篇的发布日期，不是上次抓取时间）。
过期合集不翻页、不收文章、历史条目也会被清掉，`links` 的台账跟着同步清理。
要临时放开：`python -m albums fetch --max-age-days 0`。

**云端每日三次的定时任务里已经包含合集增量**（`.github/workflows/update.yml` 的 build job）：
`python -m albums fetch --all`（增量，三校约 10 秒）→
`python -m links harvest --all --no-sogou --no-seeds` → `python -m links export --all --merge`。
水位文件 `_work/albums/state.json` 走 `actions/cache`，**不入库**（它含 `last_run`，每轮必变）；
种子页与搜狗不进定时任务（3.5MB/页、会被反爬），仍由人工按需跑。

`cloud_update.py` 默认**不跑公众号**（`--with-wechat` 才跑），原因见
[无人值守更新部署.md](无人值守更新部署.md) 第一节：cookies 是凭据、wxmp 有依赖、
云函数无持久盘。**推荐官网走云端、公众号留在本机。**
