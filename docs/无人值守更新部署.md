# 无人值守更新部署（电脑关机也能更新站点）

> 本文合并了原先分散的三份文档（`无人值守更新部署.md` / `Serverless函数计算部署.md` /
> `云端定时更新方案.md`）。它们讲的都是同一件事——**让站点自动更新**——只是调度位置不同，
> 分开写会互相矛盾。现在统一在这里，按「先选路子 → 再照着做」组织。

## 零、先选一条路

| 调度位置 | 电脑关机时 | 碰得到本机 `E:/project/thu-know` | 成本 | 要写代码吗 |
|---|---|---|---|---|
| **本机 WorkBuddy 自动化**（现状） | ✗ 不触发 | ✓ | 0 | 不用 |
| **本机系统计划任务 / crontab** | ✓（机器不关就行） | ✓ | 机器电费 | 不用 |
| **云函数 FC / SCF + 对象存储** | ✓ 真 24/7 | ✗（维护云端那份） | **≈0 元**（免费额度足够） | 要（handler 已备好） |
| **WorkBuddy 云上模式定时任务** | ✓ | ✗ | **积分**，400/月远不够 | 不用 |

一句话：
- 要更新**本机这份**站点 → 走**方案 A / A+**（本机），或**方案 B**（常开机器）。
- 要站点**彻底脱离本机、成本接近 0** → 走**方案 C：云函数**（下方第五节，最推荐）。
- **不写代码**、能接受积分开销 → 走**方案 D：WorkBuddy 云上模式**（第六节）。
- ⚠️ **四条路只能选一条。** 各自维护一份 `data/*.json`，同时开会分叉出互不相干的历史。

> 🔴 **积分预警**：云上模式是一次 Craft 模式长任务，**单次约 30~200 积分**，
> 每天两次需要几千分/月。想零积分跑，优先看第五节（云函数）或方案 B（crontab）。

# 一、通用前提：项目是怎么组织的

不管走哪条路，都要先理解本项目**有两条抓取链路**，它们的稳定性差别很大：

| 链路 | 脚本 | 稳定性 | 产物位置 |
|---|---|---|---|
| **官网链路** | `fetch_campus.py`（浙大/上交/西交）、`refresh.py --build-only`（建站） | **稳定**（20 个源长期 `failed=0`） | `_work/`（根下） |
| **公众号链路** | `fetch_wechat.py`（wxmp / 公开种子） | **不稳定**（微信账号级限流 `ret=200013`） | `_work/wechat/` |

两条链路都只往同一份 `data/<校区>.json` 里**追加**（按 `i` 去重、90 天保留期），
所以**页面是合一的**，但任何一条断了都不影响另一条。目录也刻意分开，清理/备份/排查互不牵连。
详见 [目录结构.md](目录结构.md)。

`cloud_update.py` 是官方推荐入口：一条命令跑完抓取，把上千行进度收进 `_work/run.log`，
终端只留一段摘要（省日志、省 token）。**公众号这一步默认关闭**，要跑得显式加 `--with-wechat`。

```bash
python cloud_update.py                  # 抓三校（不跑公众号），重建 index.html
python cloud_update.py --with-wechat    # 再加上公众号（需本机有 cookies 与 wxmp）
python cloud_update.py --wechat-only    # 只跑公众号这一步
python cloud_update.py --summarize-only # 不抓取，只看现状摘要
```

> **为什么公众号默认不进云端**：① cookies 是账号凭据，不能长期放云上；② wxmp 依赖链
> （pydantic/pandas/requests）和「阿里云零依赖」冲突，要打 Layer；③ 云函数无持久盘，
> 存不住 `_work/wechat/wxmp-fakeid.json` 缓存。**推荐：官网走云端、公众号留在本机跑。**

# 二、方案 A：让本机保持在线（零成本，最省事）

适合「白天/晚上机器本来就开着」的情况：
1. 接通电源，关闭自动睡眠/休眠（笔记本还要处理"合盖休眠"）。
2. WorkBuddy 保持后台运行，账号不要退出。
3. 现有的两条自动化（每天 08:00 / 20:00）照用。

Windows 下关闭休眠与睡眠（管理员 CMD）：

```bat
powercfg /change standby-timeout-ac 0
powercfg /change hibernate-timeout-ac 0
powercfg /change monitor-timeout-ac 15
```

合盖不休眠：控制面板 → 电源选项 → 选择关闭盖子的功能 → 用电池 / 接通电源 均选「不采取任何操作」。

> 注意：WorkBuddy 的定时任务**没有"错过补跑"**。8:00 那一刻机器没开，这次就整个跳过了。

# 三、方案 A+：改成 Windows 任务计划程序（有"错过补跑"）

如果痛点是"早上开机晚于 8:00 就漏掉"，系统计划任务比自动化更稳：支持**错过即补跑**、**唤醒计算机**、**开机后触发**。

先在项目根目录建包装脚本 `update_site.bat`：

```bat
@echo off
cd /d E:\project\thu-know
set PY=C:\Users\Kevin\.workbuddy\binaries\python\envs\default\Scripts\python.exe
if not exist logs mkdir logs
"%PY%" cloud_update.py >> logs\update.log 2>&1
```

> 用 `cloud_update.py` 而不是分开跑 `refresh.py` + `fetch_campus.py`：它会统一收口重建页面、
> 只留一段摘要，日志不至于几千行。公众号要一起跑就加 `--with-wechat`（且这套 Python 里得装 wxmp）。

再用管理员 PowerShell 注册任务（每天 08:00 与 20:00 各一条，错过即补，并尝试唤醒）：

```powershell
$action  = New-ScheduledTaskAction -Execute "E:\project\thu-know\update_site.bat"
$set     = New-ScheduledTaskSettingsSet -StartWhenAvailable -WakeToRun -ExecutionTimeLimit (New-TimeSpan -Hours 2)
$p       = New-ScheduledTaskPrincipal -UserId $env:USERNAME -LogonType S4U -RunLevel Highest

foreach ($t in @("08:00","20:00")) {
  Register-ScheduledTask `
    -TaskName "thu-know-update-$($t.Replace(':',''))" `
    -Action $action `
    -Trigger (New-ScheduledTaskTrigger -Daily -At $t) `
    -Settings $set -Principal $p -Force
}
```

- `-StartWhenAvailable` = 错过计划时间后，开机/恢复时尽快补跑。
- `-WakeToRun` = 睡眠状态下尝试唤醒执行（需硬件/BIOS 支持）。
- 仍解决不了"整晚关机"——关机只能补跑，不是准时。
- 若同时留着 WorkBuddy 那两条自动化会重复抓取，**建议二选一**。

# 四、方案 B：搬到一台常开设备（真 24/7，最省事）

**本项目是 `rsync` 一把梭的极简强度**：官网链路只用 Python 标准库，**零 pip 依赖**。适合放：
云服务器（轻量应用服务器最低配足够）、NAS、树莓派、软路由、家里常开的旧电脑。

```bash
# 1) 拷项目（在本地执行；只拷必要文件）
rsync -av --exclude 'build' --exclude '_work' --exclude '*.bak' --exclude '__pycache__' \
      E:/project/thu-know/ user@server:/opt/thu-know/

# 2) 服务器上确认 Python（3.9+ 即可，官网链路 stdlib-only）
python3 -V

# 3) 加 crontab：每天 08:00 与 20:00 各跑一轮，日志留一份
crontab -e
```

crontab 内容：

```cron
0 8,20 * * * cd /opt/thu-know && mkdir -p logs && /usr/bin/python3 cloud_update.py >> logs/update.log 2>&1
```

> 只跑官网链路（默认）时 `cloud_update.py` 不需要任何 pip 包。
> 想在服务器上一起跑公众号，才需要 `pip install wxmp`（Python ≥3.10）并把
> `_work/wechat/wxmp-cookie-header.txt` 传上去。

要给人看的话，再补一个静态服务（`index.html` 是自包含的，直接托管即可）：

```cron
30 8,20 * * * cp /opt/thu-know/index.html /var/www/thu-know/index.html
```

**迁移后要注意两点：**
1. **出口 IP 变了。** 家宽 → 云机房 IP，个别高校站点对机房 IP 可能限流或 403（尤其只给 `http://` 的老站）。首次上线务必手动跑一轮，看 `logs/update.log`。
2. **源码同步。** 以后改 `fetch_campus.py` / `template.html`，记得重新同步；或放进 git，服务器上 `git pull`。

# 五、方案 C：云函数 FC / SCF + 对象存储（推荐，成本 ≈ 0）

**这是「不依赖开机 + 不花积分 + 时长宽松」的最优解。** 阿里云 FC / 腾讯云 SCF 都能「Cron 定时触发 Python，直接写对象存储」，无需管理服务器。

## 5.1 一个必须先纠正的认知错误

> 很多人（包括某些方案）以为「把数据写进 OSS，网站就更新了」。**本项目不成立。**

`index.html` 是把数据**内嵌**进去的单文件：

```html
<script id="notice-data" type="application/json"> … 1.69 MB JSON … </script>
```

前端用 `document.getElementById("notice-data").textContent` 读取，**运行时不请求 `data/*.json`**。
所以「写 `data/latest.json` 就更新网站」是错的。正确做法二选一：

| 做法 | 要上传什么 | 说明 |
|---|---|---|
| **A. 上传整站（推荐，零改造）** | `index.html` **本身** | 函数里重跑 `build()` 生成新 `index.html`，再上传覆盖 |
| B. 改造为运行时拉取 | `data/*.json` | 把数据从 HTML 挪出来，前端 `fetch()`。上传量小，但要改代码，且失去「双击离线可用」 |

`deploy/serverless/handler.py` 走的是 **A**：跑 `cloud_update.py` 重建 `index.html`，
然后把 `data/*.json` **和 `index.html`** 一起回写对象存储。

## 5.2 为什么本项目在云函数上"几乎不要配置"

- **官网链路零第三方依赖**，核实过 import 全是标准库：
  ```
  refresh.py      : argparse concurrent.futures glob json os re shutil sys time urllib datetime
  fetch_campus.py : argparse datetime gzip json os re ssl sys time urllib zlib
  cloud_update.py : argparse glob json os subprocess sys time datetime
  ```
- 官方 `oss2` 体积大（900+ 文件 / 22 MB）且含平台相关 C 扩展（Windows 打的 `.pyd` 在 Linux FC 上加载不了）
  → 项目自带纯标准库的 `deploy/serverless/oss_min.py`（V1 签名，已与官方 SDK 逐字节对拍）。
- 结果：**阿里云 FC 侧零依赖**，ZIP 保持纯代码（约 **1.16 MB / 11 个文件**）。

> 唯一例外：`fetch_wechat.py` 的 API 模式要 `wxmp`。**所以公众号不建议上云**（见第一节）。

## 5.3 无状态：基线必须先从对象存储拉回来

FC/SCF 每次执行都是**全新、用完即弃**的容器，**没有持久磁盘**。而本项目是
「读上一轮 `data/*.json` → 合并 → 写回」的**只增不减**逻辑——不先拉回基线，每轮都从零开始，历史全丢。
`handler.py` 的 `pull_baseline()` 就是干这个的。

## 5.4 执行链路

```
定时触发器（Cron，如 0 0 8,20 * * *）
        │
        ▼
云函数容器（一次性，无持久盘）
  ① 复制函数包代码 → /tmp/thu-know（代码目录只读，必须复制到可写区）
  ② 从 OSS/COS 拉上一轮 data/*.json  ← 关键，否则历史丢失
  ③ python cloud_update.py
       ├─ refresh.py        重建 index.html（合并 data/*.json；也保留 pkuknow.cn 上游接口能力）
       └─ fetch_campus.py   抓浙大/上交/西交，再重建 index.html
     （上千行进度收进 _work/run.log，终端只留约 15 行摘要）
  ④ 回写 data/*.json + index.html + _work/run.log → OSS/COS（覆盖）
        │
        ▼
静态托管 / CDN / EdgeOne Pages 读取新 index.html
```

> 为什么先写 `data/*.json` 再传 `index.html`：前者是下一轮的**基线**，后者才是**网站本体**。

## 5.5 成本：基本免费

| 项目 | 免费额度 |
|---|---|
| 阿里云 FC | 每月约 40 万 GB·s + 100 万次调用 |
| 腾讯云 SCF | 每月约 40 万 GB·s + 100 万次调用 |
| OSS / COS 存储 | 项目仅几 MB，月费 **几毛钱** |

估算：单次约 3~4 分钟 × 512 MB ≈ 100 GB·s；每天 2 次 × 30 天 = 60 次 ≈ **6 千 GB·s/月**，
只占免费额度的 **4~5%**。**实际成本接近 0** —— 这是选云函数最强的理由。

## 5.6 时长上限（两边不一样，务必注意）

- **腾讯云 SCF：单次执行硬上限 15 分钟**（900 秒）。项目一轮就贴着这条线，**风险高**。
- **阿里云 FC：上限更宽松**（可按函数配置到小时级），**首选**。

若超时，三招降载：`--max-per-source 4`（每源少抓几条）、把浙大单独拆成一个函数（它最慢）、或降频。

## 5.7 部署步骤

### 阿里云 FC（首选）

> 详细分步操作（含 RAM 角色策略、控制台字段表、排错表）见 **`deploy/serverless/README.md`**，下面是要点。

1. **建桶**：OSS 建 Bucket（如 `thu-know-site`），记下 Endpoint。
2. **打包**：`python deploy/serverless/package.py` → `dist/fc-thu-know.zip`（纯代码，无依赖）。
3. **建函数**：运行环境 **Python 3.10**；入口 `handler.handler`；内存 **512 MB**；
   **超时设 1800 秒以上**；执行角色绑一个只对该 Bucket 有读写权限的 **RAM 角色**；**不要绑 VPC**（否则出不了公网）。
4. **设环境变量**：`BUCKET`、`ENDPOINT=oss-cn-hangzhou.aliyuncs.com`、`PREFIX=thu-know`。
   （公众号一律不开，**不要**设 `WITH_WECHAT`。）
5. **测试**：先设 `SKIP_CAMPUS=1` 跑通「拉基线 → 抓取 → 回写」（约 2 分钟），再删掉该变量测全量。
6. **加定时触发器**：Cron `0 0 8,20 * * *`（每天 08:00 / 20:00，6 段式，含秒；时区 Asia/Shanghai）。

### 腾讯云 SCF（若已在腾讯云生态）

逻辑完全一致，差异点：
1. 依赖改为 **`cos-python-sdk-v5`**，设 `STORAGE_BACKEND=cos`、`ENDPOINT=cos.ap-guangzhou.myqcloud.com`。
   打包须在 **Linux** 环境：`python deploy/serverless/package.py --backend cos`。
2. **单次执行上限 15 分钟**——一轮抓取贴线，务必实测；超时就用 `--max-per-source` / 拆函数 / 降频。
3. 触发器用 SCF 的「定时触发」，可自定义 Cron。

## 5.8 网站怎么"感知"更新

因为 `index.html` **内嵌**了数据，「数据感知」的实质是**整站重新部署**，不是"改一个 json"。

| 托管方式 | 数据更新后如何处理 |
|---|---|
| **OSS / COS 静态网站托管**（和函数同桶） | 覆盖 `index.html` 即生效；**若开了 CDN 需刷缓存**，或把 TTL 设短（如 5 分钟） |
| **腾讯云 EdgeOne Pages 等独立平台** | 在函数末尾调该平台的**部署钩子 URL**（`handler.py` 加一行 `urllib.request.urlopen(DEPLOY_HOOK)`） |
| **WorkBuddy「发布为应用」** | 与本机链是两套；更新后需重新发布，不适合无人值守 |

# 六、方案 D：WorkBuddy 云上模式定时任务（不写代码，但吃积分）

## 6.1 先说清机制

云上模式的定时任务跑在腾讯云沙箱里、不依赖开机，但**碰不到你本机的 `E:/project/thu-know`**——
要么把项目搬到云端资料库，要么别用这条路。搬上去之后，它更新的是**云端那份**，不会写回本机。

云端沙箱的三个硬属性：

| 属性 | 含义 | 影响 |
|---|---|---|
| **一次性** | 每次全新容器，跑完即释放，**不保留任何文件** | 每轮必须重新取脚本和数据 |
| **有临时磁盘** | 有独立临时目录，但没有你电脑的磁盘 | 中间产物只活在这一次运行里 |
| **可联网** | 实测公网可达，且可写云端资料库 | 抓取和回写都成立 |

由此得出唯一的设计结论：**云端没有持久磁盘 ⇒ 资料库是唯一的持久层，每轮都要"现取 → 跑 → 写回"。**

> ⚠️ **创建入口决定走哪条链**：在桌面客户端建的自动化 = **本机链**；只有在
> **App / 小程序的「云上模式」**下创建，才走**云端链**。

## 6.2 搭建步骤

**步骤 1：把项目搬到云端资料库**（保持相对路径不变）

```
cloud_update.py       ← 无人值守入口
fetch_campus.py
refresh.py
template.html
data/zju.json  data/sjtu.json  data/xjtu.json
```

不需要 `index.html`（每轮重建），也不需要 `*.bak`。可选：`_work/sources-<校区>.json`（补充信息源，见 6.4）。
**公众号相关的 `_work/wechat/` 不要上传**（cookies 是凭据，且云端不放公众号）。

**步骤 2：在「云上模式」下建定时任务**
1. 打开 **WorkBuddy App**（或小程序），顶部模式切到 **云上 / 云端工作**。
2. 「自动化」→ `+` 新建。
3. 频率设 `每天`，时间 `08:00`。⚠️ **频率直接等于积分账单**，确认单次消耗前不要一上来就建早晚两条。
4. 模型挑低倍率的（MiniMax-M3 一类 ≈0.25x），别用 Auto 或 Kimi-K3（1.62x）。
5. 提示词用下面这份。

**步骤 3：先「测试运行」一次**，确认链路真的通。

**步骤 4（可选）：发布为在线链接**，让站点完全脱离你的电脑。

## 6.3 定时任务提示词（复制即用）

```
更新 thu-know 高校通知聚合站点的数据并重建页面。

第一步：从云端资料库取出本项目文件，放到沙箱的工作目录里（保持相对路径）：
cloud_update.py、fetch_campus.py、refresh.py、template.html，以及 data/zju.json、
data/sjtu.json、data/xjtu.json；如果资料库里有 _work/sources-<校区>.json，
```

## 6.4 云端怎么新增信息源（不用改代码）

机制在 `fetch_campus.py`：

```python
merge_sources(campus)  =  内置 SOURCES  +  _work/sources-<校区>.json 的补充
                          （同 id 覆盖，enabled=false 可临时停用某个来源）
```

补充文件就是一份 JSON 数组，写法与内置配置一致：

```json
[
  {"id": "zju_som", "name": "浙江大学管理学院", "url": "https://www.som.zju.edu.cn/", "kind": "list", "max": 6},
  {"id": "sjtu_old", "url": "https://old.sjtu.edu.cn/", "enabled": false}
]
```

- `kind`：`"list"` 抓列表页文章；`"wechat"` 只从这个页面摘 `mp.weixin.qq.com` 链接。
- `enabled: false` = 不抓但保留注册表记录。
- 模板见 `_work/sources.example.json`（文件名不匹配 `sources-<校区>.json`，不会被加载，纯参考）。

**在云端用它的三条注意**：
1. 文件必须一起进资料库，且**每轮都要取进沙箱**（沙箱一次性）。
2. **改完必须回写资料库**，否则下一轮又变回旧清单。
3. **加源 = 加成本**：多一个来源就多一个站点的请求，耗时/日志/积分一起涨。

## 6.5 积分消耗：一个月 400 分够不够

**结论：按现在规模，400 分/月远不够，差一个数量级。**

积分口径：`输入 token + 输出 token`，**每次新消息都会把整个对话历史重新打包**，
所以轮次越多越贵；**工具调用单独计费**；模型倍率差很多（MiniMax-M3 ≈0.25x、Auto ≈1.0x、Kimi-K3 ≈1.62x）。

这个任务为什么贵：它不是问答，是一次 **Craft 模式长任务**——
抓取命令上千行输出（**最大单项**）、8~15 轮、每轮工具步价费、Craft 倍率 ≈ Ask 的 2~3 倍。

| 场景 | 每次消耗 |
|---|---|
| 乐观（已用 `cloud_update.py` + 低倍率模型） | 30 ~ 60 分 |
| 中位（默认设置、原始日志进上下文） | 100 ~ 200 分 |
| 悲观（旗舰模型 + 长对话） | 250 ~ 400 分 |

按中位 **150 分/次** 折算：

| 频率 | 每月次数 | 每月积分 | 400 分够吗 |
|---|---|---|---|
| 每天 2 次 | 60 | ~9,000 | ✗ 差 22 倍 |
| 每天 1 次 | 30 | ~4,500 | ✗ 差 11 倍 |
| 每周 1 次 | 4~5 | ~700 | ✗ |
| 每两周 1 次 | 2 | ~300 | ✓ 勉强 |

**压成本五招**：
1. **用 `cloud_update.py` 当唯一入口** —— 直接把最大的一坨 token（上千行输出）砍成十几行摘要。
2. **挑低倍率模型**（MiniMax-M3 这类 ≈0.25x）。
3. **降频率**：先每天 1 次，不够就每两天 1 次。高校通知日更，一天一次足够。
4. **一次会话做完，别追问**，也别让 agent 去读 `_work/run.log`（提示词已写明）。
5. **先测再定**：个人中心 → 用量管理，手动测试运行一次看实际扣了多少。

> 如果 400 分就是只有 400：这个任务本质是"**执行两条确定性命令**"，不需要 AI 判断。
> 交给确定性执行器 —— 云函数（第五节）、crontab（方案 B）、或国内代码托管平台的定时流水线
> （腾讯 CNB 等）—— **积分消耗为 0**。把云上模式留给"真需要判断"的活（自动发现并验证新源、检查抓取质量、生成简报）。

## 6.6 风险与首轮验证清单

1. **单次时长上限不明**（云沙箱）。95 个来源、每域限速 1.2 秒、还要进详情页，一轮十几分钟正常。
   验证：测试运行时看能否跑到底；跑不完先加 `--max-per-source 4` 降载。
2. **出口 IP 变了**：沙箱出口是腾讯云机房 IP，个别只支持 `http://` 的老学院站可能 403。必须实测失败来源。
3. **沙箱是否放行 Python**：Ubuntu 沙箱通常自带 `python3`，若报 `python: not found` 就改 `python3`。

5. **数据基线别断**：资料库里 `data/*.json` 是唯一基线。**千万不要用空 data 覆盖资料库**。

# 八、和现有本机方案的关系

| 你想要的 | 该用哪条路 |
|---|---|
| 更新**本机这份** `E:/project/thu-know/index.html` | 方案 A / A+（本机），或方案 B（常开机器） |
| **站点本身**托管云端、与本机彻底解耦、**成本接近 0** | **方案 C：云函数**（第五节）—— 免费额度足够 |
| **站点本身**托管云端、且**不想写任何代码** | 方案 D：云上模式（第六节），代价是积分高、时长上限未知 |
| 只是想要一份每日简报推到微信 | 云上模式，且不需要搬整个项目 |
| 想按号成批更新**公众号** | **留在本机**跑 `python cloud_update.py --with-wechat`（见 [wxmp公众号接入.md](wxmp公众号接入.md)） |

> 云函数和云上模式是**同一生态位的两种实现**：都要把项目搬到云端、都能不依赖开机、
> 都需要「写回云端持久层」。区别是云函数要写一份 handler（已备好）、成本≈0；
> 云上模式不用写代码、但吃积分。**选一个即可，不要几条一起开。**

如果两边都想要，做法是：以**云端持久层为唯一权威**，本机需要时再同步一份下来看，而不是两边各自抓取。
