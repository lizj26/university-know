# 方案 A 详述：多号池 + `mp/profile_ext` 分钟级轮询

> 这是对标 `pkuknow.cn/thu` 那条通道的可落地版本。
> 前一篇（`群发级列表-获取途径与通道原理.md`）回答"数据从哪来"，这一篇回答"**我们怎么造**"。

---

## 0. 一句话，和它的边界

**一句话**：把 N 份 `wap_sid2` 组成号池，按配额轮换，每个号每分钟碰一次"历史消息第一页"，
靠 10 条缓冲吃掉漏掉的轮次 —— 于是拿到"分钟级 + 不漏一篇 + 长期"。

**它适用的**：几十到一两百个号、要分钟级、要长期无人值守。

**它不适用的**：
- 只有一个凭据 → 配额撑不住（见 §2）
- 只要热点、不要求不漏 → `sogou` 零凭据就够，别碰这个
- 想"一次抓完永远不管" → 凭据会过期，必须有人补号（见 §4.3）

## 1. 整体形状

```
        ┌──────────── 号池层（资产）────────────┐
        │  a1.txt + a1.json    b1.txt + b1.json │   每套 = 一份会话
        └───────────────┬───────────────────────┘
                        │ acquire() / report()
        ┌───────────────▼───────────────────────┐
        │ 调度层：配额窗口 + 冷却退避 + 最少使用优先 │
        └───────────────┬───────────────────────┘
                        │ 选中一个号
        ┌───────────────▼───────────────────────┐
        │ 采集层：GET profile_ext?action=getmsg  │   每个号每次只拉 1 页
        │         offset=0 & count=10            │
        └───────────────┬───────────────────────┘
                        │ general_msg_list（按批次，含 idx 1..8）
        ┌───────────────▼───────────────────────┐
        │ 存储层：seen 去重账本 + 健康度状态 + JSONL │
        └───────────────┬───────────────────────┘
                        │ 只有"新的"往下走
        ┌───────────────▼───────────────────────┐
        │ 加工层：裸抓正文 → 图片本地化 → AI 抽取   │   完全不需要微信凭据
        └───────────────────────────────────────┘
```

关键分工：**只有第 3 层吃凭据，第 5 层一点不需要**。
所以我们能把"贵的东西"压到最小，把"便宜且值钱的东西"（正文、AI）做厚。

## 2. 为什么必须是"池"——先算配额

### 2.1 单凭据的真实天花板

已知事实（我们自己的记录）：**10-10 那次，3 个公众号连续跑，就撞了 `200013`。**
单凭据不存在"能跑多快"的问题，只有"能跑多久"的问题。

保守假设每号 **120 次/小时**（这个数没有实测到撞墙点，见 §10），得到这张表：

| 场景 | 轮询周期 | 目标号数 | 请求/小时 | 需要活号 |
|---|---|---|---|---|
| 个人跟踪 | 2 小时 | 40 | 20 | **1** |
| 准实时 | 10 分钟 | 40 | 240 | **2** |
| 对标级 | 62 秒 | 145 | 8420 | **约 70** |
| 极端 | 5 分钟 | 145 | 1740 | **约 15** |

**这就解开了"清华知道"的成本结构**：

它不需要 145 个号（那条路是"一号盯一号"，很浪费），
按 62 秒 × 145 号的量算，**几十个号轮换就够**。
"消耗挺多资金"买的不是带宽，是**这几十个号的存活**。

### 2.2 一张图看懂"号数换频率"

```
号数 ↑  ──────────────────────────────►  可达频率 ↑
 1 个号   20 次/时     ≈ 40 号每 2 小时一轮
 2 个号   240 次/时    ≈ 40 号每 10 分钟一轮
 5 个号   600 次/时    ≈ 40 号每 4 分钟一轮
70 个号  8400 次/时    ≈ 145 号每 62 秒一轮（对标水平）
```

**没有免费的高频**。要么加号，要么降频，要么换通道（§5）。

## 3. 号池怎么建

### 3.1 一份凭据 = 一整套会话，不是一行 cookie

这是最容易踩的坑：

| 字段 | 从哪来 | 作用 |
|---|---|---|
| `wap_sid2` | Cookie 头 | 会话凭证，**缺它必然 `-3`** |
| `uin` | 地址栏 / 请求参数 | 账号标识 |
| `key` | 地址栏 / 请求参数 | 本次会话的密钥 |
| `pass_ticket` | 地址栏 / 请求参数 | 票据 |
| `appmsg_token` | 请求参数（旧接口常要） | 列表接口令牌 |

**这五个必须同源配套。** 拿 A 号的 cookie 配 B 号的 `key`，一定 `-3` ——
而 `-3` 的提示是"cookie 无效"，很容易误判成"号被封了"，去换号，白折腾。

所以池的落地形态就是一个 `名字.txt` + `名字.json` 成对：

```
_work/wechat/wxmp-pool/
  a1.txt          Cookie: wap_sid2=...
  a1.json         {"uin": "...", "key": "...", "pass_ticket": "...", "appmsg_token": "..."}
  a1.state.json   （程序写：配额/冷却/健康度）
  b1.txt / b1.json / b1.state.json
```

`_work/wechat/wxmp-pool/` 已在 `.gitignore` 里 —— **每个 `.txt` 等同密码**。

### 3.2 号从哪来

| 来源 | 成本 | 寿命 | 适合 |
|---|---|---|---|
| 自己手机微信 + `wap_sid2_capture.py` 抓包 | 0（人工 5 分钟） | 30 分钟 ~ 3.5 小时 | 起步、应急 |
| 副号 / 小号 + 常驻抓包 | 一张卡 | 同上 | 稳定补号 |
| 买的号 | 钱 + 风险 | 同上 | 不建议 |

抓一份的操作（工具已就绪）：

```bash
# 1. PC 微信（推荐，证书好装）或安卓副号（WireGuard 模式）
mitmdump -s tools/wap_sid2_capture.py --mode local

# 2. 在微信里打开目标号任意文章 → 右上「…」→ 查看公众号 → 查看历史消息
#    插件会自动落盘 cookie 与参数，并打印闸门判定

# 3. 加进号池（顺手带上参数）
python tools/wxmp_spider.py pool --add a1 --cookie-file _work/wechat/wxmp-wap-cookies.txt
```

### 3.3 一个号能盯多少个号——这是最省钱的杠杆

个人微信号关注公众号的上限**约 1000 个**。

所以：**一个号就能覆盖全部 145 个目标号**，不需要"一号盯一号"。
号池扩的是**频率**，不是**覆盖面**。这两件事很多方案搞混，成本差一个数量级。

**但有个前提**：号最好**关注**了目标号。外部资料说未关注只能看最近 10 篇、
翻不到第二页；这一点我们自己还没验证（§10），所以保守做法是**先关注再跑**。

### 3.4 寿命与补号速率——这里藏着一个硬结论

凭据寿命按 3 小时估：

| 号池规模 | 每天需要补的号 | 结论 |
|---|---|---|
| 1 个 | 0.3 个/天 | 人肉可行 |
| 3 个 | 1 个/天 | 人肉可行（每天抓一次） |
| 5 个 | 1.7 个/天 | 勉强 |
| 70 个 | **560 个/天，约 2.6 分钟一个** | **人肉不可能** |

**硬结论：靠 `wap_sid2` 的号池，规模上限大约在 5~10 个号。**

再往上，要么凭据寿命其实比 3 小时长得多（我们没测准），
要么**对方根本不用 `wap_sid2`，而是用了能长期保活的通道**——见下节。

## 4. 两支无法从数据区分的实现

我在上一篇里用三条指纹锁定了"批次级列表接口"。但**批次级接口有两个分支**，
从返回数据上看不出区别：

| | getmsg 号池（我们这条） | appmsgpublish 后台号池 |
|---|---|---|
| 凭据 | `wap_sid2`（关注者会话） | mp 后台 `token` + cookie（运营者登录态） |
| 寿命 | **30 分钟 ~ 3.5 小时** | **数天 ~ 数月** |
| 号的门槛 | 一个普通微信号 | 一个**有公众平台权限**的主体（个人主体也行，但要实名） |
| 覆盖 | 只能看"能看到的"历史 | 可搜任意号，深度更好 |
| 频率限制 | 按号/IP 风控，`200013` | 按天配额（每号约百次级），超了报 `200013` 或权限错 |
| 补号成本 | 5 分钟人工/个 | 注册+实名，一次性但贵 |
| 我们能不能做 | **能**（已实现） | 能（`wxmp_spider.py login` 那条路），但要有主体 |

**判断依据（对不上数据的都不算）**：
- 若对方号池规模 > 10 且频率到分钟级 → 更可能是 **appmsgpublish 后台号池**
  （因为 `wap_sid2` 那支的补号速率撑不住）
- 若对方数据里出现 `appmsgpublish` 特有的字段（如 `album_id`、`item_show_type`）→ 锁定后台号
- 若只出现 `comm_msg_info` 那套字段 → 锁定 getmsg

我们所知的数据里没有这两类特有字段（它们只暴露规范化后的 6 个字段），所以**确证不了**。
写出来是为了不让"假设 A"被误读成"一定就是 getmsg"。

## 5. 调度算法（`tools/wxmp_pool.py` 已实现）

### 5.1 选号

```
pick = argmin( used/quota , last_used )
```

先看"用量占比"，再看"多久没用"。
不按"轮询下标"轮转，是因为号会不均匀地进冷却 —— 轮转下标会把请求堆在剩下少数活号上，
一崩全崩。

### 5.2 配额窗口

按整点对齐，跨窗清零：

```
window = floor(now / 3600) * 3600
if state.window != window: state.used = 0
```

对齐整点而不是"从首次请求起 1 小时"，是为了多个进程（任务计划程序并发跑）看到同一个窗口，
不会各算各的。

### 5.3 冷却退避

| 返回值 | 含义 | 冷却 | 判死 |
|---|---|---|---|
| `0` | 正常 | 清冷却、`fail=0` | — |
| `200013` | 限流 | `min(900 × 2^(n-1), 7200)` 秒 | 不判死，一直退避 |
| `-3` | 无会话 | `3600 × n` 秒 | **连续 3 次 → dead** |
| 非 JSON / 网络错 | 验证墙 | 300 秒 | 不判死 |

`-3` 判死阈值给 3 次，是因为 `-3` 也可能是"参数没配套"而不是"号废了"。
判死后删掉 `a1.state.json` 就能复活 —— 这是故意的，避免误杀一个好号。

### 5.4 换号策略

**一次任务固定用一个号跑完，只在出错时换。**

为什么不每页换号：`getmsg` 虽然无状态，但同一 biz 的连续翻页换会话会让日志无法归因；
而且每页换号会让所有号均匀消耗，反倒更容易整体撞限。

换号后**从 offset 0 重来**：`_list_history_once` 内部按链接去重，重来不产生重复条目，
最坏多花几次请求。简单、正确，比"从断点续"少一半 bug。

### 5.5 状态跨进程共享

`a1.state.json` 用"写临时文件 + `os.replace`"原子替换。
任务计划程序每 10 分钟起一个进程时，不会读到半截 JSON。
共用同一个池目录，配额就是全局的 —— 不需要额外的中心服务。

## 6. 一轮的完整时序

```
1. acquire()                     → 选中 a1（used 最少）
2. 组请求
     GET https://mp.weixin.qq.com/mp/profile_ext
         ?action=getmsg&__biz=<biz>&f=json&offset=0&count=10
         &is_ok=1&scene=124&uin=&key=&pass_ticket=&appmsg_token=
     Headers: Cookie=a1 的 cookie
              User-Agent=<手机微信 UA>
              Referer=.../mp/profile_ext?action=home&__biz=<biz>&scene=124
3. 判 ret（见 §5.3 表）          → 失败就 report + 换号重试（默认最多换 2 次）
4. parse_history()
     general_msg_list → list[]（每条是一次群发）
     摊平 app_msg_ext_info + multi_app_msg_item_list → idx 1..8 全部展开
5. diff_new(seen, rows)          → 只留没见过的链接
6. 落盘 output.jsonl（带 seen_at）+ save_seen()
7. report(0)                     → ok+1，fail 清零
8. jitter_sleep(interval)        → 抖动 ±50%，别让请求落在整秒
```

**第 4 步是"不漏"的核心**：`getmsg` 一次返回的是**批次**，
一批多图文会同时给出主图文和 `multi_app_msg_item_list` 里的其余篇 —— 所以 idx 1..8 是全的。
这一点在测试里有专门用例（`test_flat_counts_multi_and_skips_non_article`）。

## 7. "不漏"的数学：延迟要花钱，不漏不花钱

这是这个方案最反直觉、也最该先想清楚的一点。

`getmsg` 第一页返回 **10 条批次**。只要"两次轮询之间新增的批次 ≤ 10"，就**不可能漏**。

而一个高校号平均每天发 1~2 次。代入：

| 轮询周期 | 单号两次轮询间新增批次 | 会漏吗 | 40 个号的请求量 |
|---|---|---|---|
| 2 小时 | 0.1 | 不会 | 20 次/小时 |
| 12 小时 | 0.6 | 不会 | 3.3 次/小时 |
| 24 小时 | 1.2 | 不会 | 1.7 次/小时 |
| 5 天 | 6 | 不会 | — |
| 10 天 | 12 | **会** | — |

**结论：对"一天发 1~2 次"的号，一天查一次也不漏，延迟只是 24 小时。**

所以：

> **"不漏"几乎是免费的，"实时"才是花钱的。**
> 你要买的不是"不漏"，是"多久之内知道"。

这条直接决定了报价和档位（§8）。也解释了为什么"清华知道"能靠 62 秒节拍做成产品壁垒 ——
它卖的是**时效**，不是**完整**。

## 8. 三档落地方案

### L0 · 今天就能跑（单号，2 小时一轮）

```bash
python tools/wxmp_spider.py history --name 浙江大学 \
    --watch --interval 7200 -o _work/wechat/zju.jsonl
```

- 请求量：20 次/小时，**单凭据能扛**
- 延迟：≤ 2 小时
- 补号：凭据过期时重抓一次（约每 3 小时一次，可写进待办）
- 适合：**先验证价值**，确认"2 小时延迟"够不够用

### L1 · 小号池（3~5 个号，10~20 分钟一轮）

```bash
# 加号
python tools/wxmp_spider.py pool --add a1 --cookie-file <cookies.txt>
python tools/wxmp_spider.py pool --add b1 --cookie-file <cookies2.txt>
python tools/wxmp_spider.py pool --status

# 用池跑（配额 120/号/小时，3 号 = 360 次/小时）
python tools/wxmp_spider.py history --name 浙江大学 --pool-dir _work/wechat/wxmp-pool \
    --watch --interval 900 -o _work/wechat/zju.jsonl
```

- 请求量：160 次/小时（40 号 × 4 次）
- 延迟：≤ 15 分钟
- 补号：每天 1~2 个
- 适合：**长期跑的主力档**，人肉补号可持续

### L2 · 对标级（分钟级，几十个号或协议层）

- `wap_sid2` 路线**到不了**（补号速率见 §3.4）
- 要么走 `appmsgpublish` 后台号池（需要若干有主体的号，配额按天算）
- 要么上协议层（iPad / PC hook，登录态长期保活）
- **超出本项目当前范围**，属于要不要花钱/花设备的决策

## 9. 风险与红线

> 这一节只是目录。**账号风险的完整版在 `docs/号池账号风险.md`**：
> 三层主体、六级梯度、连坐四通道、买号风险、熔断设计与早期信号清单。
> 其中最该记住的一条：号池放大的不是频率风险，是**环境同质化风险**。

| 风险 | 说明 | 缓解 |
|---|---|---|
| **封号** | 个人号高频拉列表会被限制登录 | 每号低配额、抖动、别用主号 |
| **IP 连坐** | 同一出口跑多个号，一个被判可能全挂 | 号多时分散出口（这一条我们还没做） |
| **`200013` 突然收紧** | 2026-07-30 已经发生过一次接口级收紧 | 靠号池分摊 + 退避，别把单号当命脉 |
| **凭据泄露** | cookie 等同密码 | `wxmp-pool/` 已在 `.gitignore`；日志只打掩码 |
| **合规** | 全文抓取 + 二次分发有版权风险 | 只做「标题 + 摘要 + 原文链接」对外展示更安全 |
| **未关注号取不到全量** | 外部资料称未关注只能看 10 篇（未验证） | 抓凭据的号先关注目标号 |

**红线**：不拿这个池去撞登录接口、不做自动注册、不对外转售正文。

新增 CLI 的行为：

```text
python tools/wxmp_spider.py pool --status
  → 每个号的 状态/本小时用量/成功/连败/冷却/掩码凭据，末尾给"理论吞吐"

python tools/wxmp_spider.py history --pool-dir <dir>
```

`--pool-dir` 与 `--cookie-file` 二选一：给了池就忽略单文件，避免"以为在用池、其实还在用旧 cookie"。

## 11. 还没验证的事（写出来，免得当成已知）

1. **单号真实配额上限**——`120/小时` 是保守假设，没实测到撞墙点。撞墙点可能更高（更省钱），也可能更低（要更多号）。
2. **未关注号能否翻页**——外部资料说只能看 10 篇，我们没有真凭据验证过。
3. **同 IP 多号是否连坐**——如果连坐，号池的价值会大打折扣，必须配独立出口。
4. **`200013` 的触发维度**——是"按号"、"按 IP"还是"号×IP"，决定了号池该怎么分散。
5. **`wap_sid2` 的真实寿命分布**——3 小时是外部说法，我们只有零星观察。这个数直接决定 §3.4 的补号速率。

这五条里，第 1 和第 5 条是**成本模型的两个关键常数**，值得优先测。
测法：拿一份真凭据，用 `--delay-ms 0` 连打到 `200013`，记下次数；每 20 分钟探一次，记下失效时刻。
